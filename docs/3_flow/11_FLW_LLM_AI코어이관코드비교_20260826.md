## 1. 문서 목적

현재 프로젝트에는 서로 다른 두 LLM 실행 계통이 공존한다.

```text
Admin LLM
→ backend/app/services/admin_llm.py
→ backend/app/services/llm/
→ Ollama / Gemini / Mock
```

```text
일반 LLM API
→ backend/app/services/llm_service.py
→ ai/llm/
→ MedGemma + LoRA Adapter
```

두 계통은 모델 목록, 요청·결과 계약, Registry, 실행 방식이 서로 다르다. 따라서
`backend/app/services/llm` 디렉터리를 그대로 `ai/llm`에 복사하면 Registry와 공개
함수가 충돌하고 중복 구조가 그대로 남는다.

이 문서는 실제 코드를 비교하여 다음을 결정하기 위한 자료다.

- 무엇을 `ai/llm`으로 옮길 것인가
- 무엇을 Backend에 남길 것인가
- 기존 Admin API와 일반 LLM API를 어떻게 유지할 것인가
- MedGemma를 공통 Provider 계약에 어떻게 연결할 것인가
- Requirements와 테스트를 어떻게 분리할 것인가

## 2. 결론 요약

단순한 디렉터리 이동보다 **공통 Domain 계약을 먼저 확정한 뒤 Provider를 하나씩
편입하는 방식**이 안전하다.

```text
Frontend / API Client
→ Backend Router
→ Backend Schema Adapter
→ ai.llm.LlmApplicationService
→ Provider Registry
→ Ollama / Gemini / MedGemma / Mock
← 공통 ProviderGenerateResult
← Backend Response Schema
```

권장 책임 경계는 다음과 같다.

| 구분 | `ai/llm` | Backend |
|---|---|---|
| 모델·Provider 계약 | 유지 | 사용 |
| Model/Provider Registry | 유지 | 설정값을 주입 |
| Ollama/Gemini/MedGemma 실행 | 유지 | 직접 실행하지 않음 |
| FastAPI Router | 알지 못함 | 유지 |
| Pydantic Request/Response | 알지 못함 | 유지 |
| 환경변수 읽기 | 알지 못함 | 유지 |
| HTTP 상태 코드 변환 | 알지 못함 | 유지 |
| 인증·관리자 권한 | 알지 못함 | 유지 |

`ai/llm`은 `app.*`, FastAPI, Pydantic, SQLAlchemy를 Import하지 않는 독립 패키지로
유지한다.

## 3. 현재 코드 구조 비교

### 3.1 Admin LLM 계통

중심 함수는 다음과 같다.

```text
LlmApplicationService.run()
```

호출 흐름:

```text
POST /api/admin/llm/run
→ app.api.admin.router.run_llm()
→ app.services.admin_llm.run_model()
→ LlmApplicationService.run()
→ ModelRegistry.resolve()
→ ProviderRegistry.resolve()
→ provider.generate()
← ProviderGenerateResult
← LlmExecutionResult
← LlmRunResponse
```

현재 Admin 계통은 다음 장점을 이미 갖고 있다.

- 비동기 Provider 계약
- Provider별 동시 실행 제한
- 모델 가용성 조회
- Provider 오류의 Domain 예외 변환
- 토큰 수와 종료 사유 반환
- Model Registry와 Provider Registry 분리

### 3.2 일반 LLM API 계통

중심 함수는 다음과 같다.

```text
MedGemmaEngine.generate()
```

호출 흐름:

```text
POST /api/llm/generate
→ app.api.llm.router.generate_response()
→ app.services.llm_service.generate()
→ ai.llm.get_engine()
→ MedGemmaEngine.generate()
→ LoRA Adapter 선택
→ Hugging Face 모델 추론
← 생성 문자열
← LlmGenerateResponse
```

현재 일반 LLM 계통은 다음 역할을 갖고 있다.

- MedGemma Base Model 1회 로딩
- 여러 LoRA Adapter 지연 로딩
- Adapter ID 기반 모델 선택
- GPU 및 선택적 패키지 미설치 오류 처리

### 3.3 핵심 차이

| 항목 | Admin LLM | 일반 LLM / MedGemma |
|---|---|---|
| 실행 방식 | `async` | 동기식 GPU 추론 |
| 입력 | 단일 `prompt` | role/content `messages` |
| 결과 | 답변, 토큰, 시간, 종료 사유 | 생성 문자열 |
| Registry | 모델 + Provider 연결 | LoRA Adapter 목록 |
| 오류 | Domain 예외 | `KeyError`, `RuntimeError` |
| 모델 | Ollama, Gemini, Mock | MedGemma LoRA |
| API | `/api/admin/llm/*` | `/api/llm/*` |

## 8. MedGemma Provider 편입 비교

### 8.1 현재 동기식 호출

현재 Backend Service는 동기식으로 Engine을 호출한다.

```python
engine = get_engine(hf_token=settings.hf_token)
content = engine.generate(model_id, messages)
```

이 호출을 비동기 Admin Provider 안에서 그대로 실행하면 FastAPI Event Loop가 GPU
추론이 끝날 때까지 막힐 수 있다.

### 8.2 권장 Adapter 형태

설계 예시이며 실제 구현이 아니다.

```python
# ai/llm/providers/medgemma.py

class MedGemmaLlmProvider:
    key = "medgemma"
    is_mock = False

    def __init__(self, engine, max_concurrency: int = 1):
        self._engine = engine
        self._semaphore = asyncio.Semaphore(max(1, max_concurrency))
        self._inference_lock = threading.Lock()

    async def generate(self, request, model):
        messages = [{"role": "user", "content": request.prompt}]

        async with self._semaphore:
            answer = await asyncio.to_thread(
                self._generate_locked,
                model.id,
                messages,
            )

        return ProviderGenerateResult(answer=answer)

    def _generate_locked(self, model_id, messages):
        with self._inference_lock:
            return self._engine.generate(model_id, messages)
```

두 제한이 모두 필요하다.

- `asyncio.to_thread()`: Event Loop Blocking 방지
- 추론 Lock/Semaphore: `set_adapter()`와 모델 추론의 동시 실행 충돌 방지

현재 Engine은 Adapter 로딩 과정만 Lock으로 보호한다. `set_adapter()`부터
`generate()`가 끝나는 구간은 보호하지 않으므로 여러 Adapter를 동시에 실행하면
요청 간 Adapter 선택이 섞일 가능성이 있다.

### 8.3 Messages 보존

기존 `/api/llm/generate`는 여러 role/content 메시지를 받는다. Admin 계약처럼 마지막
Prompt만 남기면 대화 이력이 유실된다.

공통 요청 계약은 다음처럼 확장하는 것이 안전하다.

```python
@dataclass(frozen=True)
class LlmMessage:
    role: Literal["system", "user", "assistant"]
    content: str

@dataclass(frozen=True)
class ProviderGenerateRequest:
    prompt: str | None = None
    messages: tuple[LlmMessage, ...] = ()
    document_name: str | None = None
    max_output_tokens: int | None = None
```

다만 `prompt`와 `messages`를 동시에 허용할지, Backend Adapter에서 항상 messages로
정규화할지는 구현 전에 결정해야 한다. 권장안은 Core에서는 messages만 받고 Admin
Adapter가 단일 Prompt를 user message 하나로 변환하는 방식이다.

```python
async def run_model(request: LlmRunRequest) -> LlmRunResponse:
```

## 10. API 호환 전략 비교

### 10.1 현재 외부 계약

Admin API:

```text
GET  /api/admin/llm/models
POST /api/admin/llm/run
POST /api/admin/llm/compare
```

일반 LLM API:

```text
GET  /api/llm/models
POST /api/llm/generate
POST /api/llm/compare
```

Frontend Admin은 현재 `/api/admin/llm/models`와 `/api/admin/llm/run`을 사용한다.
Repository 검색 결과에서는 Frontend가 `/api/llm/*`를 직접 호출하는 코드는 확인되지
않았지만 Backend의 공개 Endpoint로 등록되어 있으므로 사용자가 없다고 단정하여
삭제하면 안 된다.

### 10.2 권장 이관 방식

```text
기존 Admin API ─┐
                ├→ 각각의 Backend Adapter → 같은 ai.llm Core
기존 일반 API ──┘
```

1차 이관에서는 Endpoint와 DTO를 변경하지 않는다. Core 안정화와 실제 호출자 확인 후
API 통합 여부를 별도 결정한다.

## 11. Requirements 비교

### 11.1 현재 상태

`ai/llm/requirements.txt`:

```text
torch
transformers
peft
bitsandbytes
accelerate
```

`backend/requirements.txt`:

```text
httpx
google-genai
```

Admin Provider를 `ai/llm`으로 옮긴 뒤 Backend가 기존 `ai/llm/requirements.txt`를
그대로 참조하면 CPU Backend에도 수 GB 규모의 GPU 패키지가 설치될 수 있다.

### 11.2 권장 분리

```text
ai/llm/
├─ requirements-api.txt         # httpx, google-genai
├─ requirements-medgemma.txt    # torch, transformers, peft, bitsandbytes, accelerate
└─ requirements.txt             # 전체 LLM Lab/Worker용 통합 참조
```

예시:

```text
# ai/llm/requirements.txt
-r requirements-api.txt
-r requirements-medgemma.txt
```

```text
# backend/requirements.txt
-r ../ai/llm/requirements-api.txt
```

이 구조에서는 일반 CPU Backend가 MedGemma GPU Runtime을 강제로 설치하지 않는다.
MedGemma를 같은 Backend 프로세스에서 실행하는 배포판만 전체 requirements를 설치한다.

Test로 둔다.

## 16. 주요 위험과 방지 기준

### 높음: MedGemma 대화 이력 유실

Admin의 단일 Prompt 계약만 기준으로 통합하면 `/api/llm/generate`의 messages가
유실된다.

방지 기준:

- Core 요청은 role/content Messages를 표현할 수 있어야 한다.
- Admin Prompt는 Backend Adapter에서 user message로 변환한다.

### 높음: Adapter 동시 전환

MedGemma Engine의 `set_adapter()`와 추론이 동시에 실행되면 다른 요청의 Adapter와
섞일 수 있다.

방지 기준:

- Adapter 선택부터 추론 완료까지 하나의 동시성 경계로 보호한다.

### 높음: 무거운 의존성의 Backend 강제 설치

방지 기준:

- API Provider와 MedGemma requirements를 분리한다.
- CPU Backend 이미지에는 필요한 Provider 의존성만 설치한다.

### 중간: 기존 API 회귀

방지 기준:

- `/api/admin/llm/*`, `/api/llm/*` Endpoint를 1차 이관에서 유지한다.
- camelCase와 snake_case 응답을 각각 회귀 테스트한다.

### 중간: Domain 예외의 HTTP 코드 손실

방지 기준:

- `ai/llm`은 Domain 예외만 발생시킨다.
- Backend Router 또는 Adapter가 422/429/502/503/504로 변환한다.

### 중간: 외부 Gemini로 의료 문서 전송

방지 기준:

- API Key와 원문을 로그에 남기지 않는다.
- 실제 의료·개인정보 전송 전 동의, 마스킹, 보관 정책을 별도로 확정한다.

## 17. 구현 전 결정할 사항

1. 공통 Core 입력을 messages 하나로 통일할지
2. MedGemma를 이번 작업에서 실제 Provider로 편입할지
3. Mock Provider를 개발 환경에서만 등록할지
4. 두 API를 장기적으로 유지할지, 추후 하나로 통합할지
5. MedGemma를 Backend 프로세스에서 실행할지 별도 GPU Worker로 분리할지
6. 모델 목록을 코드 상수로 둘지 별도 설정 파일로 관리할지

권장 기본값:

```text
두 API 유지
→ 내부 Core만 단일화
→ Core 입력은 messages 기준
→ Admin Prompt는 Adapter에서 messages로 변환
→ Mock은 개발 설정에서만 등록
→ MedGemma는 Provider로 감싸되 GPU Runtime은 선택 설치
```

## 18. 완료 기준

- `ai/llm`에 `app.*`, FastAPI, Pydantic, SQLAlchemy Import가 없다.
- Ollama, Gemini, MedGemma가 같은 Provider 계약을 구현한다.
- Model ID와 Provider 연결 기준이 한 곳에만 존재한다.
- Admin과 일반 LLM Endpoint의 URL 및 JSON 계약이 유지된다.
- 기존 Admin LLM 테스트 10개의 동등한 회귀 범위가 유지된다.
- MedGemma messages와 LoRA Adapter 선택 기능이 유지된다.
- CPU Backend 설치 시 Torch/BitsAndBytes가 강제 설치되지 않는다.
- Docker 또는 실행 환경에서 `import ai.llm`이 성공한다.
- 실제 GPU 검증을 실행하지 못했다면 완료 보고서에 명확히 기록한다.
