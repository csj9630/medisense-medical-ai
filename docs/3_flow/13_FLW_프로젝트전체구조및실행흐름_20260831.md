# 프로젝트 전체 구조 및 실행 흐름 분석

- 작업일: 2026-08-31
- 작업 영역: Frontend / Backend / AI Core / Database / External Provider / Deployment
- 대상 기능: 인증, 상담 채팅, LLM, OCR, Embedding, RAG 검색, 관리자, 대시보드, 평가
- 주요 기술: React 19, TypeScript, Vite, FastAPI, SQLAlchemy, PostgreSQL, pgvector, PaddleOCR, Gemini Embedding, Vast.ai LLM
- 작업 범위: 현재 저장소의 실제 코드 기준 구조·호출·데이터 흐름과 구현 상태 분석
- 제외 범위: 운영 DB 직접 조회, Vast.ai·Gemini·R2 실연동 시험, 코드 수정 및 신규 기능 구현

## 1. 분석 결론

이 프로젝트는 의료 상담 SPA와 FastAPI API 서버, 재사용 가능한 `ai` 코어를 한 저장소에서 관리하는 모노레포다.

전체 실행 구조는 다음 한 줄로 요약할 수 있다.

```text
React 화면
→ Frontend API Adapter
→ FastAPI Router
→ Backend Service
→ Repository 또는 ai Core
→ PostgreSQL/pgvector·Vast.ai·Gemini·Cloudflare R2
→ 같은 경로로 결과 반환
```

현재 핵심 상담 흐름은 Mock이 아니다. 사용자가 선택한 모델 ID가 Backend 공통 Model Registry를 거쳐 Vast.ai 원격 추론 서버로 전달되며, 그 전에 RAG 검색·응급 키워드 검사·진료과 분류가 실행되고, 그 후에 응답 검증·의료 면책 문구·DB 저장·대시보드 로그 기록이 수행된다.

반면 프로젝트 전체가 완전히 연결된 상태는 아니다. 특히 다음 경계는 반드시 구분해야 한다.

1. 관리자 OCR 저장은 Gemini 벡터를 `document_chunks.embedding`에 저장하지만, 상담 RAG는 별도 `chunk_embeddings` 테이블을 검색한다. 두 파이프라인을 이어 주는 `ingest_document()`는 존재하지만 실제 API에서 호출되지 않는다.
2. 채팅 첨부파일은 이름·크기·MIME 메타데이터만 DB에 저장하며 원본 파일은 저장하거나 LLM에 전달하지 않는다.
3. `/document`, `/ocr`, `/evaluation` 일반 화면은 제목만 있는 Placeholder다. 실제 OCR·평가 UI는 채팅 미리보기와 관리자 화면에 있다.
4. `/api/admin/dashboard/*`는 Backend 관리자 권한을 검사하지만 기존 `/api/admin/ocr/*`, `/api/admin/llm/*`, `/api/admin/evaluations/*`는 서버 권한 검사가 없다.
5. 초기 Alembic migration이 비어 있어 빈 PostgreSQL에서 전체 기본 스키마를 만들 수 없다. 생성 모델은 기존 Neon 스키마를 전제로 한다.

따라서 현재 상태는 **핵심 상담·OCR·LLM 기능은 구현되어 있으나, 지식 수집과 RAG 검색의 연결·관리자 API 보안·신규 DB 재현성·파일 저장이 남아 있는 통합 진행 단계**로 보는 것이 정확하다.

┌──────────────────────── Backend ─────────────────────────┐
│ FastAPI main.py → api/router.py → 기능별 Router          │

| AI Core | OCR/RAG/LLM/상담 순수 로직 | FastAPI·DB Session 의존 |

## 4. 애플리케이션 시작과 설정 로딩

### 4.1 개발 실행

```text
run.bat
→ 최상위 .env 확인
→ backend/.venv Python 3.12 확인
→ Backend 필수 import 확인
→ frontend/node_modules 확인
→ PYTHONPATH=프로젝트 루트 설정
→ backend에서 uvicorn app.main:app --reload
→ frontend에서 npm run dev
```

`PYTHONPATH`가 중요한 이유는 Backend가 형제 디렉터리인 `ai`를 import하기 때문이다. `run.bat`은 이를 자동 설정하지만, `backend` 디렉터리에서 Uvicorn이나 테스트를 직접 실행할 때는 `pip install -e ..`로 `ai`를 설치하거나 프로젝트 루트를 Python 경로에 포함해야 한다.

### 4.2 Backend 생성

중심 진입점은 `backend/app/main.py::create_app()`이다.

```text
Python이 app.main을 import
→ Settings가 최상위 .env를 읽음
→ SQLAlchemy engine/sessionmaker 생성
→ 공통 llm_application 생성
→ FastAPI app 생성
→ CORS Middleware 등록
→ api_router를 settings.api_prefix(/api)에 등록
→ /health, /health/db 등록
→ APP_ENV=local이면 선택적으로 local_lab Router 탐색
```

`local_lab`은 Git에서 제외되는 개인 실험용 디렉터리이므로 다른 환경에 없으면 조용히 건너뛴다.

### 4.3 Frontend 생성

중심 진입점은 `frontend/src/main.tsx`와 `frontend/src/app/App.tsx`다.

```text
main.tsx
→ React StrictMode
→ ThemeProvider
→ AuthProvider
→ ModelSelectProvider
→ CursorFxProvider
→ RouterProvider
→ MainLayout/기능 Page 렌더링
```

`AuthProvider`는 저장된 로그인 Token을 `/api/auth/me`로 검증하고, `ModelSelectProvider`는 공개 `/api/llm/models`에서 Model Registry를 읽는다. Backend가 없으면 모델 UI는 로컬 fallback 목록을 유지한다.

## 5. Frontend 구조와 화면 상태

### 5.1 Route 구성

| Route | 화면 | 접근 제어 | 현재 상태 |
|---|---|---|---|
| `/` | 상담 시작 | 공개, 채팅 시 게스트 자동 발급 | 실제 Backend 연결 |
| `/chat/:conversationId` | 대화 | 로그인 또는 게스트 JWT | 실제 DB·RAG·LLM 연결 |
| `/login`, `/signup`, `/verify-email` | 인증 | 공개 | 실제 Backend 연결 |
| `/forgot-password`, `/reset-password` | 비밀번호 재설정 | 공개 | 실제 Backend/SMTP 연결 |
| `/search` | RAG 직접 검색 | 게스트 가능 | 실제 API 연결, 데이터 필요 |
| `/document` | 문서 업로드 | 없음 | 제목만 존재 |
| `/ocr` | OCR 결과 | 없음 | 제목만 존재 |
| `/evaluation` | 평가 | 없음 | 제목만 존재 |
| `/admin` | OCR·LLM·검색평가 탭 | Frontend `RequireAdmin` | 실제 Admin API 연결 |
| `/dashboard` | 운영 지표 | Frontend+Backend 관리자 검사 | 실제 집계 API 연결 |
| `/mypage`, `/my` | 사용자 설정 | `RequireAuth` | 실제 Backend 연결 |

모든 화면은 `MainLayout` 아래에 있어 Sidebar, Theme Toggle, Admin Nav, 문서 미리보기 Panel을 공유한다.

### 5.2 공통 HTTP 경계

`frontend/src/services/apiClient.ts`가 다음을 통합한다.

- `VITE_API_URL` 또는 기본 `http://localhost:8000/api` 사용
- JSON 요청에 `Content-Type: application/json` 설정
- `FormData`는 Browser가 multipart boundary를 생성하도록 Content-Type 생략
- Token이 있으면 Bearer Header 추가
- 오류 Response의 `detail`을 `ApiError`로 변환

### 5.3 로그인 Token과 게스트 Token

로그인 Token과 게스트 Token은 별도로 관리된다.

```text
로그인 사용자: thegpt_access_token → AuthContext.user와 연결
비로그인 채팅: thegpt_guest_token → 채팅 API에서만 사용
```

`withChatToken()`은 로그인 Token을 우선하고, 없으면 저장된 게스트 Token을 재사용한다. 게스트 Token이 401이면 새 게스트 계정을 한 번 발급해 요청을 재시도한다. 로그인 Token이 만료된 경우에는 조용히 게스트로 전환하지 않는다.

## 6. Backend API와 접근 제어

기본 Prefix는 `/api`다.

| 영역 | 주요 Endpoint | Backend 접근 제어 |
|---|---|---|
| 상태 | `GET /health`, `GET /health/db` | 공개 |
| 인증 | `/api/auth/login`, `/signup`, `/verify-email`, `/forgot-password` 등 | 공개 또는 기능별 JWT |
| 사용자 | `/api/auth/me`, 프로필, 비밀번호 변경, 탈퇴 | 로그인 JWT |
| 대화 | `/api/conversations/*` | 로그인 또는 게스트 JWT |
| 문서 OCR | `POST /api/documents/ocr` | 로그인 또는 게스트 JWT |
| RAG 검색 | `POST /api/rag/search` | 로그인 또는 게스트 JWT |
| LLM Catalog | `GET /api/llm/models` | 공개 |
| LLM 단일 생성 | `POST /api/llm/generate` | 로그인 또는 게스트 JWT |

## 7. 메인 상담 채팅 전체 흐름

### 7.1 중심 함수

```text
Frontend: ChatPage.sendUserMessage()
Backend:  MessageService.send_message()
AI Core:  ai.consultation.pipeline.consult()
LLM Core: LlmApplicationService.run()
```

### 7.2 모델 목록 로드

```text
App 시작
→ ModelSelectProvider
→ GET /api/llm/models
→ llm.router.get_models()
→ llm_service.list_available_models()
→ llm_runtime.llm_application.model_registry.list()
← 공개 model_id/label/description
→ Context와 localStorage에 선택값 유지
```

이 Catalog 조회는 Vast.ai `/health`를 호출하지 않으므로 모델이 목록에 보인다는 사실이 실제 가용성을 보장하지 않는다. 가용성은 Admin `/api/admin/llm/models`가 별도로 확인한다.

### 7.3 첫 메시지 전송

```text
ConsultationPage에서 질문 입력
→ createConversation()
→ withChatToken()
   ├─ 로그인 Token 사용
   └─ 없으면 POST /api/auth/guest → 게스트 User/JWT 생성
→ POST /api/conversations
→ Conversations 행 생성
→ /chat/{conversationId} 이동
→ pendingMessage를 ChatPage가 한 번만 처리
→ 선택한 modelId와 첨부 메타데이터를 sendMessage()로 전달
```

React StrictMode가 Effect를 두 번 실행해도 첫 메시지가 중복 전송되지 않도록 `handledPendingFor`, `pendingSendInFlightFor`가 Conversation별 상태를 기억한다.

### 7.4 Backend 상담 실행 순서

```text
POST /api/conversations/{id}/messages
→ JWT 해석 → current_user 조회
→ conversations.router.send_message()
→ MessageService.send_message()
   1. 내용 또는 첨부 존재 검증
   2. 대화 소유권 검증
   3. 게스트 누적 메시지/첨부 한도 검증
   4. user Message 저장
   5. 첨부 메타데이터 저장
   6. 첫 메시지이면 대화 제목 자동 생성
   7. RAG 검색을 Worker Thread에서 실행
   8. consult(llm_application, 현재 질문, model_id, RAG chunks)
   9. 진료과가 있으면 Conversation category 최초 1회 저장
  10. assistant Message 저장
  11. Conversation updated_at 갱신
  12. consultation_logs 저장
← 저장된 assistant Message
→ Frontend assistant Bubble 추가
```

### 7.5 의료 상담 Core

```text
consult()
→ 응급 키워드 검사
   └─ 감지 시 LLM 없이 응급 안내+면책 문구 반환
→ KeywordDepartmentClassifier로 진료과/신뢰도 분류
→ 검색 Chunk를 [참고 의료 정보] 블록으로 제한·정리
→ system_prompt.md + 분류 + 참고 정보 + 현재 질문 조립
→ LlmApplicationService.run(model_id, request)
→ ModelRegistry.resolve(model_id)
→ ProviderRegistry.resolve("remote-http")
→ Vast.ai POST /v1/generate
← answer/token 정보
→ 위험한 복약 수치 표현 검사
→ 의료 면책 문구 추가
← ConsultationResult
```

LLM 호출이 실패하면 `consult()`가 예외를 기록하고 안전한 고정 fallback 답변을 반환한다. 이 때문에 Browser에서는 HTTP 201이어도 실제 모델 응답이 아닐 수 있으며 `consultation_logs.is_fallback`과 Backend 로그를 함께 봐야 한다.

### 7.6 채팅의 현재 제한

- LLM Prompt에는 **현재 질문만** 들어가며 이전 대화 Message는 포함하지 않는다.
- 첨부 원본 Byte와 OCR 결과는 상담 Prompt에 들어가지 않는다.
- 사용자 Message, 첨부, assistant Message가 각각 별도 commit되므로 전체 요청이 하나의 DB Transaction은 아니다.
- RAG 검색 실패는 rollback 후 빈 참고 목록으로 바꾸어 LLM 상담을 계속한다.
- 대시보드 로그 저장 실패도 채팅 응답을 실패시키지 않는다.

## 8. LLM 구조와 실행 흐름

### 8.1 공통 Runtime

`backend/app/services/llm_runtime.py`가 Admin, 일반 LLM API, 상담 채팅이 공유하는 단일 Runtime을 프로세스 시작 시 만든다.

등록된 공개 모델 ID는 다음과 같다.

| 공개 ID | Provider | 실제 원격 모델 이름 |
|---|---|---|
| `gemma` | `remote-http` | `LLM_REMOTE_GEMMA_MODEL` |
| `medgemma` | `remote-http` | `LLM_REMOTE_MEDGEMMA_FINAL_MODEL` |
| `medgemma-dataset` | `remote-http` | `LLM_REMOTE_MEDGEMMA_DATASET_MODEL` |
| `qwen` | `remote-http` | `LLM_REMOTE_QWEN_MODEL` |
| `llama` | `remote-http` | `LLM_REMOTE_LLAMA_MODEL` |

Frontend는 공개 ID만 알고, Vast.ai 주소·API Key·내부 모델 이름은 Backend에만 남는다.

### 8.2 Provider 호출

```text
LlmApplicationService.run()
→ ModelDefinition 확인
→ RemoteHttpLlmProvider.generate()
→ Semaphore로 프로세스 내 동시 호출 수 제한
→ Authorization: Bearer ...
→ POST {LLM_REMOTE_BASE_URL}/v1/generate
→ HTTP/Redirect/Auth/Timeout/빈 응답을 도메인 오류로 변환
← ProviderGenerateResult
← LlmExecutionResult + 실행 시간
```

Admin 모델 목록은 각 모델의 `provider_model`이 Vast.ai `/health`의 `models` 목록에 있는지 병렬 확인한다.

### 8.3 API 역할 구분

| API | 목적 |
|---|---|
| `GET /api/llm/models` | 메인 UI용 가벼운 공개 Catalog |
| `POST /api/llm/generate` | 저장·RAG·안전 처리 없는 원시 Messages 생성 |
| `POST /api/llm/compare` | 관리자용 여러 모델 비교 |
| `GET /api/admin/llm/models` | Provider 실제 가용성 포함 상세 Catalog |
| `POST /api/admin/llm/run` | 관리자 단일 Prompt 실행 |
| `POST /api/admin/llm/compare` | 기존 camelCase 비교 계약 |

`ai/llm/registry.py`에는 로컬 MedGemma/Qwen/Llama 호환 정의와 Provider 구현도 남아 있지만, 현재 Backend Runtime은 Vast.ai `remote-http` 하나만 등록한다. `backend/app/services/llm/`에는 Python Source 없이 캐시 파일만 남아 있어 삭제 가능한 잔여물이다.

## 9. OCR 전체 흐름

### 9.1 공통 OCR 중심 함수

```text
Backend Adapter: OcrWorkflowService.analyze_upload()
AI Core:         ai.ocr.pipeline.analyze_document()
```

```text
UploadFile
→ 설정 한도보다 1 Byte 더 읽어 실제 크기 확인
→ asyncio.to_thread(analyze_document)
→ 파일명/MIME/Binary 구조/압축 안전성 검증
→ 형식별 추출
   ├─ 이미지: 전처리 → PaddleOCR
   ├─ Digital PDF: Native Text
   ├─ Scanned PDF: Page Rendering → PaddleOCR
   ├─ Hybrid PDF: Native Text + 의미 있는 이미지 OCR
   ├─ DOCX: 문단·표·Header/Footer·이미지 직접 추출
   └─ PPTX: Slide·도형·표·Chart·Note·이미지 직접 추출
→ raw_text 보존
→ cleaned_text 최소 정제
→ Line/Confidence/Page/Warning/문서 유형 반환
```

PaddleOCR Engine은 지연 로딩·캐시되며 같은 Pipeline의 예측 호출은 직렬화된다. DOCX/PPTX는 LibreOffice 변환 없이 OOXML을 직접 읽는다.

### 9.2 채팅 첨부 미리보기 OCR

```text
방금 첨부한 이미지의 blob URL 클릭
→ DocumentPreviewPanel
→ blob을 다시 File로 구성
→ POST /api/documents/ocr
→ OcrWorkflowService.analyze_upload()
→ OCR text/lines 반환
→ 수정 가능한 textarea에 표시
```

이 결과는 미리보기용이며 Message, RAG, LLM Prompt에 저장되지 않는다. 새로고침하거나 과거 대화를 열면 원본 URL이 없으므로 OCR할 수 없다. UI상 PDF 원본 미리보기는 가능하지만 텍스트 추출 호출은 현재 이미지만 허용한다.

### 9.3 관리자 비동기 OCR

```text
Admin 파일 선택
→ POST /api/admin/ocr/jobs (multipart)
→ OcrJobManager.create_job()
→ 파일 Byte 복사 + 메모리 Job 생성
← 202 + jobId
→ asyncio.create_task(_run_job)
→ OcrWorkflowService.process_document()
→ 공통 OCR Core
→ 관리자용 문자 단위 Chunk 생성
→ OcrDocumentResponse 저장

Frontend
→ 700ms 간격 GET /api/admin/ocr/jobs/{jobId}
→ queued/processing/completed/failed와 진행률 표시
```

Job은 FastAPI 프로세스 메모리에만 존재한다. 서버 재시작·다중 Instance 간 공유가 되지 않으며 완료/실패 Job은 설정된 TTL 후 제거된다.

### 9.4 관리자 OCR Vector 저장

중심 함수는 `save_ocr_result_with_embeddings()`다.

```text
POST /api/admin/ocr/vector-save {jobId}
→ 완료된 Job과 기존 문자 Chunk 확인
→ GeminiEmbeddingService.embed_chunks()
→ RETRIEVAL_DOCUMENT, 1024차원 배치 Embedding
→ Chunk 수·Vector 차원·유한값 검증
→ DocumentRepository.save_with_chunks()
→ vector_db.admin_documents 1행
→ vector_db.document_chunks N행 + embedding VECTOR(1024)
→ 한 Transaction으로 commit 또는 rollback
```

원본 파일은 저장하지 않는다. `admin_documents.original_file_url`에는 실제 URL과 구분되는 `ocr-job://...` 추적값이 들어간다.

## 10. RAG 구조와 OCR 저장의 연결 상태

이 프로젝트에는 목적이 다른 두 Embedding 경로가 공존한다.

| 경로 | 설정 | 저장 위치 | 현재 호출자 |
|---|---|---|---|
| 관리자 OCR Gemini 저장 | `EMBEDDING_*`, `GEMINI_API_KEY` | `document_chunks.embedding VECTOR(1024)` | Admin OCR 저장 API |
| 상담 RAG 검색 | `RAG_EMBEDDING_*` | `chunk_embeddings.embedding VECTOR(2048)` | 채팅과 `/rag/search` |

### 10.1 상담 RAG 검색

```text
질문
→ rag_search_service.search()
→ 설정된 RAG EmbeddingProvider로 query vector 생성
→ chunk_embeddings.provider_name별 pgvector cosine distance 검색
→ Provider별 순위 목록
→ Reciprocal Rank Fusion
→ 선택 시 reranker
→ 상위 RetrievedChunk
→ 상담 Prompt의 [참고 의료 정보]
```

기본 `RAG_EMBEDDING_PROVIDER`는 의미 검색 모델이 아닌 해싱 Placeholder다. `sentence_transformer`로 바꿀 수 있지만 모델명과 `ai/rag/requirements.txt` 의존성이 필요하다.

### 10.2 현재 끊어진 지점

```text
현재 Admin OCR 저장
→ document_chunks.embedding(Gemini)
╳ rag_search_service는 이 컬럼을 읽지 않음

RAG가 요구하는 데이터
→ document_chunks
→ chunk_embeddings(provider_name, dimension, embedding)
```

`backend/app/services/document_ingestion_service.py::ingest_document()`는 텍스트를 AI RAG용 토큰 Chunk로 다시 나누고 `chunk_embeddings`까지 저장할 수 있다. 그러나 현재 Router나 다른 Service에서 이 함수를 호출하는 경로가 없다.

즉, Admin에서 “VectorDB 저장 성공”이 표시되어도 그 문서가 메인 상담 RAG 검색 결과에 자동으로 나타나지는 않는다. 통합을 완료하려면 다음 중 하나의 정책이 필요하다.

1. OCR 저장 직후 동일 문서에 대해 RAG ingestion을 함께 실행한다.
2. `rag_search_service`가 Gemini `document_chunks.embedding`을 검색하는 별도 Provider 경로를 지원한다.
3. 두 Embedding 파이프라인을 하나로 통합한다.

현재 코드는 어느 정책도 자동 실행하지 않는다.

### 10.3 검색 화면의 점수 의미

`/search` 화면은 결과를 “유사도”로 표시하지만 Service가 반환하는 최종 `score`는 기본적으로 RRF 점수다. 원래 pgvector cosine similarity 자체가 아니므로 UI 명칭을 해석할 때 주의해야 한다. DB 검색 결과에는 Source를 조립하지 않아 화면에는 대체로 `출처 미상`이 표시된다.

## 11. 인증·회원·마이페이지 흐름

### 11.1 회원가입과 이메일 인증

```text
SignupPage
→ POST /api/auth/signup
→ SignupService
→ 이메일 중복 검사
→ Argon2 계열 Password hash 저장
→ 6자리 인증 코드와 만료 시각 저장
→ SMTP 발송
→ 인증 화면에서 POST /api/auth/verify-email
→ users.is_email_verified=true
```

개발 환경에서 SMTP 발송이 되지 않으면 Response에 개발용 인증 코드가 포함될 수 있고, Production에서는 노출하지 않는다.

### 11.2 로그인과 인증 의존성

```text
POST /api/auth/login
→ 비밀번호 hash 검증
→ 이메일 인증 여부 확인
→ JWT(sub=user_id, exp) 발급
→ localStorage 저장

보호 API 요청
→ HTTPBearer
→ jwt.decode()
→ sub로 Users 조회
→ current_user 주입
```

대화 Service는 요청한 Conversation의 `user_id`와 현재 User를 비교하고, 불일치와 미존재를 모두 404로 처리해 다른 사용자의 대화 존재 여부를 숨긴다.

### 11.3 비밀번호와 프로필

- 비밀번호 변경은 현재 비밀번호와 새 비밀번호 확인을 검증한다.
- 비밀번호 재설정 JWT에는 purpose와 현재 비밀번호 hash의 짧은 fingerprint가 포함되어 한 번 사용한 링크를 무효화한다.
- 프로필 이미지는 JPG/PNG/WEBP, 최대 5MB를 검증한 뒤 Cloudflare R2에 저장하고 공개 URL을 User에 기록한다.
- 회원 탈퇴 시 업로드 문서는 유지하되 `uploaded_by`를 `NULL`로 만들고 User를 삭제한다.
- 상담 전체 삭제는 Conversation 삭제와 DB `ON DELETE CASCADE`로 Message/Attachment를 함께 제거한다.

### 12.2 관계

  │                └──────── consultation_logs ────────────┘

  └── N admin_documents 1 ── N document_chunks 1 ── N chunk_embeddings

| 테이블 | 역할 |
|---|---|
| `users` | 회원·게스트·관리자와 Profile |
| `conversations` | 대화 제목·진료과·갱신 시각 |

| `consultation_logs` | 모델, fallback, 응급, RAG hit, Token, 응답 시간 |
| `admin_documents` | OCR 문서 메타와 전체 추출 Text |
| `document_chunks` | 관리자 OCR Chunk와 Gemini 1024 Vector |
| `chunk_embeddings` | RAG Provider별 정규화 Embedding, 최대 2048 폭 |

### 12.3 DB 재현성 주의

`models/generated.py`는 기존 Neon Schema에서 생성된 Model이다. 최초 migration인 `5d7e62474617_create_tables.py`의 `upgrade()`가 비어 있으므로 새 DB에서 `alembic upgrade head`만 실행하면 `users`, `conversations`, `messages`, `admin_documents`, `document_chunks` 같은 기본 테이블이 생성되지 않는다.

후속 migration은 다음 항목만 추가한다.

- `users.is_admin`
- `vector_db.chunk_embeddings`
- `app_db.consultation_logs`

또한 기본 `DATABASE_URL`은 SQLite지만 Model은 PostgreSQL Schema와 pgvector를 사용하므로 실제 전체 기능은 PostgreSQL/Neon을 전제로 한다.

## 15. 배포 흐름

### 15.1 Backend

```text
Git Commit
→ Cloud Build
→ backend/dockerfile로 Image Build
→ Artifact Registry Push
→ Cloud Run the-gpt-dev 배포
→ uvicorn app.main:app --port ${PORT:-8080}
```

Docker Image는 Backend와 필요한 `ai` Source를 복사하고 PaddleOCR의 GUI OpenCV 의존성을 제거한 뒤 headless Wheel을 설치한다. Cloud Run은 `--allow-unauthenticated`로 공개되므로 API별 JWT/관리자 의존성이 실제 보안 경계다.

배포 관련 현재 주의점은 다음과 같다.

- 로컬 가이드는 Python 3.12를 강제하지만 Docker Base는 Python 3.11이다. `pyproject.toml`은 3.11 이상을 허용한다.
- `.dockerignore`가 `scripts`와 `ai/evaluation`을 제외하므로 Admin 검색 평가 Endpoint는 배포 Image에서 평가 데이터 또는 모듈을 찾지 못한다.
- Backend Requirements는 `ai/rag/requirements.txt`를 포함하지 않는다. 기본 해싱 검색은 OCR 의존성의 NumPy로 동작할 수 있지만 토큰 청킹의 `tiktoken`, SentenceTransformer 전환, 전체 AI 테스트에는 RAG 의존성 설치가 필요하다.

### 15.2 Frontend

`frontend/wrangler.jsonc`는 `dist`를 정적 Asset으로 배포하고 존재하지 않는 경로를 SPA `index.html`로 처리하도록 설정되어 있다. `npm run build`는 TypeScript 검사 후 Vite Production Build를 수행한다.

## 17. 우선순위별 구조적 위험과 후속 작업

### P0: 배포 전 필수

1. **기존 Admin API에 `require_admin` 적용**
   - Frontend Guard는 URL 직접 호출을 막지 못한다.
   - Cloud Run 자체는 공개이므로 `/api/admin/ocr/*`, `/llm/*`, `/evaluations/*`에 Backend 인가가 필요하다.
   - Frontend Admin API Adapter도 로그인 Token을 보내도록 함께 수정해야 한다.

2. **신규 DB를 만들 수 있는 Baseline Migration 작성**
   - 현재 `alembic upgrade head`만으로 기본 Schema/Table을 재현할 수 없다.
   - PostgreSQL extension, `app_db`, `vector_db`, 기본 테이블과 FK를 포함해야 한다.

3. **OCR 저장과 상담 RAG ingestion 연결 정책 확정**
   - 현재 Vector 저장 성공과 상담 검색 가능은 다른 의미다.
   - 이 상태를 UI와 운영 문서에서도 구분하거나 자동 연결해야 한다.

### P1: 핵심 기능 완성

1. 채팅 첨부 원본을 Object Storage에 저장하고 Message Attachment에 실제 URL을 기록한다.
2. 첨부 OCR 결과를 사용자가 확인·수정한 뒤 상담 Prompt에 포함하는 경계를 설계한다.
3. 이전 대화 Message를 Token Budget 내에서 LLM Context에 포함한다.
4. RAG 실사용 Embedding Model과 Provider 이름을 확정하고 기존 문서를 재수집한다.
5. Message 저장·Assistant 생성·로그 기록의 Transaction/보상 정책을 명확히 한다.
6. 메모리 OCR Job을 다중 Instance 환경에서 공유 가능한 Queue/Store로 이동한다.

### P2: 정리와 운영성

1. `/document`, `/ocr`, `/evaluation` Placeholder Route를 구현하거나 숨긴다.
2. `backend/app/services/llm/__pycache__` 잔여물을 정리한다.
3. `/api/admin/evaluations/retrieval`이 실제 서비스 RAG 설정과 같은 Pipeline을 평가하도록 통합한다.
4. 검색 UI의 “유사도”를 실제 RRF 점수에 맞는 명칭으로 바꾸고 문서 Source를 반환한다.
5. Docker Python 버전과 로컬 표준을 통일한다.
6. Frontend 자동 테스트 Script와 실제 Playwright Test를 추가한다.

## 21. 최종 요약

이 프로젝트에서 가장 먼저 읽어야 할 중심 흐름은 `MessageService.send_message()`다. 이 함수가 인증된 대화, DB 저장, RAG, 의료 상담 Core, 공통 LLM Runtime, 응답 저장, 운영 로그를 한 요청 안에서 연결한다.

OCR의 중심은 `OcrWorkflowService`와 `ai.ocr.analyze_document()`, LLM의 중심은 `LlmApplicationService.run()`, RAG 검색의 중심은 `rag_search_service.search()`다. 이 네 경계를 이해하면 전체 코드의 대부분을 따라갈 수 있다.

현재 가장 중요한 통합 과제는 다음 세 가지다.

```text
Admin API Backend 인가 적용
→ 신규 DB Baseline Migration 완성
→ OCR Vector 저장과 상담 RAG ingestion 연결
```

이 세 항목이 해결되면 현재 분리되어 있는 관리·데이터 수집·실제 상담 검색 흐름이 하나의 운영 가능한 End-to-End 구조로 정리된다.
