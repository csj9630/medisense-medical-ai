# OCR 전체 구조·흐름 분석

작성일: 2026-08-20

## 1. 전체 목적

현재 OCR 기능은 이미지의 글자를 무조건 OCR하는 단일 기능이 아니다. RAG 등록 전 문서에서 텍스트를 최대한 효율적으로 추출하고, 관리자가 추출 결과와 Chunk를 검토할 수 있게 하는 Hybrid 문서 처리 파이프라인이다.

핵심 원칙은 다음과 같다.

```text
Native Text가 있으면 직접 추출
OCR이 필요한 이미지나 스캔 페이지에만 PaddleOCR 적용
DOCX/PPTX는 PDF로 정규화해 동일한 판단 기준 사용
최종 텍스트 정제와 Chunking은 모든 형식이 공유
```

## 3. Frontend 구조

| 모듈 | 책임 |
| --- | --- |
| `OcrPanel.tsx` | OCR 입력·설정·결과 UI 조합 |
| `OcrDropzone.tsx` | PDF/이미지/DOCX/PPTX 파일 선택 |
| `SelectedFile.tsx` | 선택 파일명, 크기, MIME 표시 |
| `OcrFilePreview.tsx` | PDF/이미지 미리보기, Office 변환 안내 |
| `OcrChunkSettings.tsx` | Chunk Size와 Overlap 설정 |
| `useOcrTest.ts` | 선택 파일, 진행 상태, 결과, 취소 상태 관리 |
| `apiAdminAiService.ts` | Job 생성과 700ms 상태 polling |
| `OcrResultSummary.tsx` | 진행률과 최종 추출/Chunk 결과 표시 |

파일 선택기의 `accept`는 사용자 편의를 위한 필터일 뿐이다. 드래그 앤 드롭이나 조작된 HTTP 요청을 막을 수 없으므로 실제 허용 여부는 Backend 검증 결과가 결정한다.

## 4. API와 Job 흐름

### 4.1 Job 생성

```text
POST /api/admin/ocr/jobs
Content-Type: multipart/form-data

file
chunkSize
overlap
```

응답:

```json
{
  "jobId": "...",
  "status": "queued"
}
```

Job Manager는 업로드 내용을 byte로 복사한 뒤 즉시 Job ID를 반환한다. 실제 문서 처리는 별도 asyncio task에서 수행한다.

### 4.2 진행 상태

대표 stage 순서는 다음과 같다.

```text
queued
→ uploading
→ validating
→ analyzing
→ converting       # DOCX/PPTX에서만 발생
→ preprocessing    # 이미지/OCR 대상에서 발생 가능
→ loading_model    # PaddleOCR가 필요할 때 발생 가능
→ extracting
→ merging
→ cleaning
→ chunking
→ finalizing
→ completed
```

오류가 발생하면 `failed`와 오류 메시지가 저장된다.

## 5. 공통 검증 흐름

```text
파일명 정규화
→ 확장자 확인
→ 실제 byte 크기 확인
→ 빈 파일 확인
→ 형식별 MIME 확인
→ 형식별 실제 바이너리 구조 확인
```

### 이미지

- PNG/JPEG 실제 포맷 확인
- 확장자와 이미지 포맷 일치 확인
- 최대 픽셀 수 확인
- 전체 디코딩으로 손상 여부 확인

### PDF

- `%PDF-` signature 확인
- PyMuPDF open 확인
- 암호화 여부 확인
- 1페이지 이상인지 확인
- 최대 페이지 수 확인
- 모든 페이지 객체 load 확인

### DOCX/PPTX

- 유효한 ZIP/OOXML인지 확인
- 필수 package 파트 확인
- DOCX/PPTX 내부 핵심 파트로 실제 형식 확인
- 암호화 ZIP 엔트리 거부
- 내부 경로 traversal 거부
- 엔트리 수와 전체 압축 해제 크기 제한
- CRC 손상 확인

## 6. 입력 형식별 처리 분기

### 6.1 PNG/JPG

```text
이미지 byte
→ Pillow load
→ EXIF 방향 보정
→ RGB/투명 배경 정리
→ 최대 이미지 크기 조정
→ PaddleOCR
→ ExtractedDocument
```

이미지는 전체가 OCR 대상이며 페이지 수는 1이다.

### 6.2 PDF

```text
PDF
→ 페이지별 Native Text 양과 이미지 영역 분석
→ 페이지 유형에 따라 직접 추출 또는 OCR
→ 페이지 순서대로 병합
→ ExtractedDocument
```

PDF는 세 가지 결과 유형으로 분류한다.

#### 디지털 PDF

```text
Native Text 충분
→ pymupdf4llm Markdown 추출
→ 실패 시 PyMuPDF 기본 Text fallback
→ PaddleOCR 호출 없음
```

#### Hybrid PDF

```text
Native Text 있음 + 유효 이미지 영역 있음
→ Text block과 이미지 block의 위치 수집
→ 이미지 영역만 전처리/PaddleOCR
→ 원래 block 순서에 [이미지 OCR] 삽입
```

#### 스캔 PDF

```text
Native Text 부족
→ 페이지 전체를 설정 DPI로 렌더링
→ 이미지 전처리
→ PaddleOCR
→ 페이지 순서대로 결과 병합
```

### 6.3 DOCX/PPTX

```text
검증된 OOXML byte
→ 작업별 임시 디렉터리 생성
→ LibreOffice 격리 프로필 생성
→ headless PDF 변환
→ 변환 결과 크기 확인
→ PDF signature/암호화/페이지/손상 재검증
→ 기존 PDF 처리 함수 호출
→ 변환 경고를 ExtractedDocument에 병합
```

Office 형식별 별도 텍스트 추출기를 두지 않으므로 변환 이후 동작은 일반 PDF와 같다. PPTX의 한 슬라이드는 보통 변환 PDF의 한 페이지가 되며, DOCX 페이지 수는 변환 환경의 글꼴과 레이아웃에 영향을 받는다.

## 8. 내부 데이터 계약

### ValidatedDocument

검증이 끝난 원본 문서를 형식별 처리기로 전달한다.

```text
file_name

content: bytes
```

### ConvertedOfficeDocument

Office 변환기에서 중심 서비스로 반환한다.

```text
content: PDF bytes
warnings: 변환 및 레이아웃 안내
```

### ExtractedDocument

이미지/PDF/Office 분기가 공통 형태로 중심 서비스에 복귀한다.

```text

```

### OcrDocumentResponse

```text

notes
```

## 9. 텍스트 정제와 Chunking

형식별 추출이 끝나면 모든 문서가 동일한 후처리를 거친다.

```text
ExtractedDocument.text
→ Unicode 정규화
→ 제어문자 제거
→ 줄 끝/공백 정리
→ 과도한 빈 줄 축소
→ clean text
→ Chunk Size/Overlap 분할
```

Chunking은 문장 종료 위치와 공백을 우선 탐색하고, 적당한 경계를 찾지 못하면 최대 크기에서 분할한다. 다음 Chunk는 설정된 Overlap만큼 앞 내용을 포함한다.

## 10. Confidence와 readiness 해석

- 이미지/스캔 영역은 PaddleOCR line confidence 평균을 사용한다.
- OCR하지 않은 Native PDF는 텍스트가 있으면 confidence가 100으로 계산된다.
- Office 문서도 변환 PDF의 Native Text를 사용하면 100으로 보일 수 있다.
- 따라서 Office 결과의 confidence는 Word/PowerPoint 원본 대비 변환 충실도를 의미하지 않는다.

다음 조건이면 `review`가 된다.

```text
정제 텍스트가 비어 있음
또는 confidence < 80
또는 warning에 처리 실패가 포함됨
```

Office 변환 레이아웃 경고는 정상적인 제한 안내이므로 그 자체만으로 `review`가 되지는 않는다.

## 11. 오류 전파 흐름

```text
Validator / Converter / PDF / PaddleOCR
→ HybridOcrError 계열 예외
→ OcrJobManager가 catch
→ Job status = failed
→ Frontend polling이 error 수신
→ useOcrTest가 화면 오류 상태로 변경
```

예상 가능한 문서 오류는 사용자 메시지로 반환하고, 예상하지 못한 예외의 상세 내부 정보는 사용자에게 그대로 노출하지 않는다.

## 12. 현재 구조의 운영상 주의점

### 12.1 Job 상태가 프로세스 메모리에만 존재

현재 `_jobs`, `_tasks`는 FastAPI 프로세스 내부 dictionary다. 서버 재시작 시 사라지며, 여러 Cloud Run 인스턴스가 생기면 Job 생성 요청과 상태 조회 요청이 다른 인스턴스로 전달될 수 있다.

운영 확장 시에는 다음 구조가 필요하다.

```text
Job 상태: DB 또는 Redis
원본/변환 파일: Object Storage
실행 요청: Cloud Tasks, Pub/Sub 또는 별도 worker
```

### 12.2 응답 이후 background task

현재 Job 생성 API는 `asyncio.create_task()` 후 202를 반환한다. request-based CPU 환경에서는 응답 이후 작업 실행이 안정적으로 보장되지 않을 수 있다. Cloud Run 설정을 instance-based CPU로 바꾸거나 외부 작업 큐로 분리해야 한다.

### 12.3 메모리 사용

현재 원본 파일 byte, 변환 PDF, OCR 모델, PDF 렌더링 이미지, Job 결과가 같은 프로세스 메모리를 사용한다. Office 문서는 압축 원본보다 변환 PDF가 커질 수 있으므로 동시 실행 수를 낮추고 실제 샘플로 메모리 사용량을 측정해야 한다.

### 12.4 임시 파일

Office 변환 임시 파일은 `TemporaryDirectory` 종료 시 정리된다. 다만 컨테이너가 강제 종료되는 경우를 고려해 임시 디렉터리를 영구 저장소로 사용해서는 안 된다.

## 13. 확장 방향

### 서버 변환 PDF 미리보기

현재 Office 파일은 변환 안내만 표시한다. 미리보기를 추가하려면 다음 흐름이 필요하다.

```text
변환 PDF Object Storage 저장
→ 만료 시간이 있는 preview URL 생성
→ Job result에 preview URL 추가
→ OcrFilePreview에서 PDF 표시
→ TTL 후 변환 파일 삭제
```

### HWP/HWPX

HWP를 추가할 때 `OfficeDocumentConverter` 계약의 다른 구현체를 추가할 수 있다.

```text
LibreOfficeDocumentConverter: DOCX/PPTX
HancomDocumentConverter: HWP/HWPX
```

중심 서비스는 변환 결과 PDF만 받기 때문에 PDF 이후 파이프라인은 변경하지 않아도 된다. 다만 최신 HWP를 LibreOffice HWP 필터에 그대로 맡기는 방식은 호환성 위험이 있어 공식 Hancom 변환기 도입을 전제로 검토해야 한다.

### 결과 품질 지표 분리

향후 다음 값을 분리하는 것이 적절하다.

```text
ocrConfidence
extractionMethod
sourceFormat
converterName / converterVersion
conversionWarnings
```

현재 하나의 `confidence` 값만으로는 Native Text, OCR 정확도, Office 변환 품질을 구분할 수 없다.
