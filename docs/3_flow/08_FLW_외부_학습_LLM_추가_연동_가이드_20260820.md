# 외부에서 학습한 LLM 추가 및 연동 가이드

> 대상: Google Colab 또는 다른 PC에서 학습·파인튜닝한 LLM을 이 프로젝트의 관리자 LLM 화면에서 호출하려는 개발자  
> 작성일: 2026-08-20  
> 상태: Vast.ai 2× V100의 5개 모델용 `RemoteHttpLlmProvider`와 실행 Notebook 구현 완료.

## 1. 목적

이 문서는 다음 위치에서 실행하는 학습 모델을 현재 프로젝트에 연결하는 방법을 설명한다.

- Google Colab GPU Runtime
- 학원·연구실·개인 PC의 로컬 GPU 서버
- 사내 GPU 서버
- 외부 VM 또는 추론 전용 서버

목표는 모델마다 Frontend와 API Router를 다시 만드는 것이 아니라, 공통 LLM 계약을 지키는 Provider를 통해 모델을 교체·추가하는 것이다.

## 2. 가장 중요한 전제

학습 결과 파일 자체는 HTTP로 호출할 수 없다.

예를 들어 다음 결과물은 먼저 추론 엔진에 로드되어야 한다.

- Hugging Face Transformers 모델 폴더
- PEFT/LoRA Adapter
- `safetensors` 가중치
- GGUF 파일
- 모델과 Tokenizer가 저장된 Checkpoint

전체 흐름은 다음과 같다.

```text
학습 결과물
  -> Colab 또는 GPU PC의 추론 엔진에 로드
  -> HTTP 추론 서버로 노출
  -> 프로젝트 Backend의 Remote Provider가 호출
  -> 기존 LLM Application Service가 결과 표준화
  -> 기존 /api/admin/llm/run 응답
  -> Frontend 모델 카드에 출력
```

즉, 이 프로젝트의 Backend는 원격 모델의 가중치를 직접 로드하지 않는다. 원격 추론 서버에 요청을 보내고 응답을 현재 프로젝트 계약으로 변환한다.

## 3. 권장 아키텍처

```text
[Frontend]
    |
    | POST /api/admin/llm/run
    v
[현재 프로젝트 FastAPI Backend]
    |
    | ModelRegistry: modelId -> providerKey + providerModel
    | ProviderRegistry: providerKey -> Provider 객체
    v
[RemoteHttpLlmProvider]
    |
    | HTTPS + Bearer Token
    v
[Colab 또는 다른 PC의 추론 API]
    |
    v
[학습 모델 / Base Model + LoRA Adapter]
```

Frontend가 Colab이나 원격 PC에 직접 요청하지 않도록 한다. 원격 URL과 인증 토큰은 Backend만 알고 있어야 한다.

이 구조의 장점:

- Frontend에 비밀키가 노출되지 않는다.
- 원격 API 형식 차이를 Provider가 흡수한다.
- 기존 관리자 모델 목록과 실행 화면을 그대로 사용한다.
- Mock 모델 ID를 유지한 채 실제 Provider로 교체할 수 있다.
- 오류, Timeout, 동시성 제한을 Backend 한 곳에서 관리할 수 있다.

## 4. 현재 프로젝트의 확장 지점

현재 LLM 구조는 다음 파일로 나뉘어 있다.

| 파일 | 역할 |
| --- | --- |
| `ai/llm/contracts.py` | 모든 Provider가 따르는 요청·응답·오류 계약 |
| `ai/llm/registry.py` | 공통 Model/Provider Registry |
| `ai/llm/application.py` | Provider 선택, 가용성 확인, 실행 시간 측정 |
| `backend/app/services/admin_llm.py` | Provider 인스턴스 생성과 API 응답 변환 |
| `ai/llm/providers/` | 로컬/원격 LLM Provider 구현 |
| `backend/app/core/config.py` | 최상위 `.env`를 읽는 Backend 설정 |
| `backend/tests/test_admin_llm_api.py` | Registry, Provider, API 계약 자동 검증 |

Provider가 반드시 구현해야 하는 최소 계약은 다음과 같다.

```python
class LlmProvider(Protocol):
    key: str
    is_mock: bool

    async def generate(
        self,
        request: ProviderGenerateRequest,
        model: LlmModelDefinition,
    ) -> ProviderGenerateResult: ...

    async def check_availability(
        self,
        model: LlmModelDefinition,
    ) -> ProviderAvailability: ...
```

## 5. 권장 원격 추론 API 계약

가능하면 추론 엔진이 제공하는 OpenAI 호환 API를 사용하는 것을 우선 고려한다. 같은 Provider로 여러 Serving Engine과 모델을 연결하기 쉽기 때문이다.

OpenAI 호환 규격을 사용하기 어렵다면 다음과 같은 프로젝트 공통 규격을 원격 서버에 구현한다.

### 5.1 상태 확인

```http
GET /health
Authorization: Bearer {REMOTE_LLM_API_KEY}
```

권장 응답:

```json
{
  "status": "ok",
  "models": ["medical-gemma-lora-v1"]
}
```

`/health`에서는 실제 추론을 실행하지 않는다. 모델이 메모리에 로드됐는지와 요청 가능한 모델 ID만 빠르게 확인한다.

### 5.2 생성 요청

```http
POST /v1/generate
Authorization: Bearer {REMOTE_LLM_API_KEY}
Content-Type: application/json
```

```json
{
  "model": "medical-gemma-lora-v1",
  "messages": [
    {"role": "user", "content": "질문 내용"}
  ],
  "max_output_tokens": 512
}
```

권장 성공 응답:

```json
{
  "answer": "모델의 답변",
  "input_tokens": 120,
  "output_tokens": 80,
  "total_tokens": 200,
  "finish_reason": "stop"
}
```

토큰 수를 추론 서버에서 계산할 수 없다면 `null`을 반환할 수 있다. 다만 `answer`는 비어 있지 않은 문자열이어야 한다.

### 5.3 오류 응답 원칙

| HTTP 상태 | 의미 |
| --- | --- |
| 400 | 요청 형식 또는 생성 옵션 오류 |
| 401/403 | 원격 API 토큰 또는 접근 권한 오류 |
| 404 | 요청한 모델이 로드되지 않음 |
| 422 | 프롬프트 거부 또는 입력 검증 실패 |
| 429 | 동시 요청 또는 사용량 제한 초과 |
| 500/502/503 | 추론 엔진·GPU·상위 서비스 오류 |
| 504 | 추론 제한시간 초과 |

오류 응답에는 Stack Trace, 파일 경로, 토큰, 내부 IP 등 민감한 정보를 포함하지 않는다.

## 6. Colab에서 연결하는 흐름

Colab은 개발·시연용 원격 모델 서버로 사용할 수 있지만 장기 운영 서버로 간주하면 안 된다.

```text
Colab Runtime 시작
  -> 모델 및 Tokenizer 로드
  -> 필요하면 Base Model에 LoRA Adapter 결합
  -> FastAPI 또는 추론 Serving Engine 시작
  -> 인증된 HTTPS Tunnel 생성
  -> Tunnel URL을 프로젝트 최상위 .env에 설정
  -> 프로젝트 Backend 완전 재시작
  -> /llm/models와 /llm/run으로 확인
```

Colab 사용 시 주의점:

- Runtime이 중지되면 API도 즉시 종료된다.
- Runtime을 다시 만들면 Tunnel URL이 달라질 수 있다.
- GPU가 회수되거나 유휴 세션이 종료될 수 있다.
- 무료 Runtime의 성능과 지속 시간은 보장되지 않는다.
- Tunnel URL을 알기만 하면 접근할 수 있는 구조로 만들지 말고 Bearer Token을 반드시 적용한다.
- 실제 환자 정보나 민감한 의료 문서를 공개 Tunnel과 개인 Colab으로 전송하지 않는다.

Colab에서 URL이 변경될 때는 `.env`의 원격 URL을 바꾸고 Backend를 완전히 재시작해야 한다.

## 7. 다른 PC의 로컬 모델을 연결하는 흐름

다른 PC에서는 먼저 모델 서버가 프로젝트 Backend PC에서 접근 가능한 주소에 Bind되어야 한다.

```text
모델 PC
  추론 서버: 0.0.0.0:{port}
  방화벽: Backend PC에서 오는 연결만 허용
  인증: Bearer Token

프로젝트 PC
  REMOTE_LLM_BASE_URL=https://고정주소:{port}
```

권장 연결 방법:

1. 같은 신뢰 네트워크의 고정 사설 IP
2. 사설 VPN 또는 Mesh VPN
3. 인증·TLS·접근제어가 적용된 Reverse Proxy

공유기 포트 포워딩으로 인증되지 않은 추론 API를 인터넷에 직접 공개하지 않는다. HTTPS를 사용하고 인증서 검증을 끄지 않는다.

## 8. 프로젝트 환경변수 추가안

범용 Remote Provider 하나를 추가하는 경우의 권장 예시는 다음과 같다.

```dotenv
# Remote trained LLM provider
LLM_REMOTE_ENABLED=false
LLM_REMOTE_BASE_URL=http://vast-host:published-port
LLM_REMOTE_API_KEY=
LLM_REMOTE_GEMMA_MODEL=gemma
LLM_REMOTE_MEDGEMMA_FINAL_MODEL=medgemma-final
LLM_REMOTE_MEDGEMMA_DATASET_MODEL=medgemma-dataset
LLM_REMOTE_QWEN_MODEL=qwen
LLM_REMOTE_LLAMA_MODEL=llama
LLM_REMOTE_TIMEOUT_SECONDS=300
LLM_REMOTE_MAX_CONCURRENCY=5
```

적용 위치:

- 실제 값: 프로젝트 최상위 `.env`
- 공유 가능한 항목명과 안전한 예시: 프로젝트 최상위 `.env.example`
- Pydantic 설정 필드: `backend/app/core/config.py`

보안 규칙:

- `LLM_REMOTE_API_KEY`에 `VITE_` 접두사를 붙이지 않는다.
- 실제 키를 `.env.example`, README, 테스트, 로그에 넣지 않는다.
- Frontend에는 Remote URL도 가급적 노출하지 않는다.
- API 키의 존재 여부만 검사하고 값을 출력하지 않는다.

## 9. Remote Provider 구현 절차

구현은 `ai/llm/providers/remote_http.py`에 있다.

개념적인 형태는 다음과 같다.

```python
class RemoteHttpLlmProvider:
    key = "remote-http"
    is_mock = False

    async def check_availability(self, model):
        # GET {base_url}/health
        # 활성화 여부, URL, 인증, HTTP 상태, 모델 목록 확인
        # 실패하면 ProviderAvailability(False, 안전한 메시지)
        ...

    async def generate(self, request, model):
        # Semaphore 안에서 POST {base_url}/v1/generate
        # model.provider_model을 원격 model 필드로 전달
        # 응답을 ProviderGenerateResult로 변환
        # Timeout/인증/429/5xx를 LlmServiceError 계열로 변환
        ...
```

반드시 포함할 항목:

- `httpx.AsyncClient` 기반 비동기 호출
- 연결·전체 요청 Timeout
- `asyncio.Semaphore` 동시성 제한
- `Authorization: Bearer ...` 헤더
- URL 끝의 `/` 정규화
- 응답 JSON과 필드 타입 검증
- 빈 답변 차단
- HTTP 상태별 도메인 오류 매핑
- Client 종료 또는 Application Lifespan 기반 자원 정리
- 비밀키와 전체 Prompt를 제외한 안전한 로그

Provider가 반환할 결과는 현재 공통 계약으로 변환한다.

```python
ProviderGenerateResult(
    answer=answer.strip(),
    input_tokens=input_tokens,
    output_tokens=output_tokens,
    total_tokens=total_tokens,
    finish_reason=finish_reason,
)
```

## 10. Provider Registry 등록

새 Provider 객체는 `backend/app/services/admin_llm.py`의 `create_llm_application()`에서 생성해 `ProviderRegistry`에 넣는다.

개념적인 등록 형태:

```python
ProviderRegistry(
    (
        RemoteHttpLlmProvider(
            enabled=settings.llm_remote_enabled,
            base_url=settings.llm_remote_base_url,
            api_key=settings.llm_remote_api_key,
            timeout_seconds=settings.llm_remote_timeout_seconds,
            max_concurrency=settings.llm_remote_max_concurrency,
        ),
    )
)
```

`RemoteHttpLlmProvider.key`와 모델 정의의 `provider_key`는 반드시 같아야 한다.

## 11. 새 모델 추가와 기존 Mock 교체

### 11.1 새 모델 카드 추가

`backend/app/services/admin_llm.py`의 `create_admin_model_registry()`에 모델 정의를 추가한다.

```python
LlmModelDefinition(
    id="medical-gemma-v1",
    label="Medical Gemma v1",
    family="Fine-tuned Gemma",
    training_stage="학습 및 파인튜닝 완료",
    description="외부 GPU 서버에서 실행하는 의료 특화 모델입니다.",
    group="main",
    provider_key="remote-http",
    provider_model=settings.llm_remote_model,
)
```

필드 의미:

| 필드 | 의미 |
| --- | --- |
| `id` | Frontend와 API가 사용하는 프로젝트 내부 고유 ID |
| `label` | 화면에 표시할 이름 |
| `family` | 모델 계열 설명 |
| `training_stage` | 학습 단계 설명 |
| `description` | 모델 카드 설명 |
| `group` | 현재는 `main` 또는 `other`만 허용 |
| `provider_key` | Provider Registry에서 찾을 Key |
| `provider_model` | 원격 추론 서버에 전달할 실제 모델 ID |
| `enabled` | 프로젝트에서 모델을 활성화할지 여부 |

### 11.2 기존 Mock 모델을 실제 모델로 교체

화면과 API에서 기존 모델 ID를 유지하려면 해당 정의의 `provider_key`와 `provider_model`만 실제 Provider 기준으로 변경한다.

예를 들어 `medgemma` Mock을 원격 학습 모델로 교체하는 개념은 다음과 같다.

```text
변경 전
  id             = medgemma
  provider_key   = mock
  provider_model = medgemma

변경 후
  id             = medgemma
  provider_key   = remote-http
  provider_model = medical-gemma-lora-v1
```

이 방식은 Frontend의 `modelId=medgemma`를 유지하면서 실행 Provider만 교체한다.

## 12. 모델이 여러 개일 때의 설계

### 같은 서버와 같은 인증을 사용하는 경우

Remote Provider 하나를 여러 모델 정의가 공유하면 된다.

```text
remote-http Provider
  -> provider_model=medical-gemma-v1
  -> provider_model=medical-qwen-v2
  -> provider_model=summary-llama-v1
```

원격 서버가 요청의 `model` 값에 따라 올바른 모델이나 Adapter를 선택해야 한다.

### 서버 URL이나 인증키가 서로 다른 경우

현재 `ProviderRegistry`는 `provider.key`를 고유 키로 사용한다. 서로 다른 Endpoint를 동시에 연결하려면 다음 중 하나를 선택한다.

1. `colab-remote`, `lab-pc-remote`처럼 Provider Key가 다른 인스턴스를 만든다.
2. 설정에 Endpoint Map을 추가하고 하나의 Provider가 모델별 연결 설정을 선택하도록 확장한다.
3. 중앙 Model Gateway를 두고 프로젝트에는 Gateway Provider 하나만 등록한다.

모델이 계속 늘어날 예정이라면 3번이 운영과 키 관리 측면에서 가장 단순하다.

## 13. Frontend 변경 여부

현재 Frontend는 `/api/admin/llm/models` 결과를 순회해 모델 카드를 동적으로 만든다. 새 모델이 기존 응답 계약을 지키면 일반적으로 Frontend 코드 변경은 필요하지 않다.

필수 조건:

- 모델 `id`가 중복되지 않아야 한다.
- `group`은 현재 타입이 허용하는 `main` 또는 `other`여야 한다.
- `available`, `availabilityMessage`, `isMock`이 정확해야 한다.
- `/api/admin/llm/run` 결과가 기존 camelCase 계약을 지켜야 한다.

화면 배치, 그룹 종류 또는 모델별 설정 UI를 새로 만들 때만 Frontend 타입과 Component 변경을 검토한다.

## 14. 문서 입력과 OCR 결과에 관한 현재 제한

현재 LLM 실행 요청은 다음 데이터만 Provider로 전달한다.

- Prompt
- `documentName`
- 내부 계약상 선택적인 System Prompt 및 최대 출력 토큰

`documentName`은 파일 이름일 뿐 문서 본문이 아니다. 현재 화면에서 파일을 선택해도 학습 모델에 OCR 본문이나 원본 파일이 자동으로 전달되는 것은 아니다.

원격 모델이 문서 내용을 사용해야 한다면 별도 구현이 필요하다.

```text
파일 업로드
  -> OCR Job 완료
  -> 추출 Text 또는 Chunk 획득
  -> 필요한 Chunk 선택
  -> Prompt/Context로 LLM 요청에 포함
  -> Remote Provider 호출
```

긴 문서를 통째로 보내지 말고 Token 제한, Chunking, 검색 결과, 개인정보 제거 정책을 먼저 정해야 한다.

## 15. Timeout과 장시간 추론

현재 `/api/admin/llm/run`은 요청이 끝날 때까지 기다리는 동기형 HTTP 흐름이다. 응답에 수 분이 필요한 모델은 다음 문제가 생길 수 있다.

- Browser 또는 Proxy Timeout
- Colab Tunnel Timeout
- Backend Worker 장시간 점유
- 사용자가 취소해도 원격 GPU 추론이 계속 실행

짧은 생성은 기존 Provider 방식으로 처리할 수 있다. 장시간 추론이나 대규모 Batch 작업에는 OCR Job과 유사한 비동기 작업 구조를 권장한다.

```text
POST /llm/jobs
  -> jobId 반환
GET /llm/jobs/{jobId}
  -> queued/running/completed/failed 조회
DELETE /llm/jobs/{jobId}
  -> 가능하면 원격 추론 취소
```

## 16. 보안 필수 점검

- Remote URL과 API 키는 Backend 환경변수에서만 읽는다.
- Frontend 요청으로 임의 URL을 받아 호출하지 않는다. 이는 SSRF 위험이 있다.
- HTTPS 인증서 검증을 비활성화하지 않는다.
- API 키, Authorization Header, 전체 Prompt를 로그에 남기지 않는다.
- 오류 메시지에 원격 응답 원문을 그대로 노출하지 않는다.
- 모델 API에 인증, 요청 크기 제한, 속도 제한을 적용한다.
- GPU 서버 방화벽에서 허용된 Backend 또는 VPN 대역만 접근시킨다.
- 실제 의료·개인정보는 Colab이나 공개 Tunnel로 전송하지 않는다.
- 학습 가중치와 대용량 Checkpoint를 이 Git 저장소에 커밋하지 않는다.

## 17. 테스트 추가 기준

`backend/tests/test_admin_llm.py`에 최소한 다음 테스트를 추가한다.

### Provider 단위 테스트

- `/health` 성공과 대상 모델 확인
- 대상 모델 미로드 상태
- 정상 생성 응답 변환
- 토큰 수가 `null`인 응답
- 빈 Answer와 잘못된 JSON 차단
- 연결 실패와 Timeout
- 401/403 인증 오류
- 404 모델 오류
- 429 동시성·할당량 오류
- 5xx 원격 서버 오류
- API 키가 예외 문자열에 포함되지 않는지
- HTTP Client가 정상·오류·취소 상황에서 정리되는지

### Registry 및 API 테스트

- 새 Provider Key가 등록되는지
- 새 모델 ID 또는 Mock 교체가 정확한지
- 모델 목록 개수와 표시 순서
- `isMock=false`인지
- `providerModel`이 실제 원격 모델 ID인지
- `/api/admin/llm/run`의 camelCase 응답 계약
- 모델 목록과 오류 응답에 비밀키가 없는지

현재 테스트는 5개 모델의 개수와 순서를 명시적으로 검사하므로 모델을 추가하면 기대값도 함께 갱신해야 한다.

## 18. 구현 후 검증 순서

```text
1. 원격 서버에서 모델 로드 확인
2. 원격 서버 내부에서 /health 확인
3. 프로젝트 Backend PC에서 원격 /health 접근 확인
4. 잘못된 토큰이 거부되는지 확인
5. 최상위 .env 설정
6. Backend 완전 재시작
7. GET /api/admin/llm/models 확인
8. 대상 모델 available=true 확인
9. POST /api/admin/llm/run 단일 호출
10. Frontend에서 대상 모델 단독 실행
11. 여러 모델 동시 실행과 동시성 제한 확인
12. Timeout·원격 서버 종료·429 오류 화면 확인
```

Backend 설정은 `lru_cache`되고 LLM Application도 전역 생성되므로 `.env` 변경 후에는 반드시 Backend 프로세스를 완전히 종료하고 다시 시작한다.

## 19. 문제 발생 시 판단 흐름

```text
/llm/models에서 available=false
  -> Remote URL, 인증, /health, 모델 ID 확인

available=true인데 /llm/run 실패
  -> 실제 생성 Endpoint, GPU 메모리, Timeout, 응답 JSON 확인

Backend에서는 성공하지만 Frontend에서 실패
  -> Browser Network의 /admin/llm/run 상태와 VITE_API_URL 확인

Colab 재시작 후 실패
  -> 변경된 Tunnel URL과 모델 재로딩 여부 확인

다른 PC에서만 연결 실패
  -> Bind 주소, 방화벽, VPN, TLS 인증서, DNS 확인

문서 질문에 문서 내용이 반영되지 않음
  -> 현재는 documentName만 전달됨. OCR Text 연결 구현 여부 확인
```

## 20. 권장 구현 순서

첫 번째 외부 학습 모델은 다음처럼 작은 범위로 구현하는 것이 안전하다.

1. 원격 모델 서버의 `/health`, `/v1/generate` 계약 확정
2. 최상위 환경변수 설계
3. 범용 `RemoteHttpLlmProvider` 구현
4. 기존 Mock 모델 하나의 `provider_key`만 Remote로 교체
5. Provider 및 API 테스트 추가
6. Colab 또는 다른 PC에서 단일 모델 통합 테스트
7. 운영 PC 연결과 보안 설정
8. 두 번째 모델부터 같은 Provider와 API 계약 재사용

이 순서를 따르면 Frontend와 Router를 모델마다 수정하지 않고, Registry와 원격 모델 ID 중심으로 확장할 수 있다.
