# 메인 페이지 LLM 연동 가이드

- 작업일: 2026-08-31
- 작업 영역: Frontend / Backend / AI Core / FastAPI
- 대상 기능: 메인 의료 상담 채팅의 Vast.ai LLM 연동
- 주요 기술: React, TypeScript, FastAPI, Pydantic, asyncio, httpx
- 작업 범위: 공통 LLM Runtime 분리, 모델 Registry 동기화, 메인 채팅 호출, 연동·장애 가이드
- 제외 범위: 원격 GPU 배포 자동화, 채팅 첨부파일 바이트/OCR 처리, 대화 전체 이력의 LLM 전달

---

## 1. 목적

기존 LLM 실행 객체는 `admin_llm.py`에 조립되어 어드민 전용 기능처럼
보였다. 메인 채팅 코드가 이 객체를 직접 Import하면 실제로는 동작해도
다음 문제가 있다.

- 메인 기능이 어드민 Facade에 의존한다.
- Frontend 모델 목록과 Backend Registry가 하드코딩으로 중복된다.
- 새 모델을 추가할 때 메인 화면의 ID를 따로 고치지 않으면 선택값이 어긋난다.
- 어드민 비교 API와 메인 상담 API의 목적이 구분되지 않는다.

이번 작업에서는 Backend에 공통 LLM Runtime을 두고 어듼민·일반 LLM
API·메인 채팅이 같은 Model Registry와 Provider를 사용하게 했다. 메인
Frontend는 Backend에서 모델 목록을 받고, 선택한 `model_id`를 대화 메시지
API로 전달한다.

## 2. 작업 전·후 구조

### 작업 전

```text
어드민 API ─┐
일반 LLM API ─┼→ app.services.admin_llm.llm_application
메인 채팅 ──┘   → ai.llm.LlmApplicationService
```

메인 모델 선택 목록은 `frontend/src/components/Chat/modelOptions.ts`에만
고정되어 있었다.

### 작업 후

```text
Admin Facade ─────────────┐
일반 LLM Service ─────────┤
메인 MessageService → consult() ─┼→ app.services.llm_runtime
                               │  → ModelRegistry
                               │  → RemoteHttpLlmProvider
                               └→ Vast.ai /v1/generate
```

```text
Frontend 시작
→ GET /api/llm/models
→ Backend Registry의 공개 모델 ID/라벨로 선택 목록 구성
→ 선택한 model_id를 POST /api/conversations/{id}/messages에 포함
```

## 3. 어드민 API와 메인 API의 역할 구분

| 용도 | Endpoint | 권장 사용처 |
|---|---|---|
| 모델 상태·가용성 확인 | `GET /api/admin/llm/models` | 어드민 LLM 테스트 탭 |
| 단일 Prompt 원시 실행 | `POST /api/admin/llm/run` | 어드민 테스트 |
| 모델 비교 | `POST /api/admin/llm/compare` | 어드민 비교 UI |
| 공개 모델 Catalog | `GET /api/llm/models` | 메인 모델 선택 UI |
| 저장 없는 Messages 기반 생성 | `POST /api/llm/generate` | 내부 API 호출자 |
| 대화 저장·RAG·의료 안전 처리 포함 | `POST /api/conversations/{id}/messages` | **메인 채팅 권장** |

메인 채팅이 `POST /api/llm/generate`를 바로 호출하면 대화 DB 저장,
게스트 한도, RAG 검색, 응급 키워드 필터, 진료과 분류, 면책 문구
후처리를 우회한다. 따라서 메인 UI는 대화 메시지 API를 사용한다.

## 4. 전체 실행 흐름

### 4.1 모델 목록 로드

```text
App 렌더링
→ ModelSelectProvider.useEffect()
→ frontend/src/api/llm.ts::getLlmModels()
→ GET /api/llm/models
→ app.api.llm.router.get_models()
→ app.services.llm_service.list_available_models()
→ llm_runtime.llm_application.model_registry.list()
← model_id, label, description
→ ModelSelectContext의 modelOptions 갱신
```

`GET /api/llm/models`는 비밀 값이 아닌 공개 ID·라벨·설명만 반환한다.
`provider_model`, `LLM_REMOTE_API_KEY`는 Frontend에 반환하지 않는다.

Backend가 기동 전이거나 목록 조회가 실패하면 Frontend는
`FALLBACK_MODEL_OPTIONS`를 유지한다. 이 fallback은 화면을 그리기 위한 목록이며,
실제 LLM 실행 가능 여부를 보장하지는 않는다.

### 4.2 홈에서 첫 메시지 전송

```text
사용자가 홈에서 모델 선택
→ ModelSelectContext에 modelId 저장
→ localStorage(thegpt-selected-model)에 선택 유지
→ ConsultationPage.handleSend()
→ POST /api/conversations로 대화 생성
→ /chat/{conversationId}로 이동
→ ChatPage.sendUserMessage()
→ api/messages.ts::sendMessage(..., modelId)
→ POST /api/conversations/{conversationId}/messages
```

비로그인 사용자는 `withChatToken()`이 게스트 Token을 발급·재사용한다.
로그인 사용자는 기존 Access Token을 사용한다. 둘 다 메시지 API에
`Authorization: Bearer ...`가 포함된다.

### 4.3 Backend 상담과 LLM 실행

중심 Service 함수는 다음과 같다.

```text
MessageService.send_message()
```

```text
HTTP Request
→ conversations.router.send_message()
→ MessageService.send_message()
  1. 소유한 대화인지 확인
  2. 게스트 메시지/첨부 한도 확인
  3. 사용자 메시지와 첨부 메타데이터 저장
  4. RAG 참고 Chunk 검색
  5. consult(llm_application, content, model_id, reference_chunks)
     → 응급 키워드 필터
     → 진료과 분류
     → system prompt + 분류 + RAG + 사용자 질문 조립
     → llm_runtime.llm_application.run(model_id, request)
     → ModelRegistry.resolve()
     → RemoteHttpLlmProvider.generate()
     → POST {LLM_REMOTE_BASE_URL}/v1/generate
     ← ProviderGenerateResult
     → 응답 검증 + 의료 면책 문구
  6. 진료과 category 저장
  7. assistant 메시지 저장
← MessageResponse
→ ChatPage에 assistant 버블 표시
```

응급 키워드가 감지되면 `consult()`가 즉시 안전 안내를 반환하므로 LLM을
호출하지 않는다. 텍스트 없이 첨부파일만 전송한 경우도 안내 문구만
반환하고 LLM을 호출하지 않는다.

## 5. Request / Response 계약

### 5.1 메인 채팅 Request

```http
POST /api/conversations/{conversation_id}/messages
Authorization: Bearer <access-or-guest-token>
Content-Type: application/json
```

```json
{
  "content": "머리가 아프고 열이 나요.",
  "attachments": [],
  "model_id": "medgemma"
}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `content` | 조건부 | 사용자 질문. 첨부가 있으면 빈 문자열도 가능 |
| `attachments` | 아님 | 파일명·크기·MIME 타입 메타데이터 |
| `model_id` | 아님 | `GET /api/llm/models`의 `model_id`. 생략 시 `medgemma` |

### 5.2 메인 채팅 Response

```json
{
  "id": "assistant-message-uuid",
  "role": "assistant",
  "content": "...\n\n※ 본 답변은 참고용 정보이며 ...",
  "created_at": "2026-08-31T00:00:00Z",
  "attachments": []
}
```

응답은 방금 저장된 assistant 메시지 하나다. Frontend는 사용자 메시지를
낙관적으로 먼저 표시하고 이 응답을 뒤에 추가한다.

### 5.3 모델 Catalog Response

```http
GET /api/llm/models
```

```json
[
  {
    "model_id": "medgemma",
    "label": "MedGemma (최종)",
    "description": "Vast.ai V100에서 ..."
  }
]
```

이 Endpoint는 Registry 목록을 빠르게 읽으며 원격 `/health`를 호출하지 않는다.
실제 로드·가용 여부는 어드민의 `GET /api/admin/llm/models`에서 확인한다.

## 6. 환경변수 설정

최상위 `.env`에서 다음 변수를 설정한다. 실제 키는 문서·Frontend·Git에
기록하지 않는다.

```dotenv
LLM_REMOTE_ENABLED=true
LLM_REMOTE_BASE_URL=http://Vast_호스트:공개포트
LLM_REMOTE_API_KEY=Backend와_Vast서버가_공유하는_키
LLM_REMOTE_GEMMA_MODEL=gemma
LLM_REMOTE_MEDGEMMA_FINAL_MODEL=medgemma-final
LLM_REMOTE_MEDGEMMA_DATASET_MODEL=medgemma-dataset
LLM_REMOTE_QWEN_MODEL=qwen
LLM_REMOTE_LLAMA_MODEL=llama
LLM_REMOTE_TIMEOUT_SECONDS=300
LLM_REMOTE_MAX_CONCURRENCY=5
```

Frontend에는 API 기본 주소만 설정한다.

```dotenv
VITE_API_URL=http://localhost:8000/api
```

`LLM_REMOTE_API_KEY`에 `VITE_` 접두사를 붙이면 브라우저 번들에 노출될 수
있으므로 절대 그렇게 설정하지 않는다.

## 8. 새 LLM 모델 추가 방법

1. Vast.ai 서버가 새 내부 모델 ID를 `/health` 목록과 `/v1/generate`에서
   받도록 설정한다.
2. 필요하면 `backend/app/core/config.py`와 `.env.example`에 Provider 모델 매핑
   환경변수를 추가한다.
3. `backend/app/services/llm_runtime.py::create_model_registry()`에 공개 `id`,
   `label`, `provider_model`, `provider_key`를 추가한다.
4. Backend를 재시작한 뒤 `GET /api/llm/models`에 새 모델이 나오는지 확인한다.
5. 메인 Frontend는 Catalog를 동적 조회하므로 정상 서버 연결 시에는
   별도 코드 추가 없이 목록에 표시된다.
6. Backend 없이도 새 모델 이름을 표시해야 한다면
   `FALLBACK_MODEL_OPTIONS`도 함께 갱신한다.
7. `backend/tests/test_admin_llm_api.py`, `backend/tests/test_llm_api.py`에서 모델 ID
   순서와 응답 계약을 갱신한다.

공개 `id`는 Frontend가 저장·전송하는 안정적인 계약이다.
`provider_model`은 Vast.ai 내부 모델 이름이므로 서버 배포에 맞게 환경변수로
변경할 수 있다. 두 값을 혼동하지 않는다.

## 11. 오류 처리와 장애 확인

### 모델 목록 조회 실패

Frontend는 fallback 목록을 그대로 사용한다. Network의 `GET /api/llm/models`,
`VITE_API_URL`, Backend CORS를 확인한다.

### 모델은 보이지만 답변이 fallback으로 나옴

Catalog Endpoint는 Registry만 읽으므로 모델이 보인다고 원격 서버가
사용 가능한 것은 아니다. 다음을 확인한다.

- `LLM_REMOTE_ENABLED=true`
- `LLM_REMOTE_BASE_URL`이 `/health`를 붙이지 않은 기본 주소인지
- `LLM_REMOTE_API_KEY`가 Vast.ai의 키와 같은지
- 원격 `GET /health`의 `models`에 `provider_model`이 로드되었는지
- Vast.ai Container 포트와 공개 포트가 연결되었는지

`consult()`는 원격 서버 중지, 인증, Timeout, 모델 미로드 오류를 로그에
남기고 안전한 상담 fallback 답변을 반환한다. 따라서 Browser에서는 HTTP
201이어도 내용이 fallback일 수 있으므로 Backend 로그를 함께 확인한다.

### RAG 검색 실패

RAG 오류는 DB Session을 rollback한 뒤 빈 참고 목록으로 계속한다. LLM과
프롬프트는 계속 실행되므로 응답은 받을 수 있다.

## 15. 현재 제한과 후속 작업

- 메인 상담은 현재 모델에 **현재 질문**만 전달한다. DB의 이전 대화
  Messages를 Prompt에 포함하는 멀티턴 컨텍스트는 후속 작업이다.
- 첨부파일은 메타데이터만 저장된다. 파일 원문을 OCR하여 상담 문맥에
  합치는 기능은 아직 없다.
- 메인 Catalog는 가용성을 즉시 표시하지 않는다. 필요하면 어드민 상태
  조회와 분리된 캐시를 도입해야 한다.
- LLM 실패는 상담 fallback 문구로 변환되므로 Frontend HTTP Status만으로는
  원격 장애를 구분할 수 없다. 운영 모니터링은 Backend 로그·지표를 사용한다.

## 16. 작업 시 주의사항

- 메인에서 어드민 `/api/admin/llm/*` Endpoint를 직접 호출하지 않는다.
- Frontend에 `provider_model`, Vast.ai 주소, API Key를 하드코딩하지 않는다.
- Frontend `model_id`와 Backend Registry의 공개 `id`를 일치시킨다.
- 실제 원격 모델 이름은 `provider_model`에만 두고 환경변수로 관리한다.
- 모델 ID를 변경하면 localStorage에 이전 ID가 남을 수 있다. Context는
  Catalog에 없는 값을 기본 모델로 자동 교체한다.
- 원격 API 호출은 네트워크 I/O이므로 `async/await`를 유지하고 Event Loop에서
  동기 HTTP Client를 사용하지 않는다.
