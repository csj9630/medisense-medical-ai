# OCR 전체 구조 흐름

작성일: 2026-08-20  
구분: 시스템 구조 및 기능 흐름  
대상: 관리자 OCR Backend·Frontend 전체

## 1. 문서 목적

이 문서는 LibreOffice 제거와 DOCX/PPTX 직접 추출 전환 이후의 관리자 OCR 전체 구조를 설명한다.

관련 문서:

- [Office 직접 추출 전환 결과](../2_reports/06_RPT_OCR_Office직접추출전환_20260820.md)
- [Office 문서 오류 및 시스템 장애 분석](../4_errors/01_DOCX_PPTX_OCR_문서_오류_처리_및_장애_대응_2026-08-20.md)

## 2. 지원 형식과 처리 방식

| 입력 형식 | 기본 처리 |
| --- | --- |
| PNG, JPG, JPEG | 이미지 전처리 → PaddleOCR |
| PDF | Native Text·포함 이미지·스캔 페이지를 구분하는 Hybrid PDF 처리 |
| DOCX | python-docx + 필요한 OOXML 직접 추출 → 포함 이미지 OCR |
| PPTX | python-pptx 직접 추출 → 포함 이미지 OCR |
| JSON, JSONL | Encoding·JSON 문법 검증 → RAG용 Text 직접 추출 |
| CSV, TXT | Encoding·CSV 구조 검증 → RAG용 Text 직접 추출 |
| ZIP | 경로·암호화·크기·CRC 검증 → 내부 지원 문서 통합 추출 |

지원하지 않는 형식:

- DOC, PPT
- DOCM, PPTM
- HWP, HWPX
- 암호화된 Office 문서

```text

  ├─ 업로드 파일 메모리 보관
  ├─ 처리 Task 생성
  ├─ 진행 상태 저장
  ├─ 성공·실패 결과 저장
  └─ TTL·동시 Job 수 제한

DocumentProcessingService
  ├─ validate_document
  ├─ 형식별 추출 분기
  ├─ clean_document_text
  ├─ create_chunks
  └─ OcrDocumentResponse 조립
```

## 5. 공통 입력 검증

`document_validator.py`가 모든 입력의 첫 경계를 담당한다.

### 5.1 공통 검증

- 허용 확장자
- 실제 업로드 크기
- MIME Type
- 빈 파일 여부
- Chunk Size와 Overlap 관계

### 5.2 PDF 검증

- `%PDF-` signature
- 암호화 여부
- 1페이지 이상
- 최대 페이지 수
- 모든 페이지 객체 로딩 가능 여부

### 5.3 이미지 검증

- PNG/JPEG 실제 형식
- 확장자와 이미지 형식 일치
- 최대 픽셀 수
- Pillow 디코딩 가능 여부

### 5.4 DOCX/PPTX 검증

- ZIP 열기 가능 여부
- 확장자별 필수 OOXML 엔트리
- 내부 경로 순회 차단
- 암호화 ZIP 엔트리 차단
- 최대 엔트리 수
- 최대 압축 해제 크기
- ZIP CRC
- DOCX와 PPTX 내부 형식 불일치 차단

LibreOffice를 제거했어도 OOXML ZIP 보안 검증은 그대로 유지한다.

## 6. 중심 처리 서비스

`DocumentProcessingService.process_document()` 순서:

```text
1. validating  8%  Chunk 설정과 파일 검증 시작
2. validating 15%  파일 검증 완료
3. analyzing  20%  형식별 분석 준비
4. 형식별 추출 20~80%
5. merging    82%  추출 결과 통합
6. cleaning   86%  텍스트 정제 시작
7. cleaning   90%  텍스트 정제 완료
8. chunking   93%  Chunk 생성 시작
9. chunking   97%  Chunk 생성 완료
10. finalizing 99% 응답 조립
11. completed 100% Job 완료
```

형식 분기:

```text
file_type == image → _process_image_document
file_type == pdf   → process_pdf_document
file_type == docx  → _process_office_document → DirectOfficeDocumentParser
file_type == pptx  → _process_office_document → DirectOfficeDocumentParser
```

## 7. 이미지 처리 흐름

```text
PNG/JPG bytes
→ Pillow 로드
→ EXIF 방향 반영
→ 투명 배경을 흰색으로 합성
→ 최대 픽셀 수 확인
→ 최대 변 길이로 축소
→ PaddleOCR 모델 준비
→ OCR 실행
→ bbox 위→아래, 왼쪽→오른쪽 정렬
→ 텍스트·평균 신뢰도 반환
```

PaddleOCR 서비스는 한 프로세스에서 모델을 재사용하고 추론 실행을 Lock으로 직렬화한다.

## 8. PDF Hybrid 처리 흐름

### 8.1 페이지 분석

각 PDF 페이지에서 다음 값을 수집한다.

- Native Text
- 공백 제외 Native 문자 수
- 유효 이미지 영역 수
- 전체 페이지 OCR 필요 여부

### 8.2 페이지 분기

```text
Native 문자 < 기준
  → 스캔 페이지
  → 페이지 전체를 200 DPI 렌더링
  → PaddleOCR

Native 문자 충분 + 유효 이미지 있음
  → Hybrid 페이지
  → Native Text 추출
  → 유효 이미지만 OCR
  → bbox 위치에 맞춰 OCR 텍스트 삽입

Native 문자 충분 + 유효 이미지 없음
  → 디지털 PDF
  → pymupdf4llm Markdown 우선
  → 실패 시 PyMuPDF 기본 텍스트
```

### 8.3 PDF 결과 유형

- `digital_pdf`
- `hybrid_pdf`
- `scanned_pdf`

## 9. DOCX 직접 추출 흐름

```text
검증된 DOCX bytes
→ python-docx Document 로드
→ 본문 block 순회
   ├─ Heading → Markdown heading
   ├─ 일반 문단 → 본문
   ├─ List Bullet → bullet
   ├─ List Number → numbered item
   └─ Table → Markdown table
→ OOXML 보완 추출
   ├─ 텍스트 상자
   ├─ 변경 추적 삽입 내용
   ├─ 각주
   └─ 미주
→ document relationship에서 이미지 수집
→ 동일 이미지 제거
→ 이미지 OCR
→ DOCX 문서 단위 텍스트 조립
```

제외 또는 제한:

- 변경 추적 삭제 내용
- altChunk
- OLE
- SmartArt와 복잡한 부유 도형의 화면 순서

### 9.1 DOCX 페이지 수

DOCX에는 PDF처럼 확정된 페이지 객체가 없다. 페이지 수는 Word의 글꼴·용지·레이아웃 렌더링 결과다.

따라서:

```text
DOCX pageCount = null
```

문서 속성의 캐시된 페이지 수는 사용하지 않는다.

## 10. PPTX 직접 추출 흐름

```text
검증된 PPTX bytes
→ python-pptx Presentation 로드
→ 슬라이드 순서대로 순회
→ 각 슬라이드 shape를 top/left 좌표로 정렬
→ shape 유형별 처리
   ├─ TextFrame → 문단 텍스트
   ├─ GroupShape → 자식 shape 재귀
   ├─ Table → Markdown table
   ├─ Picture → 이미지 수집
   ├─ Chart → 제목·계열명
   └─ NotesSlide → 발표자 노트
→ 동일 이미지 제거
→ 이미지 OCR
→ 슬라이드별 Markdown 조립
```

PPTX 결과 예시:

```markdown
## 슬라이드 1

발표 제목

본문 내용

### 발표자 노트

발표자가 작성한 추가 설명

### 이미지 OCR 1

이미지에서 인식한 텍스트
```

### 10.1 PPTX 순서 한계

PowerPoint의 shape 저장 순서와 사람이 읽는 순서는 같지 않을 수 있다. 현재는 좌표 기반 휴리스틱을 사용한다.

- 위쪽 shape 우선
- 같은 높이면 왼쪽 shape 우선
- 그룹은 그룹 내부에서 같은 규칙 적용

흐름도, 연결선, SmartArt의 의미 관계는 완전하게 복원하지 않는다.

## 11. Office 이미지 OCR 흐름

DOCX와 PPTX의 직접 추출 이미지에는 공통 경로를 적용한다.

```text
OfficeImage
→ 중복 바이트 제거
→ preprocess_image
→ 4,096 pixel 미만 이미지 제외
→ PaddleOCR
→ OCR 결과가 있으면 해당 문서/슬라이드 뒤에 삽입
→ 처리 불가 이미지는 warning 후 계속
```

Office 이미지 OCR 실패는 문서 전체 실패로 확대하지 않는다.

## 12. 텍스트 정제와 Chunking

형식별 추출 결과는 모두 공통 처리로 복귀한다.

### 12.1 정제

`clean_document_text()`가 다음을 정리한다.

- 제어문자
- 불필요한 공백
- 과도한 빈 줄
- 형식별 추출 과정에서 생긴 공백 차이

### 12.2 Chunking

`create_chunks()`는 관리자 설정을 사용한다.

- `chunkSize`: Chunk 최대 문자 수
- `overlap`: 인접 Chunk 중복 문자 수
- `overlap < chunkSize` 필수

긴 문서는 문장 경계를 우선 사용하고 경계를 찾지 못하면 안전한 길이에서 분리한다.

## 16. 배포 구조

Docker에는 LibreOffice와 Office 렌더링 글꼴을 설치하지 않는다.

```text
python:3.11-slim
→ requirements.txt 복사
→ pip upgrade
→ Python requirements 설치
→ Backend 소스 복사
→ uvicorn 실행
```

DOCX/PPTX 협업 환경은 Python package 버전으로 통일한다.

## 17. 주요 설정

| 설정 | 역할 |
| --- | --- |
| `OCR_MAX_FILE_SIZE_MB` | 업로드 최대 크기 |
| `OCR_MAX_PDF_PAGES` | PDF 최대 페이지 수 |
| `OCR_NATIVE_TEXT_MIN_CHARS` | PDF 페이지 OCR 판단 기준 |
| `OCR_SIGNIFICANT_IMAGE_AREA_RATIO` | PDF 유효 이미지 판단 |
| `OCR_PDF_RENDER_DPI` | 스캔 PDF 렌더링 DPI |
| `OCR_MAX_IMAGE_SIDE` | OCR 이미지 최대 변 길이 |
| `OCR_MAX_IMAGE_PIXELS` | OCR 이미지 최대 픽셀 |

| `OCR_PADDLE_LANGUAGE` | PaddleOCR 언어 |
| `OCR_MAX_OFFICE_UNCOMPRESSED_SIZE_MB` | OOXML 압축 해제 최대 크기 |

LibreOffice 실행 경로, 변환 PDF 크기, Office 변환 timeout 설정은 제거됐다.

## 18. 확장 지점

### 18.1 Office 추출기 교체

`OfficeDocumentParser` Protocol을 구현하면 중심 서비스 변경 없이 다른 직접 파서를 주입할 수 있다.

### 18.2 HWP/HWPX

현재 지원하지 않는다. HWP를 추가할 때 LibreOffice를 다시 공통 필수 의존성으로 넣지 않는다.

권장 방향:

- HWP/HWPX 전용 파서
- 별도 변환 Worker 또는 외부 변환 서비스
- 지원하지 않는 경우 PDF 업로드 안내

### 18.3 정확한 미리보기

정확한 Office 화면 미리보기 요구가 생기면 텍스트 추출 Backend와 분리된 선택형 렌더링 서비스를 검토한다. RAG 기본 추출 경로는 직접 파싱을 유지한다.

## 19. 최종 구조 요약

```text
업로드
→ 안전성 검증
→ Job 비동기 처리
→ 형식별 추출
   ├─ Image → PaddleOCR
   ├─ PDF → Native/Hybrid/Scanned
   ├─ DOCX → python-docx/OOXML + 이미지 OCR
   └─ PPTX → python-pptx + 이미지 OCR
→ 텍스트 정제
→ Chunking
→ 품질 메모와 결과 조립
→ Frontend 결과 표시
```

Office 처리에서 LibreOffice, 임시 PDF, 외부 subprocess가 제거됐으며 PDF 입력의 기존 Hybrid OCR 경로는 변경하지 않았다.
