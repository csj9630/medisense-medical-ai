# 작업 완료 문서화 공통 지시서

> 이 문서는 특정 기능 구현을 위한 요구사항이 아니라, **Codex 또는 AI Agent가 프로젝트에서 코드 작성·수정 작업을 완료한 뒤 반드시 수행해야 하는 공통 문서화 규칙**이다.
>
> 다른 기능 구현 프롬프트와 이 문서가 함께 제공되었다면, 기능 구현과 검증이 끝난 후 아래 규칙에 따라 작업 설명 문서를 작성한다.

---

# 1. 목적

작업 완료 후 프로젝트를 처음 보는 사람이나 초심자가 다음 내용을 쉽게 이해할 수 있도록 작업 설명서를 작성한다.

- 이번에 무엇을 구현했는가
- 왜 이 작업이 필요한가
- 어떤 파일을 추가하거나 수정했는가
- 각 파일은 어떤 역할을 하는가
- 요청이 어디에서 시작되는가
- 전체 실행 순서는 어떻게 되는가
- 다른 파일을 호출한 뒤 결과가 어디로 돌아오는가
- Frontend와 Backend가 어떻게 연결되는가
- 실제 데이터와 Mock 데이터 중 무엇을 사용하는가
- 아직 구현되지 않은 부분은 무엇인가
- 어떻게 실행하고 확인할 수 있는가

단순한 변경 파일 목록이 아니라 **실제 코드를 이해하기 위한 인수인계 및 학습용 문서**로 작성한다.

---

# 2. 문서 저장 위치

작업 완료 문서는 프로젝트의 다음 위치에 저장한다.

```text
docs/
```

`docs` 폴더가 없다면 프로젝트 구조를 확인한 후 생성할 수 있다.

단, 기존 프로젝트에 별도의 문서 관리 위치가 명확하게 존재한다면 기존 구조를 우선한다.

---

# 3. 파일명 규칙

기본 형식:

```text
NN_작업명_YYYY-MM-DD.md
```

예:

```text
02_Admin_FastAPI_Mock_Backend_구현_2026-08-19.md
```

또는:

```text
02_Hybrid_OCR_구현_2026-08-19.md
```

현재 작업에서 문서 번호가 `02`로 지정되어 있다면:

```text
02_작업명_YYYY-MM-DD.md
```

형식을 사용한다.

향후 다른 작업에서 별도의 번호가 지정되어 있다면 해당 번호를 사용한다.

번호가 명시되지 않은 경우에는 `docs/`의 기존 작업 문서를 확인하고 기존 번호 체계를 유지한다.

날짜는 **실제 작업을 수행한 날짜**를 사용한다.

---

# 4. 문서 작성 시 실제 코드를 기준으로 한다

작업 설명서는 처음 작성한 계획이나 프롬프트가 아니라 **최종적으로 구현된 실제 코드 상태**를 기준으로 작성한다.

예를 들어 처음 계획이:

```text
Router → Service → OCR → DB
```

였더라도 실제 구현이:

```text
Router → Service → OCR → Chunking → Response
```

까지만 되어 있다면 실제 구현 내용만 기록한다.

구현되지 않은 기능을 구현된 것처럼 작성하지 않는다.

다음 상태를 명확하게 구분한다.

```text
구현 완료
Mock 구현
연결 준비만 완료
파일/인터페이스만 존재
미구현
후속 작업 예정
```

---

# 5. 문서 첫 부분에 작업 개요 작성

문서 가장 위에는 다음 정보를 작성한다.

예:

```markdown
# 관리자 FastAPI Mock Backend 구현

- 작업일: 2026-08-19
- 작업 영역: Backend / FastAPI
- 대상 기능: 관리자 OCR / LLM
- 주요 기술: Python, FastAPI, Pydantic
- 작업 범위: API, Schema, Service, Mock 응답
- 제외 범위: 실제 PaddleOCR, Ollama, Embedding, VectorDB
```

이를 통해 문서를 열자마자 작업 범위를 확인할 수 있어야 한다.

---

# 6. 작업 목적 설명

기술적인 구현 내용보다 먼저 **왜 이번 작업을 했는지** 설명한다.

예:

```text
기존 관리자 Frontend에서는 OCR과 LLM 기능이 Mock Service를 사용하고 있었다.

이번 작업에서는 Frontend와 실제 HTTP 통신을 테스트할 수 있도록
FastAPI 관리자 Endpoint와 Backend용 Mock Service를 구현했다.

실제 OCR 및 LLM 모델은 아직 연결하지 않고,
향후 실제 구현체로 교체하기 쉬운 구조를 만드는 것이 목적이다.
```

초심자가 프로젝트 상황을 모르더라도 이해할 수 있도록 작성한다.

# 7. 작업 전 상태와 작업 후 상태 비교

가능하다면 이번 작업 전후의 차이를 간단하게 정리한다.

예:

```text
작업 전

React
→ Frontend Mock Service
→ Mock 결과
```

```text
작업 후

React
→ FastAPI
→ Backend Mock Service
→ Mock 결과
```

향후:

```text
React
→ FastAPI
→ 실제 OCR / LLM Service
```

처럼 후속 구조도 구분한다.

---

# 8. 전체 실행 흐름을 먼저 보여준다

세부 파일 설명 전에 전체 기능 실행 흐름을 한눈에 볼 수 있도록 작성한다.

가능하면 가로 흐름을 사용한다.

예:

```text
사용자 버튼 클릭 → React → POST /api/admin/ocr → FastAPI Router
→ OcrService.process_document() → Mock OCR 실행
→ 결과 반환 → Router → React 화면 표시
```

복잡한 기능이라면 단계별 흐름을 추가한다.

예:

```text
파일 업로드 → Router → 중심 Service 함수
→ 파일 검증 → PDF 분석 → PaddleOCR → Chunking
→ 결과 조립 → Router → Frontend
```

---

# 9. 중심 함수를 반드시 표시한다

기능 전체 실행 순서를 관리하는 **중심 함수**가 무엇인지 문서에 명확하게 표시한다.

예:

```text
중심 함수

DocumentProcessingService.process_document()
```

설명 예:

> 이 함수가 문서 처리 전체 실행 순서를 관리한다.  
> 파일 검증, PDF 파싱, OCR, Chunking 등의 실제 작업은 다른 모듈에 위임하지만 각 작업 결과를 다시 반환받은 뒤 다음 단계를 호출한다.

실행 구조:

```text
process_document()

→ validate_document()
← 검증 결과

→ extract_text()
← 추출 결과

→ create_chunks()
← Chunk 결과

→ build_response()
← 최종 Response
```

초심자가 전체 흐름을 따라가려면 **어느 함수를 먼저 읽으면 되는지** 반드시 알려준다.

# 10. 파일별 역할 설명

추가하거나 수정한 주요 파일을 표로 정리한다.

예:

| 파일 | 역할 |
|---|---|
| `admin/router.py` | 관리자 HTTP 요청을 받는다 |
| `admin_schema.py` | Request / Response 데이터 구조를 정의한다 |
| `admin_service.py` | 전체 기능 실행 순서를 관리한다 |
| `mock_ocr_service.py` | OCR 테스트용 Mock 결과를 반환한다 |
| `mock_llm_service.py` | LLM 비교 테스트용 Mock 결과를 반환한다 |

단순히 파일명을 나열하지 말고 **왜 존재하는 파일인지** 설명한다.

---

# 11. 파일 간 호출 관계 설명

기능 하나의 실제 호출 순서를 표로 작성한다.

예:

| 순서 | 파일 | 함수 | 역할 |
|---:|---|---|---|
| 1 | `router.py` | `analyze_document()` | HTTP 요청 수신 |
| 2 | `document_service.py` | `process_document()` | 전체 실행 순서 관리 |
| 3 | `validator.py` | `validate_file()` | 파일 검증 |
| 4 | `ocr_service.py` | `extract_text()` | OCR 실행 |
| 5 | `chunk_service.py` | `create_chunks()` | Chunk 생성 |
| 6 | `document_service.py` | `process_document()` | 결과 취합 |
| 7 | `router.py` | `analyze_document()` | HTTP Response 반환 |

특히 다른 파일로 이동한 뒤 **중심 함수로 결과가 다시 돌아오는 과정**을 표시한다.

# 12. 주요 코드 설명

모든 코드를 그대로 복사하지 않는다.

이해에 중요한 코드만 발췌하여 설명한다.

특히 다음 코드를 우선 설명한다.

- Router Endpoint
- 중심 Service 함수
- Request / Response Schema
- Repository 호출
- 외부 API 호출
- Mock Service
- 주요 예외 처리
- Dependency Injection
- 비동기 처리

예:

```python
@router.post("/ocr")
async def run_ocr(request: OcrRequest):
    return await admin_service.run_ocr(request)
```

설명:

```text
Frontend에서 `/ocr`로 POST 요청이 들어오면 가장 먼저 실행되는 함수다.

Router에서는 OCR 로직을 직접 처리하지 않고
admin_service의 중심 함수를 호출한 뒤 반환된 결과를 HTTP Response로 돌려준다.
```

코드를 처음 보는 사람이 이해할 수 있는 수준으로 설명한다.

# 13. Request / Response 설명

API를 구현했다면 Frontend와 Backend 사이에서 실제로 어떤 데이터가 이동하는지 설명한다.

예:

```text
Frontend Request

{
  "question": "당뇨병 초기 증상을 설명해주세요.",
  "models": ["qwen", "gemma"]
}
```

Backend Response:

```text
{
  "results": [
    {
      "model": "qwen",
      "answer": "...",
      "elapsed_time": 1.5
    }
  ]
}
```

그리고 각 주요 필드가 무엇을 의미하는지 설명한다.

# 17. 테스트 방법 작성

작업 후 어떤 방법으로 기능을 확인했는지 기록한다.

예:

```text
1. FastAPI 서버 실행
2. Swagger 접속
3. POST /api/admin/ocr 실행
4. Mock OCR 결과 확인
5. Frontend에서 OCR 버튼 클릭
6. Network 요청 200 확인
7. 결과 화면 표시 확인
```

자동 테스트가 있다면 실행 명령과 결과도 작성한다.

예:

```text
pytest: 통과
Frontend build: 통과
TypeScript check: 통과
```

실행하지 않은 검증은 통과했다고 작성하지 않는다.

# 18. 오류가 있었다면 기록한다

작업 중 실제로 발생했고 이해에 도움이 되는 오류는 간단하게 기록할 수 있다.

예:

```text
문제:
Frontend는 `/api/admin/ocr`을 호출했지만
Backend Router가 `/api/v1/admin/ocr`에 등록되어 404가 발생했다.

원인:
Frontend와 Backend의 API Prefix 불일치.

해결:
현재 프로젝트의 API_PREFIX 기준으로 Endpoint를 통일했다.
```

단순 오타처럼 중요하지 않은 모든 시행착오를 기록할 필요는 없다.

# 23. 작업 시 주의사항

향후 해당 코드를 수정할 사람이 알아야 할 사항을 작성한다.

예:

- Frontend와 Backend의 DTO를 동시에 확인해야 한다.
- Mock 응답 필드명은 Frontend 타입과 연결되어 있다.
- 실제 OCR 구현 시 파일 요청은 JSON이 아니라 `multipart/form-data`를 사용한다.
- `.env`의 실제 값은 문서에 기록하지 않는다.
- 관리자 API는 현재 권한 Guard가 없을 수 있다.

실제 코드에서 확인한 내용만 기록한다.

# 24. 민감한 정보는 기록하지 않는다

작업 문서에는 다음 값을 절대 기록하지 않는다.

```text
API Key
DB Password
JWT Secret
Access Token
Refresh Token
SMTP Password
R2 Secret Key
사용자의 실제 개인정보
.env 실제 값
```

환경변수가 중요하면 변수 이름만 기록한다.

예:

```text
DATABASE_URL
JWT_SECRET_KEY
OLLAMA_BASE_URL
```

---

# 25. 과도한 문서 생성을 피한다

문서는 상세하게 작성하되 코드 전체를 복사해 붙여 넣는 형태로 만들지 않는다.

목표는:

> 코드 없이도 모든 것을 설명하는 문서

가 아니라,

> 코드를 처음 읽을 사람이 어디서부터 어떻게 따라가야 하는지 알려주는 문서

이다.

---

# 26. 권장 문서 구성

작업 내용에 따라 일부 항목은 조정할 수 있지만 기본적으로 다음 형식을 따른다.

```markdown
# 작업명

- 작업일:
- 작업 영역:
- 대상 기능:
- 주요 기술:
- 작업 범위:
- 제외 범위:

## 1. 작업 목적

## 2. 작업 전 상태

## 3. 구현 내용

## 4. 전체 실행 흐름

## 5. 디렉터리 및 파일 구조

## 6. 파일별 역할

## 7. 주요 코드 설명

## 8. Request / Response 구조

## 9. 기능별 상세 실행 흐름

## 10. Mock / 실제 구현 구분

## 11. 코드 읽는 순서

## 12. 실행 방법

## 13. 테스트 및 검증 결과

## 14. 현재 구현 상태

## 15. 미구현 및 후속 작업

## 16. 작업 시 주의사항
```

작업 성격상 필요하지 않은 항목은 억지로 작성하지 않는다.

---

# 27. 작업 완료 시 문서도 함께 업데이트한다

코드 구현과 테스트가 모두 완료된 뒤 마지막 단계에서 문서를 작성한다.

권장 순서:

```text
기능 구현
→ 코드 검토
→ 실행 또는 테스트
→ 실제 최종 구조 확인
→ docs 작업 문서 작성
→ 작업 완료 보고
```

문서를 먼저 작성한 뒤 코드가 변경되어 내용과 실제 구현이 달라지는 상황을 피한다.

---

# 28. 기존 문서가 있으면 덮어쓰지 않는다

`docs/`에 기존 작업 기록이 있다면 먼저 확인한다.

기존 작업 문서를 삭제하거나 덮어쓰지 않는다.

새 작업은 새로운 작업 문서로 기록한다.

기존 문서를 수정해야 하는 특별한 이유가 있다면 변경 이유를 확인한 후 최소 범위만 수정한다.

---

# 29. 코드 변경이 추가되면 문서도 최종 상태에 맞춘다

문서를 작성한 뒤 오류 수정이나 구조 변경으로 코드가 다시 수정되었다면 작업 완료 전에 문서도 다시 확인한다.

다음 정보가 실제 코드와 일치해야 한다.

- 파일명
- 함수명
- Endpoint
- 실행 흐름
- Request / Response
- Mock / 실제 구현 여부
- 실행 방법
- 테스트 결과

---

# 30. 작업 완료 보고

모든 작업이 끝나면 사용자에게 다음 내용을 간단하게 보고한다.

```text
구현한 기능
수정/추가한 주요 파일
검증 결과
작성한 docs 문서 경로
남아 있는 미구현 기능
```

예:

```text
작업 문서:
docs/02_Admin_FastAPI_Mock_Backend_2026-08-19.md
```

# 핵심 원칙

작업 설명서에서 가장 중요하게 보여줘야 하는 것은 다음 세 가지다.

### 1. 무엇을 만들었는가

```text
작업 목적 → 구현 결과
```

### 2. 어떻게 실행되는가

```text
Request
→ Router
→ 중심 함수
→ 세부 기능 호출
→ 결과 반환
→ 중심 함수
→ Response
```

### 3. 코드를 어디서부터 읽어야 하는가

```text
진입점
→ 중심 함수
→ 세부 Service
→ Repository / 외부 기능
```

특히 다른 파일의 로직을 호출하는 경우 다음 관계를 명확하게 문서화한다.

```text
중심 함수
→ 세부 함수 호출
← 결과 반환
→ 다음 단계 실행
```

작업 문서는 **프로젝트를 처음 보는 초심자가 실제 실행 흐름을 따라갈 수 있는 설명서**가 되는 것을 가장 중요한 목표로 한다.
