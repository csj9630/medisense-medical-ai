# Hybrid OCR 구현

- 작업일: 2026-08-19
- 작업 영역: Backend / FastAPI, Frontend / React
- 대상 기능: 관리자 이미지·PDF Hybrid OCR
- 주요 기술: FastAPI, PaddleOCR, PaddlePaddle, PyMuPDF, pymupdf4llm, Pillow
- 작업 범위: 실제 파일 업로드, 문서 검증, Native Text 추출, 선택적 OCR, 텍스트 정제, Chunking, 관리자 결과 표시
- 제외 범위: Embedding, 실제 VectorDB 저장, RAG 검색, LLM OCR 교정, OCR 엔진 비교

## 1. 작업 목적

기존 관리자 OCR 화면은 파일 본문을 서버로 보내지 않고 파일명과 크기만 JSON으로 전송했다.
Backend는 고정된 Mock 텍스트와 Chunk를 반환했기 때문에 실제 문서의 내용을 확인할 수 없었다.

이번 작업에서는 다음 목표를 구현했다.

```text
관리자 파일 업로드
→ FastAPI multipart 요청
→ 디지털 PDF는 Native Text 우선 추출
→ 필요한 이미지 영역과 스캔 페이지만 PaddleOCR
→ 텍스트 정제
→ Chunk 생성
→ 기존 관리자 결과 화면에 반환
```

PDF 전체를 무조건 이미지로 변환하지 않고, OCR이 필요한 영역에만 PaddleOCR를 사용한다.

## 2. 작업 전후 비교

### 작업 전

```text
React OcrPanel
→ 파일 메타데이터 JSON
→ POST /api/admin/ocr/analyze
→ admin_ocr.py Mock 응답
→ 고정 텍스트 표시
```

### 작업 후

```text
React OcrPanel
→ 실제 File을 FormData로 구성
→ POST /api/admin/ocr/analyze
→ 파일 검증
→ 이미지/PDF 유형별 실제 추출
→ 정제 및 Chunking
→ 실제 문서 결과 표시
```

기존 LLM Mock과 `POST /api/admin/ocr/vector-save-test` 저장 Mock은 유지했다.

## 3. 전체 실행 흐름

중심 함수는 다음과 같다.

```text
DocumentProcessingService.process_document()
```

이 함수를 먼저 읽으면 전체 처리 순서를 확인할 수 있다.

```text
process_document()

→ validate_chunk_options()
← Chunk 설정 검증 결과

→ validate_document()
← 검증된 파일명, 형식, 바이너리

→ 이미지인 경우 _process_image_document()
← PaddleOCR 결과

→ PDF인 경우 process_pdf_document()
← Native/OCR 통합 결과

→ clean_document_text()
← 정제된 텍스트

→ create_chunks()
← Chunk 목록

→ _build_response()
← OcrDocumentResponse

→ Router
→ Frontend
```

## 4. PDF 처리 흐름

PDF의 중심 함수는 다음과 같다.

```text
process_pdf_document()
```

페이지마다 Native Text의 양과 유효 이미지 면적을 먼저 확인한다.

```text
PDF
→ analyze_pdf_structure()

Native Text 충분 + 유효 이미지 없음
→ pymupdf4llm Native Markdown
→ PaddleOCR 호출 0회

Native Text 충분 + 유효 이미지 있음
→ Text/Image Block을 문서 순서대로 순회
→ 이미지 Block만 PaddleOCR
→ 원래 이미지 위치에 [이미지 OCR] 삽입

Native Text 부족
→ 해당 페이지만 이미지 렌더링
→ 전처리
→ PaddleOCR
```

문서 유형은 실제 페이지 처리 결과로 구분한다.

| 유형          | 판단 결과                                   |
| ------------- | ------------------------------------------- |
| `digital_pdf` | Native Text만 사용                          |
| `hybrid_pdf`  | Native Text와 이미지/페이지 OCR을 함께 사용 |
| `scanned_pdf` | 전체 페이지가 OCR 또는 빈 페이지            |

## 5. 이미지 처리 흐름

```text
PNG/JPG 업로드
→ 확장자·MIME·실제 이미지 형식 검증
→ EXIF 방향 반영
→ 투명 배경을 흰색으로 합성
→ 최대 이미지 크기 제한
→ PaddleOCR
→ bbox 기준 위→아래, 왼쪽→오른쪽 정렬
→ 텍스트와 평균 Confidence 반환
```

Deskew, CLAHE, Perspective Correction 등은 실패 사례가 확인되지 않은 상태에서 과도하게
적용하지 않았다.

## 8. Request와 Response

### Request

```text
POST /api/admin/ocr/analyze
Content-Type: multipart/form-data
```

| 필드        | 형식    | 설명                              |
| ----------- | ------- | --------------------------------- |
| `file`      | File    | PDF, PNG, JPG/JPEG 원본 파일      |
| `chunkSize` | integer | 100~4096, 기본 512                |
| `overlap`   | integer | 기본 50, Chunk Size보다 작아야 함 |

브라우저가 multipart boundary를 생성하므로 Frontend는 `Content-Type`을 직접 지정하지 않는다.

### Response 예시

```json
{
  "documentName": "medical-document.pdf",
  "pageCount": 2,
  "characterCount": 1380,
  "estimatedChunks": 4,
  "confidence": 94.7,
  "extractedText": "## 페이지 1\n\n...",
  "chunks": ["..."],
  "readiness": "ready",
  "notes": ["문서 유형: Hybrid PDF", "PaddleOCR 처리 이미지: 1개"]
}
```

기존 Frontend가 사용하는 필드명을 유지했다. `estimatedChunks`에는 Mock 예상치가 아니라 실제
생성된 Chunk 개수가 들어간다.

## 9. 서버 검증과 오류 처리

서버는 Frontend의 `accept` 설정을 신뢰하지 않고 다음을 다시 검증한다.

- 지원 확장자: PDF, PNG, JPG/JPEG
- MIME Type
- 실제 PDF signature 또는 이미지 형식
- 빈 파일
- 최대 파일 크기
- 이미지 픽셀 수
- 손상 이미지/PDF
- 암호화 PDF
- PDF 페이지 수
- Chunk Size와 Overlap 관계

오류는 Router에서 다음 HTTP 상태로 변환한다.

| 오류                            | 상태 |
| ------------------------------- | ---: |
| 파일 크기 초과                  |  413 |
| 입력 검증 실패                  |  422 |
| PaddleOCR 설치·모델 초기화 실패 |  503 |
| 문서 처리 실패                  |  500 |

## 10. PaddleOCR 초기화와 재사용

PaddleOCR는 요청마다 새로 만들지 않는다.

```text
첫 OCR 요청
→ get_paddle_ocr_service()
→ PaddleOcrService 생성
→ 모델 초기화

이후 OCR 요청
→ 같은 설정의 캐시된 PaddleOcrService 재사용
```

`PaddleOCR` 초기화 옵션은 `backend/app/services/hybrid_ocr/paddle_ocr_service.py`에서 결정한다.
설정 가능한 값과 안정성을 위해 고정한 값, 프로젝트에서 지정하지 않은 값을 구분한다.

| 설정                           | 현재 값       | 사용하거나 사용하지 않는 이유                                                                                                                                |
| ------------------------------ | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ocr_version`                  | `PP-OCRv5`    | 사용할 OCR 모델 버전을 고정해 실행 환경에 따라 모델이 달라지지 않게 한다.                                                                                    |
| `lang`                         | `korean`      | 한국어 문서가 주요 대상이므로 한국어 인식 모델을 사용한다. `OCR_PADDLE_LANGUAGE`로 변경할 수 있다.                                                           |
| `device`                       | `cpu`         | Windows 학원 PC 등 GPU가 보장되지 않는 환경에서도 동작하도록 CPU를 기본값으로 사용한다. GPU 초기화에 실패하면 CPU로 한 번 재시도한다.                        |
| `use_doc_orientation_classify` | `False`       | 문서 전체 회전 판별 모델을 추가 실행하지 않는다. 일반 이미지와 PDF 페이지를 대상으로 추가 추론 시간과 모델 메모리 사용을 줄인다.                             |
| `use_doc_unwarping`            | `False`       | 원근 왜곡 보정 모델을 사용하지 않는다. 현재 전처리는 EXIF 방향, 투명 배경, 크기 조절까지만 수행하므로 불필요한 보정 비용과 품질 변화를 피한다.               |
| `use_textline_orientation`     | `False`       | 텍스트 라인의 회전 방향을 별도로 판별하지 않는다. 정방향 문서를 기본 대상으로 하여 추론 시간을 줄인다. 회전된 표·스탬프·촬영 문서는 인식률이 낮아질 수 있다. |
| `enable_mkldnn`                | `False`       | Windows CPU에서 PaddlePaddle 3.3.1의 oneDNN 정적 실행 경로와 관련된 PIR 변환 오류가 확인되어 안정성을 우선한다.                                              |
| `cpu_threads`                  | 지정하지 않음 | 프로젝트에서 값을 고정하지 않으므로 PaddleOCR/PaddlePaddle의 내부 기본값을 사용한다. CPU별 최적값이 달라 일괄 지정하지 않았다.                               |
| `precision`                    | 지정하지 않음 | CPU 기본 실행에 별도 정밀도 설정이 필요하지 않다. GPU FP16 최적화가 필요해질 때 별도로 검토할 수 있다.                                                       |

현재 기본 설정은 인식률을 최대화하기보다 한국어·Windows CPU·일반적인 정방향 문서를 대상으로 안정성과 처리 속도를 우선한 구성이다.

```text
OCR Version: PP-OCRv5
Language: korean
Device: cpu
Document orientation model: 사용 안 함
Document unwarping model: 사용 안 함
Text-line orientation model: 사용 안 함
MKL-DNN: 사용 안 함
```

`device`와 `language`는 `Settings`에서 읽어 같은 설정 조합에 재사용한다. 반면 방향·왜곡
관련 플래그와 `enable_mkldnn`은 현재 코드에서 고정값이다. `cpu_threads`와 `precision`은
초기화 옵션으로 전달하지 않아 라이브러리 기본 동작에 맡긴다.

### 지연 초기화와 동시성 제어

서비스 객체와 실제 Paddle 모델 로딩은 분리되어 있다.

1. `get_paddle_ocr_service(device, language)`가 캐시된 서비스를 반환한다.
2. 실제 `PaddleOCR` 모델은 첫 `extract_text()` 호출 때 초기화한다.
3. 이후에는 같은 Pipeline을 재사용한다.
4. `_initialization_lock`으로 동시 요청의 중복 초기화를 막는다.
5. Paddle Pipeline의 동시 `predict`를 피하기 위해 `_inference_lock`으로 추론을 한 번에 하나씩 실행한다.

`get_paddle_ocr_service()`는 `device`와 `language` 조합을 기준으로 최대 4개 서비스를 캐시한다.
따라서 같은 설정의 요청마다 모델을 새로 만들지 않는다. 디지털 PDF처럼 OCR이 필요하지 않은
경우에는 OCR 경로를 호출하지 않으므로 PaddleOCR 모델도 초기화하지 않는다.

```text
OCR_PDF_RENDER_DPI

OCR_PADDLE_LANGUAGE
```

PDF 유형 판단 threshold를 여러 파일에 하드코딩하지 않고 Config에서 관리한다.

## 18. 작업 시 주의사항

- 기존 `docs/03`, `docs/05`는 Mock 또는 단계별 계획 당시 상태를 설명한다. 실제 최신 구현은 이 문서를 기준으로 확인한다.
- 최초 PaddleOCR 요청은 모델 다운로드와 초기화 때문에 오래 걸릴 수 있다.
- 의료 문서 원문과 개인정보를 로그에 출력하지 않는다.
- 디지털 PDF는 OCR Confidence 대신 직접 추출 성공 기준으로 100%를 표시한다.
- `OCR_NATIVE_TEXT_MIN_CHARS`와 `OCR_SIGNIFICANT_IMAGE_AREA_RATIO` 변경은 PDF 분기 결과에 영향을 준다.
- PDF 이미지 OCR은 raster image Block을 대상으로 한다. 복잡한 vector graphic 자체를 이미지 OCR 대상으로 변환하지는 않는다.
- 관리자 API의 별도 권한 Guard는 이번 범위에서 추가하지 않았다.
