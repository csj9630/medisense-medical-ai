# LLM 연동 전수 감사 보고서

- 감사일: 2026-08-20
- 감사 범위: Provider Registry, Ollama/Gemini 오류 처리, 비밀키, async 자원, 동시성, Frontend 상태 전이, 환경변수 협업, API 계약, 테스트
- 감사 관점: Senior Backend · Frontend · Security Engineer
- 작업 조건: 코딩 비허가. 본 보고서 외 소스·설정 파일은 수정하지 않음

## 1. 결론

현재 구현은 로컬 개발 시연은 가능하지만 배포 승인 불가 상태다. 가장 큰 문제는 관리자 LLM API와 `/admin` 화면에 인증·관리자 권한 검사가 없다는 점이다.

확인한 위험은 다음과 같다.

- Critical: 1건
- High: 6건
- Medium: 5건

비밀키가 Frontend 번들, API 응답 또는 애플리케이션 로그로 직접 노출되는 경로는 발견하지 못했다. 그러나 비밀키를 사용하는 API 자체가 보호되지 않아 Gemini 쿼터와 Ollama 자원은 오용될 수 있다.

## 2. Critical

### C-1. Admin LLM API와 화면에 인증·관리자 권한 검사가 없다

근거:

- `backend/app/api/admin/router.py:33`: `APIRouter()`에 인증 의존성이 없다.
- `backend/app/api/router.py:25`: Admin Router가 `/admin`에 그대로 연결된다.
- `frontend/src/app/router.tsx:34`: `/admin`이 `RequireAuth` 바깥에 있다.
- `frontend/src/features/admin/services/apiAdminAiService.ts:74-87`: 모델 목록과 실행 요청에 JWT를 보내지 않는다.
- `frontend/src/services/apiClient.ts:15`: 공통 Client는 토큰 전달 기능을 지원하지만 Admin 서비스가 사용하지 않는다.
- `backend/app/models/generated.py:29-44`: `Users` 모델에 실제 `is_admin` 컬럼이 없다.
- `backend/app/services/auth.py:22-23`: 컬럼이 없으면 사용자를 일반 사용자로 처리한다.

영향:

- API에 네트워크 접근할 수 있는 누구나 Gemini 무료 쿼터를 소진할 수 있다.
- 로컬 Ollama CPU/GPU를 장시간 점유할 수 있다.
- 의료·개인정보가 외부 Provider로 전송되는 기능을 비인가 사용자가 호출할 수 있다.
- CORS는 브라우저 출처 제한일 뿐 인증 경계가 아니다.

수정안:

1. `users.role` 또는 `is_admin NOT NULL DEFAULT false` DB 마이그레이션을 추가한다.
2. `get_current_admin` 의존성을 만들고 Admin Router 전체에 적용한다.
3. Frontend에 `RequireAdmin`을 추가하고 Admin API에 JWT를 전달한다.
4. 권한 체계가 완성되기 전까지 운영 환경에서는 Admin LLM API를 비활성화한다.
5. `backend/app/core/config.py:15`의 기본 JWT 비밀 문자열이 운영에서 사용되면 시작을 거부한다.
6. 익명 401, 일반 사용자 403, 관리자 200 테스트를 추가한다.

## 3. High

### H-1. 출력량과 대기열 제한이 없어 자원 고갈이 가능하다

근거:

- `backend/app/schemas/admin.py:50`: 입력 프롬프트만 10,000자로 제한한다.
- `backend/app/services/llm/contracts.py:25`: `max_output_tokens` 계약은 존재한다.
- `backend/app/services/admin_llm.py:70-75`: Facade가 출력 토큰 제한을 설정하지 않는다.
- `backend/app/services/llm/providers/ollama.py:94-96`: 값이 있을 때만 `num_predict`를 전달한다.
- `backend/app/services/llm/providers/gemini.py:70-74`: Gemini 생성 설정에 출력 한도를 전달하지 않는다.
- Ollama/Gemini 모두 semaphore 획득 대기가 Provider 제한시간 바깥에 있다.
- semaphore는 프로세스별이므로 다중 worker에서 총 동시성이 증가한다.

Gemini 2.5 Flash는 최대 65,536 출력 토큰을 지원하므로 요청 하나의 비용과 응답 크기도 커질 수 있다.

수정안:

- 서버 기본 출력 한도 1,024~2,048토큰을 강제한다.
- 전체 timeout이 semaphore 대기와 Provider 호출을 모두 포함하도록 한다.
- bounded queue를 두고 초과 요청은 즉시 429 또는 503으로 거부한다.
- 사용자/IP별 rate limit과 Provider별 admission control을 추가한다.
- 다중 worker에서는 Redis 제한 또는 전용 LLM worker queue를 사용한다.

### H-2. Frontend의 취소가 서버 Provider 실행을 취소하지 않는다

근거:

- `frontend/src/features/admin/hooks/useLlmComparison.ts:198-219`는 브라우저 fetch만 abort한다.
- Backend에는 실행 ID, 취소 API, 서버 Task 저장소 또는 연결 종료 감시가 없다.
- UI도 Provider 추론이 계속될 수 있다고 표시한다.

영향:

- 사용자는 취소됐다고 보지만 Gemini 쿼터와 Ollama 자원은 계속 소비될 수 있다.

수정안:

- `POST /llm/jobs`, `DELETE /llm/jobs/{id}` 형태로 서버 작업을 관리한다.
- Provider coroutine 취소가 실제 HTTP 요청까지 전달되는지 검증한다.
- 서버 취소 확인 전에는 UI를 `cancelling` 상태로 표시한다.

### H-3. 기본 Gemini 모델이 2026-10-16 종료 예정이다

> 후속 조치(2026-08-20): 기본 모델을 실제 호출 검증에 성공한 `gemini-3.5-flash-lite`로 교체했다. 아래 내용은 감사 시점에 발견된 기존 상태를 기록한 것이다.

근거:

- `backend/app/core/config.py:40`: 기본 모델이 `gemini-2.5-flash`다.
- `backend/app/services/llm/registry.py:56-64`: 화면 라벨도 Gemini 2.5 Flash로 고정되어 있다.
- 환경변수로 모델 ID를 바꿔도 화면 라벨은 이전 모델명으로 남는다.

Google 공식 종료 일정의 권고 대체 모델은 `gemini-3.6-flash`다.

수정안:

- 무료 등급과 지역 지원 여부를 확인한 뒤 권고 모델로 전환한다.
- 라벨·설명·Provider 모델 ID를 동일한 Registry 메타데이터에서 관리한다.
- TTL 기반 실제 모델 접근성 점검과 모델 종료 일정 운영 체크리스트를 둔다.

### H-4. 파일명 조건이 실제 Provider에는 전달되지 않는다

근거:

- `frontend/src/features/admin/components/llm/LlmTestForm.tsx:68-70`은 모든 모델에 파일명 조건이 동일하게 전달된다고 안내한다.
- `backend/app/services/llm/providers/mock.py:92-100`은 파일명을 Mock 답변에 반영한다.
- Ollama는 `prompt`와 선택적 `system_prompt`만 사용한다.
- Gemini는 `request.prompt`만 사용한다.

영향:

- Mock과 실제 Provider가 서로 다른 입력을 받아 비교 실험의 전제가 깨진다.

수정안:

- RAG 미구현 상태에서는 파일 선택과 `documentName` 계약을 제거하는 것이 안전하다.
- 유지한다면 Application 계층에서 공통 입력을 한 번 생성해 모든 Provider에 동일하게 전달한다.
- 외부 Gemini로 파일명을 보낼 때는 개인정보 포함 가능성을 고려해 동의와 정제를 적용한다.

### H-5. 외부 의료·개인정보 전송 방지가 경고문에만 의존한다

근거:

- `frontend/src/features/admin/components/llm/LlmPanel.tsx:26-29`에 안내문은 있다.
- Backend는 임의 프롬프트를 그대로 Gemini에 전송한다.
- 역할 기반 허가, Provider allowlist, 개인정보 마스킹 또는 운영 비활성화 정책이 없다.

수정안:

- 운영 기본값에서는 외부 Provider를 비활성화한다.
- 관리자별 명시적 권한과 외부 전송 확인 절차를 둔다.
- 조직 정책에 맞는 개인정보 탐지·마스킹 또는 전송 차단을 서버에 둔다.
- 프롬프트 원문은 계속 로그에 남기지 않는다. 현재 완료 로그는 모델 메타데이터만 기록해 이 부분은 양호하다.

### H-6. 한 Provider의 오류가 전체 모델 목록을 실패시킬 수 있다

근거:

- `backend/app/services/llm/application.py:31-33`의 `asyncio.gather`는 예외를 모델별로 격리하지 않는다.
- `_check_availability`는 `LlmProviderUnavailableError`만 처리한다.
- 가용성 확인 후 Provider를 다시 resolve하므로 등록 누락 오류가 다시 전파된다.
- `backend/app/services/llm/providers/ollama.py:62-72`는 JSON 최상위가 dict가 아니면 발생하는 `AttributeError`를 처리하지 않는다.

영향:

- Ollama 하나의 비정상 응답 때문에 Gemini와 네 Mock 모델 카드까지 모두 사라질 수 있다.

수정안:

- 모델별 상태 점검을 독립적인 예외 경계로 감싼다.
- 예상하지 못한 오류는 correlation ID와 함께 서버에 기록하고 해당 모델만 unavailable로 반환한다.
- Ollama JSON 최상위와 필드 타입을 명시적으로 검증한다.
- Provider resolve는 모델당 한 번만 수행한다.

## 4. Medium

### M-1. Registry 중복 ID가 조용히 덮어써진다

근거:

- `backend/app/services/llm/registry.py:16`: 중복 모델 ID가 마지막 값으로 덮어써진다.
- `backend/app/services/llm/registry.py:30`: 중복 Provider key도 마지막 값으로 덮어써진다.

수정안:

- Registry 생성 시 중복을 검사하고 애플리케이션 시작을 실패시킨다.
- `system_prompt`, 출력 제한, 파일 입력 등의 Provider capability를 명시한다.
- 지원하지 않는 공통 필드를 Provider가 조용히 무시하지 못하게 한다.

### M-2. Gemini 가용성과 오류 계약이 실제 상태를 반영하지 못한다

근거:

- `backend/app/services/llm/providers/gemini.py:46-58`은 키 문자열 존재와 SDK 설치 여부만 검사한다.
- 폐기된 키, 권한 없는 키, 존재하지 않는 모델도 available로 표시될 수 있다.
- 오류 응답은 안정적인 코드 없이 한국어 문자열만 전달한다.
- 429 응답에 `Retry-After` 정보가 없다.

수정안:

- 짧은 TTL로 실제 키·모델 접근성을 검사한다.
- `LLM_AUTHENTICATION`, `LLM_RATE_LIMIT`, `LLM_TIMEOUT`, `MODEL_NOT_FOUND` 등의 고정 오류 코드를 정의한다.
- 재시도 가능 여부와 가능하면 재시도 시간을 응답 계약에 포함한다.

### M-3. async 자원 누수는 보이지 않지만 연결 재사용과 정리 관찰성이 부족하다

확인 결과:

- Ollama는 매 요청마다 `httpx.AsyncClient`를 만들고 context manager로 닫는다.
- Gemini도 매 요청마다 sync/async client를 만들고 둘 다 닫는다.
- 명백한 client 누수는 발견하지 못했다.

문제:

- 연결 풀을 재사용하지 않아 호출량 증가 시 handshake 비용이 커진다.
- `backend/app/services/llm/providers/gemini.py:100-111`은 client 종료 오류를 모두 무시한다.

수정안:

- FastAPI lifespan에서 Provider client를 만들고 종료 시 한 번 닫는다.
- 정리 실패가 원래 요청 오류를 덮지는 않되 warning 로그와 metric에 남도록 한다.

### M-4. 최상위 `.env` 방식은 타당하지만 협업 동선이 혼란스럽다

양호한 점:

- `.gitignore:9`가 실제 `.env`를 제외한다.
- 추적 파일에서 Gemini 키 형태 값은 발견되지 않았다.
- `GEMINI_API_KEY`에 `VITE_` 접두사가 없어 브라우저 번들로 직접 노출되지 않는다.
- 현재 Vite 설정은 `VITE_` 변수만 Client에 노출한다.

문제:

- `frontend/vite.config.ts:8`의 `envDir: '..'` 때문에 `frontend/.env`는 읽지 않는다.
- 협업자가 `frontend/.env.example`을 `frontend/.env`로 복사하면 작동하지 않는다.
- `VITE_API_URL` 예제가 최상위와 Frontend 두 파일에 있어 값이 어긋날 수 있다.
- Vite proxy는 `/api/v1`이지만 실제 API prefix는 `/api`다.
- 운영 빌드에서 `VITE_API_URL`이 빠지면 `http://localhost:8000/api`가 번들에 들어간다.

수정안:

- 실제 환경 파일은 계속 최상위 하나만 사용한다.
- `frontend/.env.example`에 실제 복사 대상이 `../.env`임을 명시한다.
- CI에서 두 예제의 `VITE_API_URL` 일치를 검사한다.
- 운영 기본값은 동일 출처 `/api`로 하고 Vite proxy도 `/api`로 통일한다.

현재 `frontend/.env.example`은 복구되어 있으며 내용 차이는 없다.

### M-5. API 오류 계약과 기존 Compare 계약이 일관되지 않다

근거:

- `/llm/run`은 Provider 오류를 HTTP 오류로 반환한다.
- `/llm/compare`는 일부 Provider 오류를 HTTP 200 내부의 `status="error"`로 반환한다.
- Compare 실패 응답의 `responseTimeSeconds`는 실제 경과시간이 아닌 0이다.
- Frontend `apiClient`는 FastAPI validation detail 배열을 안정적으로 표시하지 못한다.
- 오류에 request ID, 고정 code, retryable, retry-after 필드가 없다.

수정안:

- `{code, message, retryable, retryAfterSeconds, requestId}` 형태의 공통 오류 envelope를 정의한다.
- 기존 `/llm/compare`를 폐기하거나 새 실행 계약으로 통일한다.
- Pydantic validation 오류를 Frontend가 표시 가능한 형태로 정규화한다.

## 5. 테스트 감사

`backend/tests/test_admin_llm.py`에는 Registry, Ollama 정상 응답, Gemini 정상 응답·429, 기본 API 계약 등 9개의 핵심 테스트가 있다. 그러나 장애 경로 검증이 부족하다.

누락 테스트:

- 익명 401, 일반 사용자 403, 관리자 200
- Ollama 연결 실패, timeout, 400/404/429/5xx, 비정상 JSON, 빈 답변
- Gemini 키 없음, 401/403, timeout, 차단 응답, 빈 답변, 종료 실패
- semaphore 대기 timeout과 동시성 상한
- Frontend 취소 후 서버 Task 종료
- 한 Provider 실패 시 나머지 모델 목록 유지
- Registry 중복 검출
- `/llm/compare` 회귀
- 실제 Ollama/Gemini opt-in smoke test
- Frontend 개별 실행, 전체 실행, 취소, reset, stale response 상태 전이

Frontend에는 테스트 파일과 `test` script가 없다. Playwright 패키지는 있지만 LLM UI 테스트로 연결되지 않았다.

`backend/requirements.txt:14`의 `google-genai>=1.0,<3.0` 범위도 넓고 Python lock/constraints가 없어 학원 PC와 다른 PC가 서로 다른 SDK를 설치할 수 있다. 검증된 SDK 버전을 constraints 또는 lock 파일로 고정할 필요가 있다.
