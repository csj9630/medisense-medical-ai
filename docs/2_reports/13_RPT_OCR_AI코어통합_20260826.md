## 1. 작업 목적

병합 후 서비스 문서 OCR과 Admin OCR이 서로 다른 Paddle Engine·전처리·PDF 처리 경로를 사용하고 있었다. 같은 문서가 Endpoint에 따라 다른 결과를 만들고 한쪽만 수정되는 문제를 막기 위해 문서 검증, Image 전처리, Paddle 실행, PDF·Office 추출과 후처리를 Framework 독립 `ai/ocr` Core 하나로 통합했다.

Backend에는 FastAPI `UploadFile`, 인증, Thread 실행 경계, Admin Chunk·Job·Embedding·DB 저장과 HTTP Response 변환만 남겼다.

## 2. 작업 전 상태

### 서비스 문서 OCR

```text
POST /api/documents/ocr
→ Backend Router
→ 별도 OCR 또는 Hybrid OCR 호출
→ 서비스용 text + 합성 line 반환
```

### Admin OCR

```text
POST /api/admin/ocr/analyze 또는 /jobs
→ backend/app/services/hybrid_ocr
→ 별도 검증·전처리·Paddle·PDF·Office 처리
→ 문자 Chunk와 Admin Response
```

두 경로에는 Paddle 생성, Image 전처리, 결과 Parsing과 PDF 정책이 중복되어 있었다.

## 3. 작업 후 상태

두 Endpoint가 같은 중심 함수 `ai.ocr.pipeline.analyze_document()`를 사용한다.

```text
/api/documents/ocr ─┐
                    ├→ backend/app/services/ocr_workflow.py
/api/admin/ocr/* ───┘              ↓
                         asyncio.to_thread()
                                  ↓
                    ai.ocr.analyze_document()
                                  ↓
             검증 → 형식별 추출 → 전처리 → 단일 Paddle
                                  ↓
             Raw/Cleaned Text + 실제 OCR Line 공통 결과
                                  ↓
          서비스 Response 또는 Admin Chunk·Job Response
```

## 4. 중심 함수

중심 함수는 `ai/ocr/pipeline.py`의 `analyze_document()`다.

```text
analyze_document()
→ validate_document()
← ValidatedDocument
→ Image/PDF/Office 추출기
← ExtractedDocument
→ clean_document_text()
← Cleaned Text
→ OcrDocumentResult 조립
← Backend Adapter
```

형식별 추출기가 Chunking이나 DB 저장을 이어서 실행하지 않고 모든 결과를 중심 함수에 반환한다.

## 5. 공통 Domain 계약

`ai/ocr/contracts.py`에 다음 Framework 독립 계약을 추가했다.

| 계약 | 역할 |
|---|---|
| `OcrDocumentInput` | 파일명, MIME, Bytes 입력 |
| `OcrProcessingConfig` | 검증·전처리·Engine 설정 |
| `OcrLine` | 실제 OCR Line의 Text·Confidence·Page·Box·Source |
| `OcrEngineResult` | Paddle 결과를 추출기에 전달 |
| `ExtractedDocument` | 형식별 추출 결과를 중심 함수에 반환 |
| `OcrDocumentResult` | Raw/Cleaned Text와 문서 Meta를 포함한 최종 공통 결과 |

`ai/ocr` Python 파일에서 `fastapi`, `app.*`, `sqlalchemy`, `UploadFile`, `TestClient` Import가 없음을 정적으로 확인했다.

## 6. 형식별 처리

### Image

```text
Bytes 검증
→ EXIF 방향 반영
→ 투명 배경 흰색 합성
→ 한 번 Resize
→ 설정에 따른 Denoise·Deskew
→ 단일 Paddle Engine
```

### PDF

- Digital PDF: Native Text를 직접 추출하고 Paddle을 호출하지 않는다.
- Scanned PDF: Page 전체를 Rendering한 뒤 공통 전처리와 Paddle을 호출한다.
- Hybrid PDF: Native Text Block과 유효 Image OCR 결과를 문서 순서대로 합친다.
- OCR Line의 Page는 0 기준 실제 PDF Page Index로 보존한다.

### DOCX/PPTX

- OOXML Text, 표, Slide, 발표자 Note 직접 추출을 유지했다.
- 포함 Image만 공통 Image 전처리와 단일 Paddle Engine으로 전달한다.
- ZIP Path Traversal, Entry 수와 압축 해제 크기 제한을 유지했다.
- DOCX의 실제 Page 수를 계산하지 않는 기존 의미를 유지했다.

## 7. Raw Text와 Confidence 정책

- `raw_text`는 Confidence 기준 아래 Line과 정제 전 Text를 보존한다.
- `cleaned_text`는 제어문자와 과도한 빈 줄을 제거한다.
- `lines`에는 Confidence 기준 아래 Line도 포함해 실제 인식 결과를 보존한다.
- 최종 표시 Text에는 `OCR_MIN_CONFIDENCE` 기준을 적용한다.
- 연속된 동일 OCR Line만 Text 조립 단계에서 중복 제거한다.
- Native PDF와 Office 직접 추출 Text는 실제 OCR Line으로 위장하지 않는다.

## 8. Paddle Engine

`ai/ocr/engine.py`만 `PaddleOCR`를 생성하고 `predict()`를 호출한다.

현재 설치 환경과 requirements 기준은 다음과 같다.

| 항목 | 값 |
|---|---|
| PaddlePaddle | `>=3.3,<3.4` (검증 환경 3.3.1) |
| PaddleOCR | `>=3.7,<3.8` (검증 환경 3.7.0) |
| OCR Version | `PP-OCRv5` |
| Language | Backend 설정 기본 `korean` |
| Text Line Orientation | `False` |
| MKLDNN | `False` |

Admin Hybrid OCR의 검증된 옵션을 기준으로 Orientation을 `False`로 유지했다. 동일 설정 Engine Cache, 초기화 Lock, 추론 Lock과 GPU 실패 시 CPU Fallback도 유지했다.

## 10. API 호환 내용

### `POST /api/documents/ocr`

- Endpoint와 `get_current_user` 인증 Dependency를 유지했다.
- Response의 `text`, `lines[].text`, `lines[].confidence`, `lines[].page`를 유지했다.
- 이전 합성 Line 대신 공통 Core의 실제 OCR Line을 반환한다.
- Native PDF와 Office 직접 추출만 있는 경우 `text`는 존재하고 `lines`는 빈 배열일 수 있다.

### Admin OCR

다음 Endpoint를 유지했다.

```text
POST /api/admin/ocr/analyze
POST /api/admin/ocr/jobs
GET  /api/admin/ocr/jobs/{job_id}
POST /api/admin/ocr/vector-save
```

- Multipart `file`, `chunkSize`, `overlap`을 유지했다.
- Job 생성 `202 Accepted`와 상태 전이를 유지했다.
- 기존 `OcrDocumentResponse` Field, Chunk 순서와 Vector Save 연결을 유지했다.
- Admin 인증과 운영 배포 제외는 이번 작업에서 변경하지 않았다.

## 12. Requirements와 실행 환경

- OCR 의존성 기준 파일을 `ai/ocr/requirements.txt`로 통일했다.
- `backend/requirements.txt`는 `-r ../ai/ocr/requirements.txt`로 이를 참조한다.
- 중복 Paddle, NumPy, Pillow, PyMuPDF, Office 의존성 선언을 Backend에서 제거했다.
- `pypdfium2`를 제거하고 PDF Renderer를 PyMuPDF로 통일했다.
- 개발 전용 `sqlacodegen`은 `backend/requirements-dev.txt`에만 둔다.
- `run.bat`은 프로젝트 루트를 `PYTHONPATH`로 설정하고 시작 전 `ai.ocr` Import를 확인한다.
- Dockerfile은 기존부터 `ai/ocr/requirements.txt`와 `ai/ocr/` 전체를 복사하므로 추가 변경 없이 새 Package 구조를 포함한다.

추가 환경변수:

```text
OCR_MIN_CONFIDENCE
OCR_ENABLE_DENOISE
OCR_ENABLE_DESKEW
```

## 14. 실제 기능과 Mock 구분

제품 코드는 실제 PaddleOCR, PyMuPDF, python-docx, python-pptx를 호출한다. Unit Test에서는 모델 Download와 긴 추론을 피하기 위해 Fake OCR Engine을 주입했으며 실제 PDF·DOCX·PPTX 구조는 Test Fixture Factory로 생성했다.

`tests/smoke/test_paddle_ocr.py`는 실제 Paddle Model을 호출하지만 `RUN_PADDLE_OCR_SMOKE=1`일 때만 실행한다.

## 15. 실행하지 못한 검증

### 실제 Paddle Smoke Test

모델 Download·Cache와 CPU 실행 시간이 필요한 선택 Test이므로 이번 기본 검증에서는 실행하지 않았다. 따라서 실제 한국어 OCR 정확도, Denoise·Deskew 전후 품질과 모델 초기화 성공을 통과했다고 보고하지 않는다.

### Docker Build

다음 명령을 실제로 시도했다.

```powershell
docker build --file backend/dockerfile --tag thegpt-ocr-integration-check .
```

Docker Desktop Linux Engine이 실행 중이지 않아 Daemon 연결 단계에서 실패했다. Dockerfile의 Copy와 requirements 상대 경로는 정적으로 확인했지만 실제 Image Build 성공으로 기록하지 않는다.

## 16. 남은 위험과 후속 작업

1. 실제 대표 문서로 Paddle Smoke/A·B Test를 실행해 `OCR_ENABLE_DENOISE`, `OCR_ENABLE_DESKEW`, `OCR_MIN_CONFIDENCE` 기본값을 확정해야 한다.
2. Docker Desktop 또는 CI에서 실제 Backend Image Build와 Container Import를 확인해야 한다.
3. 메모리 기반 OCR Job은 다중 Worker·재시작 환경에서 상태를 공유하지 못한다. 운영 승격 시 Redis/DB/Queue 전환이 필요하다.
4. Admin API 인증과 운영 배포 시 Frontend·Backend 동시 제외는 별도 보안 작업이다.
5. LLM Core 이관은 이번 OCR 범위에 포함하지 않았다.
6. OCR 원본 파일 영구 저장과 사용자 수정본 별도 DB 보존은 후속 저장 정책이 필요하다.
