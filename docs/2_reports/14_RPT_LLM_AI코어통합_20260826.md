## 1. 작업 목적

작업 전에는 Admin LLM과 MedGemma API가 서로 다른 실행 계약과 Registry를 사용했다.

```text
Admin LLM
→ backend/app/services/admin_llm.py
→ backend/app/services/llm/
→ Ollama / Gemini / Mock
```

```text
일반 LLM API
→ backend/app/services/llm_service.py
→ ai/llm/
→ MedGemma + LoRA Adapter
```

이 구조에서는 Provider와 모델을 추가할 때 두 계통을 따로 관리해야 하고, Admin
Provider를 AI Core에서 재사용하기 어려웠다. 이번 작업은 Provider 계약, Registry,
Application Service와 Provider 구현을 `ai/llm`으로 통합하고 Backend에는 HTTP Adapter만
남기는 것이 목적이다.

## 3. 최종 통합 구조

```text

일반 LLM Client          │  → ModelRegistry.resolve()

                         ┘  → Provider.generate()
```

최종 책임 경계:

## 4. 중심 함수와 실행 흐름

공통 중심 함수:

```text
LlmApplicationService.run()
```

실행 순서:

```text
Model ID와 ProviderGenerateRequest 입력
→ ModelRegistry.resolve()
← LlmModelDefinition
→ ProviderRegistry.resolve()
← LlmProvider
→ provider.generate()
← ProviderGenerateResult
→ 실행 시간과 Provider 정보를 LlmExecutionResult로 구성
← Backend Adapter에 반환
```

Application Service는 Provider 종류를 직접 분기하지 않는다. 모델 정의의
`provider_key`를 바꾸면 동일한 실행 순서에서 다른 Provider를 선택할 수 있다.

## 5. 공통 Domain 계약

추가 파일:

```text
ai/llm/contracts.py
```

공통 입력은 단일 Prompt가 아니라 Messages를 기준으로 한다.

```python
@dataclass(frozen=True)
class LlmMessage:
    role: Literal["system", "user", "assistant"]
    content: str


@dataclass(frozen=True)
class ProviderGenerateRequest:
    messages: tuple[LlmMessage, ...]
    document_name: str | None = None
    max_output_tokens: int | None = None
```

Admin의 단일 Prompt는 `ProviderGenerateRequest.from_prompt()`를 통해 user message로
변환한다. 일반 LLM API는 요청받은 Message의 role과 순서를 그대로 Core에 전달한다.

공통 결과:

```text
answer
input_tokens
output_tokens
total_tokens
finish_reason
```

Provider가 제공하지 않는 실제 토큰 값은 추측하지 않고 `None`으로 유지한다.

## 6. Registry 통합

`ai/llm/registry.py`에 다음 Core 구현을 통합했다.

- `ModelRegistry`
- `ProviderRegistry`
- MedGemma Model Definition
- 기존 `ModelEntry` 호환 Projection

MedGemma의 단일 기준:

```text
MEDGEMMA_MODEL_DEFINITIONS
├─ medgemma-screening
└─ medgemma-main
```

기존 `MODEL_REGISTRY`, `get_model_entry()`, `list_models()`는 위 Definition에서 파생되는
호환 계층으로 유지했다. Adapter Repository 정보를 두 번째 상수 목록에 다시 작성하지
않는다.

Admin 모델은 Backend Settings 값이 필요하므로
`backend/app/services/admin_llm.py::create_admin_model_registry()`에서 완성된 Definition을
만들어 Core Registry에 주입한다.

Admin 모델 ID:

```text
ollama-gemma3
gemini
medgemma       # 기존 Mock
gemma          # 기존 Mock
qwen           # 기존 Mock
llama           # 기존 Mock 오류 비교군
```

Admin Mock `medgemma`와 실제 LoRA ID `medgemma-screening`, `medgemma-main`을 서로
대체하지 않았다.

## 7. Provider 이관 결과

### 7.1 Ollama

이관 위치:

```text
ai/llm/providers/ollama.py
```

보존된 기능:

- `/api/tags` 모델 설치 확인
- `/api/chat` 비동기 호출
- system/user/assistant Message 순서
- Timeout과 최대 동시 실행 제한
- Token Count와 Finish Reason 매핑
- 404/429/5xx Domain 오류 변환

### 7.2 Gemini

이관 위치:

```text
ai/llm/providers/gemini.py
```

보존·추가된 기능:

- Google GenAI 비동기 Client
- Client 정리
- API Key/패키지 가용성 확인
- Token Count와 Finish Reason 매핑
- 401/403/404/429/5xx 및 안전 정책 오류 변환
- system message의 `system_instruction` 변환
- assistant role의 Gemini `model` role 변환
- 대화 Message 순서 유지

로그에는 Prompt, API Key, Provider 원본 오류 문자열을 기록하지 않는다.

### 7.3 Mock

이관 위치:

```text
ai/llm/providers/mock.py
```

기존 Admin 비교 UI 회귀 방지를 위해 네 개 Fixture와 `isMock` 계약을 유지했다. 이번
작업에서는 운영 환경별 Mock 등록 정책을 추가하지 않았다.

### 7.4 MedGemma

추가 위치:

```text
ai/llm/providers/medgemma.py
```

기존 동기식 `MedGemmaEngine`을 공통 비동기 Provider로 감쌌다.

```text
Provider.generate()
→ asyncio.Semaphore
→ asyncio.to_thread()
→ MedGemmaEngine.generate()
← 생성 문자열
→ ProviderGenerateResult
```

`MedGemmaEngine`에는 별도 `_inference_lock`을 추가했다.

```text
Adapter 로드
→ set_adapter()
→ Tokenize
→ model.generate()
→ Decode
```

이 전체 구간을 보호하므로 여러 요청이 동시에 다른 Adapter를 선택하는 문제를 방지한다.
Provider의 Semaphore도 기본 동시 실행 수를 1로 제한한다.

모델 목록과 가용성 확인만으로 Base Model 또는 LoRA Adapter를 로드하지 않는다. 실제
첫 생성 요청에서만 기존 Engine의 지연 로딩이 실행된다.

## 8. Backend Adapter 결과

### 8.1 Admin Adapter

파일:

```text
backend/app/services/admin_llm.py
```

역할:

- Settings를 Admin Model Definition으로 변환
- Ollama/Gemini/Mock Provider 생성
- Admin Prompt를 Core Message로 변환
- Core 결과를 camelCase Admin Response로 변환
- 비교 결과 성공/실패 격리

### 8.2 일반 LLM Adapter

파일:

```text
backend/app/services/llm_service.py
```

역할:

- 기존 Pydantic Message를 Core Message로 변환
- MedGemma Application Service 조립
- Core 결과를 기존 snake_case Response로 변환
- 기존 일반 API의 404/503 등 상태 변환
- 비교 모델별 실패 격리

기존 동기 Router는 공통 비동기 Core에 맞춰 정상적인 `async/await` 흐름으로 전환했다.
`asyncio.run()`은 사용하지 않았다.

### 8.3 Message 입력 검증

`backend/app/schemas/llm.py`에서 다음 role만 허용한다.

```text
system
user
assistant
```

Message 또는 Model 목록이 비어 있거나 Content가 빈 문자열이면 Pydantic 422로 거부한다.

## 12. Docker 변경

`backend/dockerfile`에 다음을 추가했다.

- LLM API requirements 복사
- `ai/llm` 소스 복사

또한 기존에 `.dockerignore`가 없어 첫 Build Context가 220MB를 넘어서 계속 증가하는
문제를 발견했다. 첫 Build는 중단하고 다음 항목을 제외하는 `.dockerignore`를 추가했다.

- `.env`, Git, IDE 설정
- `.venv`, `node_modules`, Python Cache
- Frontend Build 결과
- 운영 Backend Image에 사용하지 않는 문서·테스트·Script
- 이번 Docker Image에서 사용하지 않는 AI RAG/Evaluation 소스

적용 후 Build Context는 약 301KB로 감소했다.

Docker Build 결과:

```text
thegpt-llm-integration-check:latest
Build 성공
```

이미지 내부 `import ai.llm`과 Gemini Provider Import도 성공했다.

### Backend 전체 Docker Import 잔여 문제

이미지에서 `import app.main`을 실행하면 LLM이 아니라 Admin OCR Import 과정에서 다음
오류가 발생한다.

```text
ImportError: libGL.so.1: cannot open shared object file
```

원인은 PaddleOCR 의존성이 함께 설치한 OpenCV Runtime이 `python:3.11-slim`에 없는
시스템 `libGL`을 요구하기 때문이다. LLM Core Import는 정상이며 이번 LLM 이관에서
OCR 시스템 패키지를 추가하지 않았다. Backend Docker 기동 전 별도 OCR Docker Runtime
수정이 필요하다.

## 18. 남은 위험과 후속 작업

### 실제 Provider Smoke Test

Ollama/Gemini/MedGemma는 Fake 또는 Mock Transport로 계약을 검증했다. 배포 환경별
실제 모델명, 할당량, SDK 응답과 GPU 메모리는 별도 Smoke Test가 필요하다.

### MedGemma Worker 분리

현재 Provider는 `asyncio.to_thread()`와 동시 실행 1로 Backend Event Loop와 Adapter를
보호한다. 실제 다중 사용자 서비스에서는 GPU Worker/Queue 분리를 후속 검토한다.

### Mock 운영 노출 정책

Admin Mock 네 개를 회귀 호환 목적으로 유지했다. 운영 Admin에서 숨길지 여부는 환경별
정책을 정한 뒤 Registry 조립 단계에서 처리한다.

### 의료 데이터 외부 전송

Gemini에 실제 의료·개인정보를 보내기 전에 동의, 비식별화, 로그, 보관 정책을 확정해야
한다.

### Docker OCR 시스템 의존성

Backend Docker Image Build는 성공하지만 `app.main` 전체 Import는 OpenCV
`libGL.so.1` 누락으로 실패한다. OCR Docker Runtime 수정 작업으로 별도 처리한다.

## 19. 코드 읽기 순서

```text
1. ai/llm/contracts.py
→ 2. ai/llm/registry.py
→ 3. ai/llm/application.py
→ 4. ai/llm/providers/ollama.py
→ 5. ai/llm/providers/gemini.py
→ 6. ai/llm/providers/medgemma.py
→ 7. ai/llm/engine.py
→ 8. backend/app/services/admin_llm.py
→ 9. backend/app/services/llm_service.py
→ 10. Backend Router와 Schema
```

먼저 공통 계약과 중심 Service를 읽고, Provider 구현을 확인한 뒤 두 Backend Adapter가
각 API 계약으로 변환하는 과정을 확인하면 된다.

## 20. 최종 상태 요약

```text
두 LLM 실행 계통
→ 하나의 ai/llm Domain 계약
→ 하나의 Application Service
→ 하나의 Model/Provider Registry 구현
→ 네 Provider 구현
→ 두 Backend API Adapter로 호환 유지
```

LLM 실행 코어는 Backend Framework에서 분리되었고, CPU API Provider와 GPU MedGemma
의존성도 목적별로 나뉘었다. 실제 외부 Runtime 검증과 Docker OCR 시스템 라이브러리
문제는 후속 작업으로 남는다.
