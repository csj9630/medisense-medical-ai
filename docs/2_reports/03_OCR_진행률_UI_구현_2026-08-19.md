# OCR 진행률 UI 구현

- 작업일: 2026-08-19
- 작업 영역: Backend / FastAPI, Frontend / React
- 선행 구현: `docs/07_Hybrid_OCR_구현_2026-08-19.md`
- 대상 기능: 관리자 OCR 분석의 전체 진행 단계와 퍼센트 표시
- 제외 범위: 영구 Job 저장소, 분산 Worker, 서버 측 작업 취소, PaddleOCR 내부 추론률 측정

## 1. 작업 목적

기존 OCR API는 하나의 HTTP 요청이 전체 분석을 끝낼 때까지 응답하지 않는 동기형 구조였다.
Frontend는 분석 중이라는 회전 아이콘만 표시했기 때문에 파일 검증, PDF 페이지 처리, 텍스트 정제, Chunk 생성 중 어느 단계인지 확인할 수 없었다.

이번 작업에서는 기존 동기 API를 호환용으로 유지하면서 다음 비동기 조회 흐름을 추가했다.

```text
관리자 파일 선택
→ OCR Job 생성 및 jobId 수신
→ Backend 백그라운드 처리 시작
→ Frontend가 Job 상태를 주기적으로 조회
← 현재 stage, progress, message 수신
→ 진행 막대와 퍼센트 갱신
→ 완료 시 기존 OCR 결과 화면 표시
```

## 2. 변경 전후 비교

### 핵심 차이 요약

| 비교 항목 | 이전 동기식 방식 | 현재 Job 방식 |
|---|---|---|
| 요청 방식 | 분석 API를 한 번 호출 | Job 생성 후 상태 API를 반복 조회 |
| 최초 응답 | OCR이 모두 끝난 뒤 결과 반환 | `202 Accepted`와 `jobId`를 즉시 반환 |
| HTTP 연결 | 전체 분석 시간 동안 한 요청을 유지 | 생성 요청은 바로 종료하고 짧은 조회 요청을 사용 |
| UI 표시 | 회전 아이콘과 고정 문구 | 현재 단계, 안내 문구, 0~100% 진행률 표시 |
| 완료 결과 | 분석 API 응답 본문으로 전달 | 완료된 Job의 `result`로 전달 |
| 오류 전달 | 분석 API가 즉시 HTTP 오류 반환 | Job 상태를 `failed`로 바꾸고 `error`에 저장 |
| 긴 작업 대응 | Proxy·브라우저 요청 시간 초과 가능성이 큼 | polling이므로 단일 요청 시간 초과 부담이 작음 |
| 구현 복잡도 | 구조가 단순함 | Job 상태·만료·polling 관리가 추가됨 |

두 방식 모두 실제 문서 검증, Hybrid OCR, 텍스트 정제, Chunk 생성에는 같은
`DocumentProcessingService.process_document()`를 사용한다. 즉, OCR 처리 내용이 바뀐 것이 아니라
Frontend에 처리 상태와 결과를 전달하는 방식이 동기 응답에서 Job 조회 방식으로 바뀌었다.

### 변경 전

```text
POST /api/admin/ocr/analyze
→ 요청 연결을 유지한 채 전체 OCR 실행
← 최종 결과 한 번만 반환

UI: 회전 아이콘 + 고정 안내 문구
```

### 변경 후

```text
POST /api/admin/ocr/jobs
← 202 Accepted + jobId

GET /api/admin/ocr/jobs/{jobId} 반복
← queued | processing | completed | failed
← stage + progress + message

completed
← progress 100 + 기존 OcrDocumentResponse
```

기존 `POST /api/admin/ocr/analyze`는 다른 호출부의 호환성을 위해 삭제하지 않았다.
관리자 OCR 화면만 새 Job API를 사용한다.

## 3. 전체 호출 순서

중심 Backend 흐름은 `OcrJobManager`와 `DocumentProcessingService.process_document()`에서 확인할 수 있다.

```text
OcrPanel
→ useOcrTest.analyze()
→ apiAdminAiService.analyzeDocument()

→ POST /admin/ocr/jobs
→ OcrJobManager.create_job()
  → 요청 종료 전에 UploadFile byte 복사
  → asyncio Task 생성
← jobId

Frontend polling
→ GET /admin/ocr/jobs/{jobId}
→ OcrJobManager.get_job()
← 현재 Job 상태

Backend Task
→ DocumentProcessingService.process_document()
  → validate_document()
  → asyncio.to_thread(_extract_document)
    → 이미지 전처리 또는 PDF 페이지별 분석/OCR
  → clean_document_text()
  → create_chunks()
  → OcrDocumentResponse 구성
← 완료 결과를 Job에 저장

Frontend
→ completed 확인
→ polling 종료
→ 기존 OcrResultSummary 결과 화면 표시
```

OCR/PDF 추출은 CPU 사용량이 크고 동기 라이브러리를 호출하므로 `asyncio.to_thread()`에서 수행한다.
따라서 단일 Uvicorn 프로세스에서도 OCR 추출 도중 상태 조회 요청을 받을 수 있다.

## 4. 진행률 산정 기준

진행률은 실제 처리 단계와 PDF 처리 완료 페이지 수를 기반으로 하는 단계형 추정치다.
처리 시간의 정확한 비율은 아니다.

| 진행률 | stage | 의미 |
|---:|---|---|
| 0% | `uploading` | 브라우저가 파일 업로드를 시작함 |
| 3% | `queued` | Backend Job 등록 완료 |
| 5% | `uploading` | Backend가 업로드 byte 복사 완료 |
| 8~15% | `validating` | 파일, MIME, 확장자, 크기, PDF 페이지, Chunk 설정 검증 |
| 20~25% | `analyzing` | 문서 유형 및 PDF 페이지 구조 분석 |
| 25~80% | `extracting` | PDF 전체 페이지 수 대비 현재 완료 페이지를 반영 |
| 28% | `preprocessing` | 단일 이미지 방향·크기·배경 전처리 |
| 35% 또는 현재 페이지 지점 | `loading_model` | PaddleOCR 모델 준비 및 OCR 호출 |
| 80~82% | `extracting`, `merging` | 추출 완료 및 페이지 결과 통합 |
| 86~90% | `cleaning` | 텍스트 공백과 제어문자 정제 |
| 93~97% | `chunking` | RAG 검토용 Chunk 생성 |
| 99% | `finalizing` | 응답 모델 구성 |
| 100% | `completed` | Job 결과 저장 및 분석 완료 |

PDF 진행률은 아래 구간에서 페이지 완료 비율로 계산한다.

```text
25 + round((완료 페이지 수 / 전체 페이지 수) × 55)
```

PaddleOCR 라이브러리는 한 번의 이미지 추론 내부 진행률을 제공하지 않는다.
따라서 스캔 페이지 한 장을 처리하는 동안에는 해당 페이지 시작 지점의 `loading_model` 값이 유지되고, 추론이 끝나면 페이지 완료 값으로 이동한다.

## 5. Backend 구현

### 5.1 Job API

#### Job 생성

```http
POST /api/admin/ocr/jobs
Content-Type: multipart/form-data
```

요청 필드:

| 필드 | 형식 | 설명 |
|---|---|---|
| `file` | File | PDF, PNG, JPG/JPEG |
| `chunkSize` | integer | 100~4096, 기본 512 |
| `overlap` | integer | 기본 50, `chunkSize`보다 작아야 함 |

응답:

```json
{
  "jobId": "7b2c...",
  "status": "queued"
}
```

- 정상 등록: `202 Accepted`
- 최대 파일 크기 초과: `413 Content Too Large`
- 동시 대기·처리 Job 초과: `429 Too Many Requests`

#### Job 상태 조회

```http
GET /api/admin/ocr/jobs/{jobId}
```

처리 중 응답 예시:

```json
{
  "jobId": "7b2c...",
  "status": "processing",
  "stage": "extracting",
  "progress": 58,
  "message": "PDF 3/6페이지 처리를 완료했습니다.",
  "result": null,
  "error": null
}
```

완료 시 `status`는 `completed`, `progress`는 100이고 `result`에 기존 `OcrDocumentResponse`가 들어간다.
검증 또는 처리 실패 시 HTTP polling 자체는 성공하며 `status: failed`와 사용자에게 표시할 `error`를 반환한다.
없거나 만료된 Job ID는 `404 Not Found`이다.

### 5.2 Job 보관과 보호 장치

- 업로드 요청이 종료되면 원본 `UploadFile`이 닫히므로 Job 생성 시 파일 내용을 byte로 복사한다.
- 활성 Job 수는 기본 5개로 제한한다.
- 완료·실패 Job은 기본 60분 뒤 다음 생성/조회 시 메모리에서 제거한다.
- Job 상태는 여러 thread에서 갱신될 수 있어 `RLock`으로 보호한다.
- PaddleOCR pipeline의 동시 `predict()` 호출은 별도 Lock으로 직렬화한다.
- 사용자에게 내부 예외와 stack trace를 반환하지 않고 도메인 오류 메시지만 Job에 저장한다.

환경 설정:

```dotenv
OCR_JOB_TTL_MINUTES=60
OCR_MAX_PENDING_JOBS=5
```

## 6. Frontend 구현

`apiAdminAiService.analyzeDocument()`는 Job 생성 후 700ms 간격으로 상태를 조회한다.
각 응답의 `stage`, `progress`, `message`를 callback으로 `useOcrTest`에 전달한다.

`OcrResultSummary`는 분석 중 다음 정보를 표시한다.

- 현재 처리 메시지
- 0~100 정수 퍼센트
- 진행 막대
- 스크린 리더용 `role="progressbar"`, `aria-valuenow`

화면이 unmount되거나 선택 파일이 변경되면 `AbortController`로 업로드/상태 조회 요청과 polling 타이머를 중단한다.
단, 이는 브라우저의 조회만 중단하며 이미 생성된 Backend OCR Job 자체는 계속 처리된다.

## 9. 운영 전 확인할 제한 사항

현재 Job 저장소는 단일 FastAPI 프로세스의 메모리다.

- 서버 재시작 시 모든 Job 상태와 결과가 사라진다.
- 여러 Uvicorn worker 또는 여러 서버 인스턴스를 사용하면 Job 생성 요청과 조회 요청이 서로 다른 프로세스로 전달되어 404가 발생할 수 있다.
- 운영에서 다중 worker를 사용하려면 Redis 같은 공유 Job 저장소와 Celery/RQ/Arq 같은 Worker queue로 교체해야 한다.
- 파일 byte와 완료 결과를 TTL 동안 메모리에 보관하므로 파일 크기, 활성 Job 수, TTL을 서버 메모리에 맞게 조정해야 한다.
- 현재 Frontend 중단은 polling만 취소한다. 서버 OCR 작업까지 취소하려면 `DELETE /ocr/jobs/{jobId}`와 단계별 취소 신호가 별도로 필요하다.
- 진행률은 단계·페이지 기반 추정치이며 남은 시간을 의미하지 않는다.

따라서 현재 구현은 로컬 개발 또는 단일 프로세스 관리자 도구에 적합하고, 분산 운영 전에는 공유 저장소 기반 Job 구조로 확장해야 한다.
