# 관리자 OCR·LLM 페이지 구현

- 작업일: 2026-08-17
- 대상 경로: `/admin`
- 작업 범위: React 프론트엔드 UI, mock service, 컴포넌트 아키텍처
- 제외 범위: FastAPI, 실제 파일 업로드, OCR/LLM/RAG/Embedding/VectorDB 연동

## 1. 작업 목적

관리자가 RAG용 문서의 OCR 준비 상태를 시험하고, 동일한 질문에 대한 여러 LLM의 mock 응답을 비교할 수 있는 프론트엔드 화면을 구현했다. 실제 AI나 백엔드를 호출하지 않으면서 입력, 비동기 상태, 결과, 오류 사용자 경험을 검증할 수 있도록 구성했다.

후속 작업으로 최초 구현을 컴포넌트 아키텍처 가이드에 맞춰 리팩터링했다. 페이지, 패널, 입력/결과 컴포넌트, 상태 hook, service 계약, mock 구현과 fixture의 책임을 분리해 실제 API로 교체할 때 UI 변경을 최소화했다.

## 2. 구현한 사용자 흐름

### OCR 탭

1. PDF, PNG, JPG 파일을 버튼이나 drag & drop으로 선택한다.
2. 파일명, 크기, MIME 형식을 확인하거나 선택을 제거한다.
3. `문서 분석 테스트`를 실행하면 loading 상태 후 mock OCR 결과가 표시된다.
4. 페이지 수, 추출 문자 수, 예상 chunk 수, 인식 신뢰도를 확인한다.
5. 추출 텍스트, chunk 미리보기, RAG 등록 준비 badge와 품질 메모를 검토한다.
6. `VectorDB 저장 테스트` 실행 후 실제 저장되지 않았다는 완료 메시지를 확인한다.

지원하지 않는 확장자는 사용자 가까이에 오류 메시지를 표시한다. 파일의 실제 본문은 읽거나 전송하지 않는다.

### LLM 탭

1. 공통 질문을 입력하고 필요하면 참고 문서를 선택한다.
2. 기존 프로젝트의 MedGemma, Gemma, Qwen, Llama 모델 중 2개 이상을 고른다.
3. Chunk Size와 Overlap mock 옵션을 설정한다.
4. 비교를 실행하면 모델별 loading card 후 결과가 반응형 grid로 표시된다.
5. 답변, 응답 시간, 입출력 token 수, chunk 설정을 비교하고 답변을 복사한다.

Llama는 부분 오류 UI를 확인하기 위한 의도적인 실패 fixture다. 모든 입력을 초기화할 수 있으며, 탭 전환 시 두 panel을 마운트 상태로 유지해 입력과 결과가 보존된다.

## 3. 화면과 접근성

- 기존 `MainLayout`과 `/admin` route를 유지했다.
- 밝은 관리자 도구 분위기와 청록색 강조색을 적용했다.
- 기존 root `.dark` class에 대응하는 다크 테마 색상을 제공한다.
- 데스크톱, 태블릿, 모바일 구간에 맞춰 OCR columns와 LLM result grid가 재배치된다.
- `tablist`/`tab`/`tabpanel`, `aria-selected`, `aria-controls` 관계를 적용했다.
- 좌우 방향키, Home, End 키로 탭을 전환할 수 있다.
- 모든 form input에 접근 가능한 label을 제공한다.
- icon-only 제거 버튼에 `aria-label`을 제공한다.
- loading/result 영역에 `aria-live`, `aria-busy`를 사용한다.
- 성공/오류는 색상뿐 아니라 icon과 문구로 함께 표현한다.
- `:focus-visible` outline과 reduced-motion 대응을 유지한다.

## 5. 책임 분리

| 계층 | 책임 |
|---|---|
| `AdminPage` | 페이지 조립과 활성 탭 상태 |
| `AdminHeader`, `AdminTabs` | 상단 정보와 접근 가능한 탭 탐색 |
| `OcrPanel`, `LlmPanel` | 기능별 hook과 표현 컴포넌트 조립 |
| 입력 컴포넌트 | controlled input, 파일 선택, 사용자 이벤트 전달 |
| 결과 컴포넌트 | 빈 상태, loading, 성공, 부분 오류와 결과 표현 |
| `useOcrTest` | OCR 입력, async 상태, 오류, 분석/저장 실행 |
| `useLlmComparison` | 질문·모델·옵션, validation, 비교 상태와 초기화 |
| `AdminAiService` | UI가 의존하는 OCR/저장/LLM 호출 계약 |
| `mockAdminAiService` | 지연, 지원 형식 검사, mock 결과 조립 |
| `mocks` | 고정 OCR/LLM fixture 데이터 |
| `types`, `constants` | 요청·응답 계약과 고정 UI 옵션 |

## 6. 데이터 흐름

```text
AdminPage
├─ OcrPanel → useOcrTest → adminAiService → mockAdminAiService → ocrMockData
└─ LlmPanel → useLlmComparison → adminAiService → mockAdminAiService → llmMockData
```

데이터는 panel에서 표현 컴포넌트로 전달되고 사용자 이벤트는 callback을 통해 hook으로 돌아간다. UI 컴포넌트는 fixture와 timeout을 직접 import하거나 실행하지 않는다.

## 7. Mock 처리 원칙

- `window.setTimeout` 기반의 비동기 지연은 `mockAdminAiService.ts`에만 존재한다.
- OCR mock은 파일 확장자와 파일명만 사용한다.
- LLM mock은 prompt 길이와 선택 모델 ID를 사용해 고정 지표와 답변을 조립한다.
- mock 저장은 완료 메시지만 반환하며 DB에 접근하지 않는다.
- 관리자 feature 내부에 `fetch`, `apiClient`, Axios 또는 `/api/` 참조가 없다.
- 요청·응답과 상태 타입에 TypeScript `any`를 사용하지 않는다.

## 10. 실제 API 연동 시 교체 지점

`frontend/src/features/admin/services/adminAiService.ts`의 아래 binding이 단일 교체 지점이다.

```ts
export const adminAiService: AdminAiService = mockAdminAiService;
```

실제 연동 단계에서는 `AdminAiService` 계약을 구현하는 API service를 만들고 위 binding을 교체한다. 그 전까지 다음 항목은 구현되지 않은 상태다.

- 실제 파일 업로드와 OCR
- 실제 LLM/Ollama/provider 호출
- chunking과 embedding 생성
- RAG 검색 및 답변 생성
- VectorDB 저장/조회
- FastAPI 관리자 endpoint
- 관리자 인증/권한 guard

## 11. 이후 작업 시 주의사항

1. 실제 backend 계약이 확정되기 전 types를 과도하게 확장하지 않는다.
2. API service가 `File` 업로드와 JSON 요청의 전송 형식을 책임지게 하고 UI 컴포넌트에는 network 로직을 넣지 않는다.
3. Llama 부분 오류 fixture는 실제 API 전환 시 mock service와 함께 제거한다.
4. `/admin`은 현재 공개 route이므로 실제 관리 기능 연결 전에 권한 guard를 별도로 설계한다.
5. 실제 파일을 취급할 때는 확장자뿐 아니라 서버 MIME/크기/보안 검증을 추가한다.
