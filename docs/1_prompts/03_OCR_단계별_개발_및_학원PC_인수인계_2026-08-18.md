# OCR 단계별 개발 및 학원 PC 인수인계

- 작성일: 2026-08-18
- 기준 저장소: `https://github.com/ThedaolOCR3/thegpt-project.git`
- 기준 브랜치: `csj_admin`
- 권장 실습 브랜치: `codex/ocr-learning-lab`
- 이 문서 작성 시점에는 실제 PDF 추출, PaddleOCR, Chunking, Embedding을 구현하지 않았다.

## 1. 이 문서의 목적

이 문서는 학원 PC에서 OCR 기능을 한꺼번에 생성하지 않고, 작은 단계별로 구현하고
각 단계의 흐름을 이해한 뒤 다음 단계로 넘어가기 위한 인수인계 문서다.

이번 작업에서 가장 중요한 원칙은 다음과 같다.

1. 기존 Mock 기능을 보존한다.
2. 한 번에 한 단계만 구현한다.
3. 구현이 끝나도 자동으로 다음 단계에 들어가지 않는다.
4. 각 단계의 요청 흐름과 파일별 책임을 설명할 수 있어야 다음 단계로 넘어간다.
5. OCR은 전체 RAG 시스템의 첫 번째 입력 단계일 뿐이므로 과도하게 확장하지 않는다.

전체 목표는 다음 세 구간으로 나뉜다.

```text
문서 → 텍스트 추출
텍스트 → Chunk + Embedding + VectorDB
질문 → 유사 문서 검색 → LLM 답변
```

현재 작업 범위는 첫 번째 구간 중에서도 PDF 네이티브 텍스트 추출과 최소 PaddleOCR
연동까지만이다.

## 2. 현재 프로젝트 상태

### 2.1 기존 Admin Mock 흐름

현재 관리자 OCR 화면은 실제 파일 본문을 전송하지 않고 파일명, 크기, Content Type,
Chunk Size, Overlap을 JSON으로 전송한다.

```text
OcrPanel
→ useOcrTest
→ apiAdminAiService
→ POST /api/admin/ocr/analyze
→ backend/app/api/admin/router.py
→ backend/app/services/admin_ocr.py
→ 고정 Mock 결과 반환
```

기존 주요 API는 다음과 같다.

```text
POST /api/admin/ocr/analyze
POST /api/admin/ocr/vector-save-test
POST /api/admin/llm/compare
```

### 2.2 반드시 보존할 항목

1단계에서는 다음 항목을 제거하거나 실제 구현으로 교체하지 않는다.

- `backend/app/services/admin_ocr.py`
- `POST /api/admin/ocr/analyze`
- `POST /api/admin/ocr/vector-save-test`
- 기존 `OcrAnalyzeRequest`, `OcrDocumentResponse`
- 기존 OCR Mock 화면
- 기존 LLM Mock 화면과 서비스

실제 PDF 추출은 별도 경로로 추가한다.

```text
기존 Mock
POST /api/admin/ocr/analyze
JSON 메타데이터
→ admin_ocr.py

신규 실제 추출
POST /api/admin/documents/extract-text
multipart PDF 파일
→ document_extraction.py
```

두 기능은 URL, 요청 형식, 응답 Schema가 다르므로 동시에 유지할 수 있다.

### 2.3 현재 확인된 환경

- Git 원격 저장소 `origin`이 연결되어 있다.
- 기준 브랜치는 `csj_admin`이다.
- `.env`, `backend/.venv`, `frontend/node_modules`는 Git에서 제외된다.
- 최상위 `.env.example`, `frontend/.env.example`이 존재한다.
- `frontend/package-lock.json`이 존재한다.
- `python-multipart`는 이미 Backend 의존성에 포함되어 있다.
- PyMuPDF와 PaddleOCR은 현재 `backend/requirements.txt`에 없다.

## 3. 학원 PC 준비

### 3.1 저장소 받기

```powershell
git clone https://github.com/ThedaolOCR3/thegpt-project.git
cd thegpt-project
git switch csj_admin
git pull --ff-only origin csj_admin
```

GitHub 조직 저장소를 읽을 수 있는 계정으로 인증해야 한다.

### 3.2 실습 브랜치 만들기

기준 브랜치에서 OCR 실습 전용 브랜치를 만든다.

```powershell
git switch -c codex/ocr-learning-lab
git push -u origin codex/ocr-learning-lab
```

이미 원격 브랜치가 만들어져 있다면 새로 생성하지 않고 다음처럼 받는다.

```powershell
git fetch origin
git switch --track origin/codex/ocr-learning-lab
```

OCR 실습 중에는 `csj_admin`을 직접 수정하지 않는다. 각 단계가 이해되고 검증된 뒤에만
병합 여부를 결정한다.

### 3.3 Backend 설치

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 3.4 Frontend 설치

```powershell
cd ..\frontend
npm.cmd ci
```

### 3.5 환경변수 주의

- `.env`는 Git에 올리지 않는다.
- 공용 PC에는 운영 DB, API Key, JWT Secret을 저장하지 않는다.
- 실제 의료 문서나 개인정보가 포함된 파일을 테스트 자료로 사용하지 않는다.
- 1단계는 DB 저장 없이 메모리에서 PDF를 읽고 응답하는 구조를 우선한다.
- 공용 PC 사용 후에는 ChatGPT, GitHub에서 로그아웃하고 로컬 `.env`를 제거한다.


설명이 이 문서와 일치하는 것을 확인한 후에만 해당 단계 구현을 승인한다.

## 5. 단계별 구현 계획

## 5.1 단계 1-A: Backend PDF 네이티브 텍스트 추출

### 목표

PaddleOCR 없이 실제 PDF 파일을 업로드하고, PyMuPDF로 페이지별 네이티브 텍스트를
직접 추출한다. 텍스트가 없는 페이지는 OCR하지 않고 `empty`로 표시한다.

### 예상 흐름

```text
Swagger 또는 별도 API Client
→ multipart PDF 업로드
→ POST /api/admin/documents/extract-text
→ 파일명·크기·PDF signature 검증
→ PyMuPDF로 PDF 열기
→ 암호화·손상·빈 PDF 검증
→ 페이지별 네이티브 텍스트 추출
→ 페이지 번호순 전체 텍스트 조립
→ native/empty 페이지 결과 반환
```

### 예상 신규 파일

```text
backend/app/api/admin/document_extraction_router.py
backend/app/schemas/document_extraction.py
backend/app/services/document_extraction.py
backend/tests/test_document_extraction.py
```

### 예상 수정 파일

```text
backend/app/api/admin/router.py
backend/requirements.txt
```

`admin/router.py` 수정은 신규 하위 Router를 등록하는 범위로 제한한다.
`admin_ocr.py`는 수정하지 않는다.

### 신규 응답 예시

```json
{
  "documentName": "sample.pdf",
  "pageCount": 2,
  "pages": [
    {
      "pageNumber": 1,
      "source": "native",
      "text": "PDF에서 직접 추출한 텍스트"
    },
    {
      "pageNumber": 2,
      "source": "empty",
      "text": ""
    }
  ],
  "extractedText": "PDF에서 직접 추출한 텍스트",
  "warnings": [
    "2페이지에 추출 가능한 네이티브 텍스트가 없습니다."
  ]
}
```

### 하지 않을 작업

- PaddleOCR 설치 또는 실행
- PNG/JPG 처리
- PDF 페이지 이미지 렌더링
- 이미지 전처리
- DB 저장
- Chunking
- Embedding
- VectorDB 저장
- 기존 Admin Mock UI 교체

### 검증 기준

- 디지털 PDF의 페이지 수가 정확하다.
- 페이지별 텍스트가 페이지 번호순으로 반환된다.
- 텍스트가 없는 페이지는 `empty`가 된다.
- 손상되거나 암호화된 PDF는 이해할 수 있는 오류를 반환한다.
- PDF가 아닌 파일은 거부한다.
- 기존 `/api/admin/ocr/analyze` Mock 응답은 그대로 동작한다.
- DB에 아무것도 저장하지 않는다.

### 이 단계의 Codex 구현 요청문

```text
docs/05_OCR_단계별_개발_및_학원PC_인수인계_2026-08-18.md의 5.1 단계만 구현해줘.
기존 backend/app/services/admin_ocr.py와 기존 Mock API 계약은 변경하지 마.
신규 POST /api/admin/documents/extract-text에서 PDF 네이티브 텍스트만 추출해줘.
PaddleOCR, 이미지 렌더링, DB, Chunking, Embedding은 구현하지 마.

구현 후 자동으로 다음 단계에 들어가지 말고 다음을 설명해줘.
1. 수정한 파일별 역할
2. 업로드 요청이 통과하는 함수 순서
3. native와 empty를 결정하는 위치
4. 파일 검증과 오류 처리 위치
5. 실행한 검증과 실행하지 못한 검증
6. 내가 발표에서 받을 수 있는 질문 5개
```

### 중단 지점

단계 1-A 완료 후 바로 Frontend나 PaddleOCR을 구현하지 않는다. 먼저 코드와 Swagger
응답을 확인하고 다음 질문에 직접 답할 수 있어야 한다.

- 기존 Mock API와 신규 실제 API는 왜 분리했는가?
- 브라우저 또는 Swagger의 파일은 FastAPI에서 어떤 타입으로 받는가?
- PDF 검증은 어느 계층에서 수행하는가?
- PyMuPDF는 페이지별 텍스트를 어디에서 추출하는가?
- `native`와 `empty`는 무엇을 의미하는가?

## 5.2 단계 1-B: 실제 추출용 Frontend 연결

### 선행 조건

단계 1-A의 Backend 흐름을 설명할 수 있고 Backend 테스트가 통과해야 한다.

### 목표

기존 Mock 버튼을 보존하면서 별도의 “PDF 직접 추출 테스트” 기능을 추가한다.

### 권장 흐름

```text
PDF 선택
→ FormData 생성
→ POST /api/admin/documents/extract-text
→ 페이지별 native/empty 결과 표시
→ 전체 추출 텍스트 표시
```

### 구현 원칙

- 기존 `apiAdminAiService.analyzeDocument()`의 Mock 호출을 교체하지 않는다.
- 기존 Mock 버튼과 실제 추출 버튼을 명확히 구분한다.
- `FormData` 요청에는 브라우저가 boundary를 만들도록 `Content-Type`을 직접 지정하지 않는다.
- 공통 `apiClient.ts`를 크게 수정하기보다 독립된 업로드 API 함수를 우선 검토한다.
- Chunk 수, VectorDB 저장, readiness 같은 미구현 정보를 실제 결과처럼 표시하지 않는다.

### 예상 신규 파일

```text
frontend/src/features/admin/services/documentExtractionApi.ts
frontend/src/features/admin/types/documentExtraction.ts
```

UI 파일은 기존 구조를 확인한 뒤 최소 범위로 추가한다.

### 중단 지점

- 브라우저 Network 탭에서 multipart 요청을 확인한다.
- 기존 Mock 버튼이 여전히 기존 endpoint를 호출하는지 확인한다.
- 실제 버튼이 신규 endpoint만 호출하는지 확인한다.
- 이후 PaddleOCR로 자동 진행하지 않는다.

## 5.3 단계 2-A: 일반 이미지에 PaddleOCR 적용

### 선행 조건

단계 1-B까지의 요청 흐름을 설명할 수 있어야 한다.

### 목표

PNG/JPG 한 장을 최소 정규화한 뒤 PaddleOCR 하나로 처리한다.

```text
이미지 업로드
→ 실제 이미지 형식 검증
→ EXIF 방향 보정
→ 투명 배경을 흰색으로 합성
→ 안전한 최대 해상도로 제한
→ PaddleOCR
→ bbox 기준 줄 정렬
→ 텍스트와 confidence 반환
```

### 구현 원칙

- Paddle 모델은 요청마다 만들지 않고 프로세스에서 재사용한다.
- EasyOCR, Tesseract는 추가하지 않는다.
- 첫 실행에는 deskew, CLAHE, 원근 보정, 여러 후보 비교를 넣지 않는다.
- Unit Test에서는 Paddle을 Mock 처리하고, 실제 모델 검증은 별도 Integration Test로 구분한다.
- 모델 다운로드와 실제 OCR 실행 전에는 사용자 승인을 다시 받는다.

### 중단 지점

- Paddle 모델의 초기화 위치를 설명한다.
- 한 요청이 이미지 검증부터 결과 조립까지 통과하는 순서를 설명한다.
- 실제 실패 이미지가 확인되기 전에는 전처리 기능을 추가하지 않는다.

## 5.4 단계 2-B: 스캔 PDF 페이지만 PaddleOCR 처리

### 선행 조건

단계 1-A의 PDF 추출과 단계 2-A의 이미지 OCR이 각각 독립적으로 동작해야 한다.

### 목표

PDF에서 유효한 네이티브 텍스트가 없는 페이지만 이미지로 렌더링하여 단계 2-A의
Paddle 엔진으로 전달한다.

```text
PDF 페이지
→ 네이티브 텍스트 추출
→ 유효 텍스트 존재: native 채택
→ 유효 텍스트 없음: 페이지 렌더링 → PaddleOCR → ocr 채택
→ 페이지 번호순 병합
```

### 페이지 source

```text
native  PDF 텍스트 레이어에서 직접 추출
ocr     페이지 렌더링 후 PaddleOCR로 추출
empty   양쪽 모두 텍스트 없음
error   해당 페이지 처리 실패
```

### 구현 원칙

- 문서 전체가 아니라 페이지별로 native/OCR을 판단한다.
- 한 페이지가 실패해도 나머지 페이지 결과는 유지한다.
- 처음에는 네이티브 텍스트가 존재하는 혼합 페이지의 이미지 영역까지 OCR하지 않는다.
- PDF 내 이미지 영역 OCR과 복잡한 bbox 병합은 실제 요구가 확인된 뒤 별도 단계로 둔다.

### 중단 지점

- 디지털 PDF에서 Paddle 호출이 0회인지 확인한다.
- 스캔 2페이지 PDF에서 Paddle 호출이 2회인지 확인한다.
- 디지털 1페이지와 스캔 1페이지가 섞인 PDF에서 Paddle 호출이 1회인지 확인한다.
- 페이지 순서가 유지되는지 확인한다.

## 5.5 단계 2-C: 실패 사례 기반 전처리

이 단계는 기본 OCR에서 실제 실패 사례가 수집된 경우에만 진행한다.

후보 기능:

- 문서 방향 분류
- 기울기 보정
- 원근 또는 왜곡 보정
- 대비 개선
- 저신뢰도 재시도

처음부터 전부 적용하지 않는다. 하나의 실패 원인과 하나의 전처리를 대응시키고,
전처리 전후 결과와 처리 시간을 비교한다. 재시도 결과를 무조건 채택하지 않고 1차
결과와 품질을 비교한다.

## 6. OCR 이후의 후속 로드맵

다음 항목은 OCR 단계가 이해되고 안정화되기 전에는 구현하지 않는다.

### 단계 3: Chunking

- 페이지 경계를 보존한다.
- Chunk Size와 Overlap을 실제 함수 입력으로 사용한다.
- Chunk에 `document_id`, `chunk_index`, 페이지 범위를 기록한다.

### 단계 4: Embedding과 VectorDB

- Embedding 모델 하나만 선택한다.
- 임베딩 차원과 DB의 `VECTOR(1024)` 호환성을 확인한다.
- 동일 파일 해시를 이용해 중복 저장을 방지한다.

### 단계 5: 검색

- 질문을 같은 Embedding 모델로 변환한다.
- pgvector에서 top-k Chunk를 검색한다.
- 검색 결과의 문서명과 페이지를 함께 반환한다.

### 단계 6: LLM 답변

- 검색된 Chunk만 Context로 전달한다.
- 답변과 함께 근거 문서와 페이지를 표시한다.
- 검색 결과가 부족할 때 추측하지 않도록 프롬프트 정책을 둔다.

## 7. 단계별 Git 기록 방법

한 단계가 끝날 때마다 관련 파일만 명시적으로 추가한다. `git add .`는 피한다.

예시:

```powershell
git status --short
git diff
git add backend/app/api/admin/document_extraction_router.py
git add backend/app/schemas/document_extraction.py
git add backend/app/services/document_extraction.py
git add backend/app/api/admin/router.py
git add backend/requirements.txt
git add backend/tests/test_document_extraction.py
git commit -m "feat: add native PDF text extraction"
git push
```

권장 단계별 커밋 예시:

```text
feat: add native PDF text extraction
feat: connect native PDF extraction UI
feat: add Paddle OCR for images
feat: OCR scanned PDF pages only
test: add OCR document routing cases
```

각 커밋에는 한 단계만 포함한다. 오류가 생기면 어떤 단계에서 생겼는지 추적하기 쉽다.
