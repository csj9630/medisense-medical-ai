## 1. 작업 배경

현재 프로젝트에는 실제로 동작하는 OCR 경로가 두 개 있다.

### 경로 A: 서비스 문서 미리보기

```text
POST /api/documents/ocr
→ backend/app/api/documents/router.py
→ ai.ocr.run_ocr()
→ ai/ocr/pipeline.py
→ ai/ocr/preprocessing.py
→ PaddleOCR
→ ai/ocr/postprocessing.py
→ text + lines 반환
```

이 경로는 다음 장점이 있다.

- `ai/ocr`이라는 재사용 가능한 Package 위치
- OCR Line별 Text·Confidence·Page 보존
- 최소 Confidence 필터
- 연속 중복 Line 제거
- OpenCV 기반 Denoise와 Deskew
- 기존 `from ai.ocr import run_ocr` 공개 Import 경로

### 경로 B: Admin Hybrid OCR

```text
POST /api/admin/ocr/jobs
→ OcrJobManager
→ backend/app/services/hybrid_ocr/process_document()
→ 문서 검증
→ Image/PDF/DOCX/PPTX 형식별 추출
→ Text 정제
→ 문자 기준 Chunk 생성
→ Job 결과 반환
```

이 경로는 다음 장점이 있다.

- 확장자·MIME·Binary·크기·PDF 페이지·Office 압축 구조 검증
- Digital/Scanned/Hybrid PDF 분기
- DOCX/PPTX Text 직접 추출과 포함 Image OCR
- PIL EXIF 방향·투명 배경·Pixel 제한 처리
- PaddleOCR 초기화 Lock과 추론 Lock
- Box 기반 읽기 순서 정렬
- Progress Callback과 세분화된 Domain 예외
- Hybrid OCR, Job, Vector Save 자동 Test

두 경로가 서로 다른 Paddle Engine과 전처리·후처리 정책을 사용하므로 같은 파일이 Endpoint에 따라 다른 결과를 만들 수 있다.

## 2. 최종 작업 목표

문서 형식 판별·검증·추출·이미지 전처리·PaddleOCR 실행·후처리를 `ai/ocr`의 단일 Framework 독립 코어로 통합한다.

목표 실행 구조는 다음과 같다.

```text

/api/admin/ocr/* ───┘                      ↓
                                      OCR 공통 결과
                                          ↓
                    ┌─────────────────────┴─────────────────────┐
                    ↓                                           ↓
             Document API 응답                         Admin Chunk/Job 응답
```

다음 의존 방향을 반드시 지킨다.

```text
Backend / Worker / Local Lab
          ↓
        ai/ocr

```

`ai/ocr`은 다음 항목을 Import하지 않아야 한다.

- `fastapi`
- `fastapi.UploadFile`
- `app.core.config`
- `app.schemas.*`
- `app.repositories.*`
- 그 밖의 `backend/app` Module

## 3. 협업 코드 보존 원칙

이번 통합은 기존 `ai/ocr` 또는 Admin `hybrid_ocr` 중 하나를 선택하는 작업이 아니다.

예상 기능 기여도는 다음과 같다.

```text
Admin Hybrid OCR 기반 기능: 약 75~80%
기존 ai/ocr 보완 기능:      약 20~25%
```

Admin Hybrid OCR의 PDF·Office·검증·동시성 구현을 주 기반으로 사용하되, 기존 `ai/ocr`의 Line 결과·Confidence·전처리 기능을 흡수한다.

다음 행동을 금지한다.

- `backend/app/services/hybrid_ocr`를 먼저 삭제한 뒤 새로 작성하기
- 기존 `ai/ocr`를 통째로 삭제하고 Hybrid 폴더를 그대로 복사하기
- 기존 Test를 삭제하거나 Assertion을 약화해 통과시키기
- 한쪽 결과가 다르다는 이유만으로 다른 쪽 기능을 조용히 제거하기
- API Response 필드를 임의로 삭제하거나 이름 변경하기
- 팀원 코드 전체를 불필요하게 Formatting하기

기존 파일을 삭제하기 전에는 반드시 다음 조건을 만족해야 한다.

1. 대응 기능이 `ai/ocr`에 구현되어 있다.
2. 새 Import 경로를 사용하는 Test가 통과한다.
3. 실행 코드에서 이전 Import가 더 이상 검색되지 않는다.
4. 공개 호환 Import가 필요하면 Wrapper가 남아 있다.
5. 삭제하거나 대체한 기능을 작업 보고서에 기록할 수 있다.

## 5. 유지해야 할 외부 계약

### 5.1 서비스 OCR API

다음 Endpoint와 인증 흐름을 유지한다.

```text
POST /api/documents/ocr
```

다음 Response 형태를 유지한다.

```json
{
  "text": "추출된 텍스트",
  "lines": [
    {
      "text": "라인 텍스트",
      "confidence": 0.95,
      "page": 0
    }
  ]
}
```

`backend/app/schemas/document.py`와 `frontend/src/api/documents.ts`의 계약을 임의로 변경하지 않는다.

### 5.2 Admin OCR API

다음 Endpoint를 유지한다.

```text
POST /api/admin/ocr/analyze
POST /api/admin/ocr/jobs
GET  /api/admin/ocr/jobs/{job_id}
POST /api/admin/ocr/vector-save
```

다음 항목을 유지한다.

- Multipart Field 이름 `file`, `chunkSize`, `overlap`
- Job 생성 시 `202 Accepted`
- Job `queued → processing → completed/failed` 상태 흐름
- Progress의 단조 증가
- 기존 `OcrDocumentResponse` JSON Field 이름
- Chunk 순서와 개수
- Vector Save가 완료된 Job 결과를 사용하는 흐름
- 기존 HTTP 오류 상태와 사용자용 오류 메시지 의미

### 5.3 Python 공개 계약

현재 Git에 없는 Local Lab 등 외부 호출자가 있을 수 있으므로 다음 Import를 바로 깨지 않는다.

```python
from ai.ocr import run_ocr
```

새 중심 함수가 `analyze_document()`라면 `run_ocr()`는 최소 한 단계의 호환 Wrapper로 유지한다. Wrapper 안에 별도 Paddle Pipeline을 다시 구현해서는 안 된다.

## 7. 공통 Domain 계약 요구사항

정확한 Class 이름은 기존 Naming과 Test에 맞춰 조정할 수 있다. 다만 다음 정보는 공통 결과에서 손실되지 않아야 한다.

```python
@dataclass(frozen=True)
class OcrDocumentInput:
    file_name: str
    content_type: str
    content: bytes


@dataclass(frozen=True)
class OcrLine:
    text: str
    confidence: float
    page: int
    box: tuple[float, ...] | None = None
    source: str = "ocr"


@dataclass(frozen=True)
class OcrDocumentResult:
    raw_text: str
    cleaned_text: str
    lines: list[OcrLine]
    page_count: int | None
    document_type: str
    ocr_image_count: int
    average_confidence: float
    warnings: list[str]
```

필수 원칙:

- `raw_text`와 `cleaned_text`를 구분한다.
- Line별 Text·Confidence·Page를 가능한 모든 OCR 경로에서 보존한다.
- Paddle Box가 있으면 읽기 순서 정렬에 사용한다.
- Native PDF와 Office 직접 추출 결과를 OCR Line으로 억지로 위장하지 않는다. 필요한 경우 Source가 다른 Text Block 계약을 추가하거나 `lines`에는 실제 OCR Line만 둔다.
- 평균 Confidence의 분모와 빈 결과 정책을 Test로 명시한다.
- 사용자 수정본은 원본 결과를 덮어쓰지 않으며 Backend/DB에서 별도로 다룬다.

지나친 Generic, Event Bus, 복잡한 Factory 계층을 만들지 않는다. 실제로 PDF와 Office에서 OCR Engine을 교체하기 위해 필요한 작은 Protocol과 Factory만 사용한다.

## 8. 중심 함수 요구사항

`ai/ocr`에는 전체 실행 순서를 한눈에 읽을 수 있는 중심 함수가 하나 있어야 한다.

예시:

```python
def analyze_document(
    document: OcrDocumentInput,
    config: OcrProcessingConfig,
    progress_callback: ProgressCallback | None = None,
) -> OcrDocumentResult:
    # 1. 파일명, MIME, Binary 구조와 제한을 검증한다.
    validated = validate_document(document, config)

    # 2. Image/PDF/Office 형식에 맞는 추출 함수를 호출한다.
    extracted = extract_document(validated, config, progress_callback)

    # 3. 추출 원문은 보존하고 공통 Text 정제 결과를 만든다.
    cleaned_text = clean_document_text(extracted.raw_text)

    # 4. Line, Confidence, Warning과 문서 메타데이터를 결과로 조립한다.
    return build_document_result(extracted, cleaned_text)
```

함수명은 실제 코드에 맞춰 조정할 수 있지만 다음 흐름이 중심 함수에서 보여야 한다.

```text
입력 → 검증 → 형식별 추출 → 원문 보존 → Text 정제 → 공통 결과 반환
```

세부 함수는 결과를 중심 함수로 반환해야 한다. PDF Parser가 Chunking이나 DB 저장까지 다음 흐름을 몰래 이어서 실행하게 만들지 않는다.

주요 단계에는 이유와 데이터 이동을 설명하는 한국어 주석을 작성한다.

## 9. 이미지 전처리 통합 규칙

두 구현의 전처리를 단순히 전부 직렬 적용하지 않는다.

현재 기능 후보:

```text
Hybrid OCR
- EXIF 방향 적용
- 투명 배경을 흰색으로 합성
- Pixel 제한
- 최대 변 Resize

기존 ai/ocr
- OpenCV Decode
- 최대 변 Resize
- Denoise
- Hough Line 기반 Deskew
```

권장 순서는 다음과 같다.

```text
Binary Decode
→ EXIF 방향 반영
→ 투명 배경 처리
→ Pixel/크기 제한
→ 필요 시 Resize
→ 검증된 경우에만 Denoise
→ 검증된 경우에만 Deskew
→ Paddle 입력 형식으로 한 번 변환
```

필수 조건:

- 정상 가로 Text를 Deskew가 90도 가까이 돌리지 않아야 한다.
- 큰 이미지를 두 번 Resize하지 않아야 한다.
- PIL↔NumPy↔OpenCV 변환을 반복하지 않는다.
- PDF Page, Office 포함 Image, 일반 Image가 같은 공통 전처리를 사용한다.
- Denoise/Deskew 적용 여부는 실제 Fixture Test로 결정한다.
- 결과가 불명확하면 기존 Hybrid 안전 처리와 기존 서비스 품질을 둘 다 보존할 수 있는 명시적 Option을 사용하되 Endpoint마다 영구적으로 갈라진 별도 Pipeline은 만들지 않는다.

## 10. PaddleOCR Engine 통합 규칙

PaddleOCR 생성과 `predict()` 호출은 최종적으로 한 구현에만 존재해야 한다.

반드시 유지할 기능:

- Lazy Loading
- 동일 설정 Engine Cache
- 초기화 Lock
- 추론 Lock 또는 동등한 동시성 제한
- CPU/GPU 설정과 기존 CPU Fallback 의미
- `enable_mkldnn=False` 호환 처리
- 사용자에게 내부 오류나 민감한 값을 그대로 노출하지 않는 Domain 예외
- Box 기준 위→아래·왼쪽→오른쪽 정렬
- Line Text, Confidence, Page 전달
- 처리 시간 또는 기존 상위 계층이 사용하는 집계값

결정이 필요한 Paddle Option:

- `use_textline_orientation=True/False`
- `ocr_version`
- `lang`/`language`
- PaddlePaddle/PaddleOCR 지원 버전

이 값은 추측으로 바꾸지 않는다. 현재 설치 버전, 기존 Test, 실제 Smoke Test 가능 여부를 확인하고 결정 근거를 작업 보고서에 기록한다.

실제 모델 Test가 환경 또는 Download 문제로 실행되지 않았다면 단위 Test만 통과한 상태와 실제 Paddle 검증 미실행 상태를 명확히 구분한다.

## 11. 파일 형식별 처리 규칙

### 11.1 일반 Image

```text
검증된 Bytes
→ 공통 Image 전처리
→ 단일 Paddle Engine
→ Line 정렬 및 Confidence 계산
→ 공통 결과로 반환
```

### 11.2 PDF

현재 Hybrid 방식의 다음 분기를 유지한다.

```text
페이지 Native Text가 충분함 + 유효 Image 없음
→ Native Text 추출

페이지 Native Text 부족
→ Page 전체 Rendering
→ OCR

Native Text + 유효 Image 공존
→ Native Text Block과 Image OCR을 문서 순서대로 결합
```

모든 PDF Page를 무조건 OCR하는 기존 단순 경로는 호환 Wrapper 안에 별도 Engine으로 남기지 않는다. 새 공통 PDF 처리 결과를 `/documents/ocr` Adapter가 기존 Response 형태로 변환한다.

### 11.3 DOCX/PPTX

- OOXML Text 직접 추출을 유지한다.
- 포함 Image만 공통 전처리와 단일 Paddle Engine에 전달한다.
- 문단·표·Slide·Note·Image의 기존 순서를 보존한다.
- ZIP Path Traversal, 압축 해제 크기, Entry 개수 검증을 약화하지 않는다.

## 12. Backend Adapter 구현 규칙

### 12.1 서비스 문서 OCR Adapter

`backend/app/api/documents/router.py` 안에서 무거운 OCR 단계를 직접 구현하지 않는다.

권장 흐름:

```text
Router
→ 인증 확인
→ 제한 크기까지 UploadFile 읽기
→ Backend OCR Adapter 호출
→ Adapter가 OcrDocumentInput과 Config 구성
→ asyncio.to_thread(ai.ocr.analyze_document, ...)
→ OcrDocumentResult 반환
→ 기존 OcrResponse로 변환
→ Router로 반환
```

Router의 역할은 HTTP 입력, 인증, 오류 변환, Response 반환으로 제한한다.

### 12.2 Admin OCR Adapter

Admin Job과 Vector Save를 `ai/ocr` 안으로 옮기지 않는다.

권장 흐름:

```text
OcrJobManager
→ Backend Admin OCR Workflow
→ ai.ocr.analyze_document()
← OcrDocumentResult
→ 기존 문자 Chunk 생성
← chunks
→ OcrDocumentResponse 조립
← Job Manager
```

기존 `OcrProcessor` Callable 계약을 유지하거나 작은 Adapter로 호환한다. Job Test를 불필요하게 다시 작성하지 않는다.

### 12.3 설정 조립

환경 변수는 계속 Backend `Settings`가 읽는다.

```text
app.core.config.Settings
→ Backend에서 OcrProcessingConfig 생성
→ ai/ocr에 값 전달
```

`ai/ocr`이 `.env` 위치나 Pydantic Settings를 직접 알아서는 안 된다.

## 13. 권장 파일 이관 기준

정확한 파일명은 현재 구조와 가독성을 우선한다. 다음은 책임 기준이다.

| 현재 파일 | 처리 방향 |
|---|---|
| `ai/ocr/pipeline.py` | 단일 중심 함수와 `run_ocr` 호환 Wrapper를 둔다 |
| `ai/ocr/preprocessing.py` | Hybrid Image 안전 처리와 기존 Denoise/Deskew를 통합한다 |
| `ai/ocr/postprocessing.py` | Line 정렬·Confidence·중복 제거·Text 정제를 통합한다 |
| `hybrid_ocr/models.py` | Backend 의존 없는 `ai/ocr` Domain 계약으로 옮긴다 |
| `hybrid_ocr/errors.py` | `ai/ocr` Domain 예외로 옮긴다 |
| `hybrid_ocr/document_validator.py` | `UploadFile` 읽기와 Bytes 검증을 분리해 Core 부분만 옮긴다 |
| `hybrid_ocr/image_preprocessor.py` | `ai/ocr/preprocessing.py`와 중복 없이 합친다 |
| `hybrid_ocr/paddle_ocr_service.py` | 유일한 Paddle Engine 구현으로 `ai/ocr`에 옮긴다 |
| `hybrid_ocr/pdf_parser_service.py` | `ai/ocr` PDF 추출 Module로 옮긴다 |
| `hybrid_ocr/office_parser_service.py` | `ai/ocr` Office 추출 Module로 옮긴다 |
| `hybrid_ocr/text_cleaner.py` | 공통 Postprocessing 또는 명확한 Text Cleaner로 옮긴다 |
| `hybrid_ocr/document_processing_service.py` | OCR Core 중심 함수와 Backend Adapter로 분해한다 |
| `hybrid_ocr/chunk_service.py` | 이번 단계에서는 OCR Core 밖 Backend에 유지 가능하다 |
| `ocr_job_service.py` | Backend에 유지한다 |
| `admin_ocr.py` | Embedding/DB Workflow이므로 Backend에 유지한다 |
| `embedding_service.py` | 이번 작업에서 이동하지 않는다 |

분석 문서의 예시대로 폴더를 지나치게 세분화할 필요는 없다. 초심자가 `pipeline.py`에서 전체 흐름을 확인할 수 있는 최소 구조를 사용한다.

## 15. 테스트 요구사항

### 15.1 Test 위치와 책임 분리

OCR Core Test를 제품 Package 내부인 `ai/ocr/tests`에 두지 않는다. 현재 `pyproject.toml`은 `ai*`를 Package 대상으로 탐색하고 Dockerfile도 `ai/ocr` 전체를 복사하므로, 이 위치에 Test를 두면 배포 Package와 Image에 Test·Fixture가 함께 포함될 수 있다.

권장 Test 구조는 다음과 같다.

```text
tests/
├─ __init__.py
├─ fixtures/
│  └─ ocr/
│     ├─ images/
│     ├─ pdf/
│     └─ office/
├─ ai/
│  ├─ __init__.py
│  └─ ocr/
│     ├─ __init__.py
│     ├─ test_pipeline.py
│     ├─ test_validation.py
│     ├─ test_preprocessing.py
│     ├─ test_paddle_engine.py
│     ├─ test_pdf_parser.py
│     └─ test_office_parser.py
└─ smoke/
   └─ test_paddle_ocr.py

backend/
└─ tests/
   ├─ test_document_ocr_api.py
   ├─ test_admin_ocr.py
   ├─ test_ocr_jobs.py
   └─ test_ocr_vector_save.py
```

책임은 다음처럼 나눈다.

| 위치 | 검증 책임 |
|---|---|
| `tests/ai/ocr` | Framework 독립 OCR 입력·검증·전처리·Engine·Parser·Pipeline |
| `backend/tests` | FastAPI Adapter, 인증, HTTP 계약, Job, Chunk, Embedding, DB 저장 |
| `tests/fixtures/ocr` | 양쪽 Test가 함께 사용하는 최소 Image·PDF·DOCX·PPTX Fixture |
| `tests/smoke` | 실제 Paddle Model 초기화·Download·추론이 필요한 선택 실행 Test |

`tests/ai/ocr` Test는 다음 Module을 Import하지 않아야 한다.

```text
fastapi
app.*
sqlalchemy
UploadFile
TestClient
```

현재 `backend/tests/test_hybrid_ocr.py`에 섞여 있는 검증 중 PDF·Image·DOCX·PPTX 처리, 전처리, Paddle 결과 Parsing처럼 Core 책임에 해당하는 Test는 `tests/ai/ocr`로 이관한다. Router Response, Job, Vector Save처럼 Backend 책임에 해당하는 Test는 `backend/tests`에 유지한다.

기존 Test를 먼저 새 Core Import로 통과시킨 다음에만 중복 Test를 제거한다. Test를 이동한다는 이유로 Assertion을 줄이거나 Fixture 검증을 약화하지 않는다.

### 15.2 OCR Core Unit Test

- 빈 파일과 지원하지 않는 확장자 거부
- MIME과 Binary 불일치 거부
- 최대 파일 크기와 PDF 페이지 제한
- Office 압축 Entry와 해제 크기 제한
- PNG/JPEG Image OCR
- EXIF 방향 반영
- 투명 배경 처리
- 큰 Image Resize
- Deskew 안전성
- Box 읽기 순서
- Confidence 경계값
- 연속 중복 Line 제거
- Raw/Cleaned Text 분리
- Digital PDF는 OCR을 호출하지 않음
- Scanned PDF는 Page OCR 호출
- Hybrid PDF는 Native Text와 Image OCR 순서 보존
- DOCX/PPTX Text 직접 추출
- DOCX/PPTX 포함 Image OCR
- Engine Lazy Loading과 추론 직렬화

### 15.3 Backend Contract Test

- `/api/documents/ocr` Response가 기존 Schema와 일치
- 인증 Dependency 유지
- `/api/admin/ocr/analyze` 기존 Response 유지

- Chunk 순서와 개수 유지

동일한 Image 입력을 서비스 Adapter와 Admin Adapter에 전달했을 때 OCR Text와 실제 OCR Line 결과가 같은 Core에서 나오는지 검증한다. Admin 쪽에서 Chunk와 Notes가 추가되는 차이는 허용한다.

### 15.5 실행 명령

실제 환경을 확인한 후 존재하는 명령만 실행한다. 현재 저장소 기준 기본 후보는 다음과 같다.

OCR Core Test는 프로젝트 최상위에서 실행한다.

```powershell
backend\.venv\Scripts\python.exe -B -m unittest discover -s tests -t . -p "test_*.py" -v
```

Backend Test는 `backend`를 작업 디렉터리로 사용해 `app` Import 경로를 유지한다.

```powershell
Set-Location backend
$env:PYTHONPATH = (Resolve-Path ..).Path
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_*.py" -v
```

실제 Paddle Model Test는 기본 Unit Test에 포함하지 않는다. Model Download, CPU/GPU 환경과 긴 실행 시간이 필요한 `tests/smoke/test_paddle_ocr.py`는 명시적인 환경변수 또는 별도 명령이 있을 때만 실행하고, 미실행 상태를 완료 보고서에 기록한다.

Frontend 코드를 수정하지 않았더라도 API 계약 영향 확인이 필요하면 다음을 실행한다.

```powershell
cd frontend
npm.cmd run build
```

추가 확인:

```powershell
git diff --check
rg -n "from app|import app|fastapi" ai/ocr
rg -n "PaddleOCR|run_ocr|process_document|hybrid_ocr" ai backend
```

실행하지 않은 Test나 실제 Paddle Smoke Test를 통과했다고 보고하지 않는다.

## 16. Requirements와 배포 검증

현재 OCR Dependency가 `ai/ocr/requirements.txt`와 `backend/requirements.txt`에 중복 또는 다른 범위로 존재하는지 확인한다.

목표:

- OCR Dependency의 기준 파일을 명확히 한다.
- Backend는 같은 기준을 참조한다.
- PaddlePaddle과 PaddleOCR의 호환 범위를 실제 사용 옵션과 맞춘다.
- 사용하지 않게 된 PDF Renderer Dependency를 제거한다.
- 불필요한 무거운 RAG Dependency를 OCR 때문에 설치하지 않는다.

Dockerfile은 최소한 다음을 만족해야 한다.

```text
- 새 ai/ocr Package가 Image에 포함된다.
- Backend App에서 ai.ocr Import가 성공한다.
- requirements 상대 경로가 Docker Build Context에서 유효하다.
- 삭제된 hybrid_ocr Import 때문에 App 시작이 실패하지 않는다.
```

실제 Docker Build를 실행하지 못했다면 정적 확인과 미실행 사실을 완료 보고서에 구분해 기록한다.

## 17. 예외와 로그 규칙

### 예외

- `ai/ocr`은 HTTP 상태 코드를 알지 못하는 Domain 예외를 발생시킨다.
- Backend Adapter 또는 Router가 기존 HTTP 상태로 변환한다.
- 모든 함수에 무조건 `try/except`를 추가하지 않는다.
- 오류를 처리하거나 의미를 추가할 수 있는 계층에서만 잡는다.
- 원래 예외는 `raise ... from exc`로 연결한다.

### 로그

주요 단계만 기록한다.

```text
OCR 시작
문서 검증 완료
문서 형식 판별
형식별 추출 완료
OCR Image 수와 Page 수
Text 정제 완료
Admin Chunk 생성 완료
OCR 완료 또는 실패
```

다음 값은 기록하지 않는다.

- API Key
- Token
- DB Password
- JWT Secret
- 전체 OCR 원문
- 사용자의 의료·개인정보
- `.env` 실제 값

5. 추가·이동·수정·삭제한 파일별 역할
6. 파일 간 호출 관계 표
7. `/documents/ocr` Request/Response 유지 내용
8. Admin Job과 Vector Save 연결 유지 내용
9. 실제 OCR과 Mock 사용 여부
10. Requirements와 Docker 변경 내용
11. 실행한 Test 명령과 실제 결과
12. 실행하지 못한 검증
13. 남은 위험과 후속 작업
14. LLM 이관과 Admin 배포 제외가 이번 범위 밖임을 명시

기존 분석 문서나 Prompt 문서를 작업 완료 보고서로 덮어쓰지 않는다.

## 20. Codex 최종 보고 형식

작업이 끝나면 사용자에게 다음 순서로 간단히 보고한다.

```text
1. 구현 결과
2. 단일 OCR 중심 함수와 최종 호출 흐름
3. 주요 추가·수정·삭제 파일
4. API 호환 여부
5. Test와 Build 결과
6. 생성한 docs/2_reports 문서 경로
7. 실행하지 못한 검증과 남은 후속 작업
```

단순히 “통합 완료”라고 쓰지 말고 다음 흐름을 실제 함수명과 파일명으로 보여준다.

```text
Request
→ Router
→ Backend Adapter
→ ai/ocr 중심 함수
→ 검증
→ 형식별 추출
→ 공통 결과 반환
→ Adapter Response 변환
→ Router
→ HTTP Response
```

# 최종 구현 원칙

```text
Admin Hybrid OCR의 풍부한 문서 처리 기능
          +
기존 ai/ocr의 재사용 구조와 Line·Confidence·전처리 기능
          ↓
Framework 독립 ai/ocr 단일 Core
          ↓
기존 서비스 API와 Admin API가 Adapter를 통해 공동 사용
```

폴더 이동 자체가 목표가 아니다. **같은 OCR 입력이 하나의 검증·전처리·Engine·후처리 경로를 사용하도록 만들고, 기존 호출자와 협업 코드를 안전하게 보존하는 것**이 이번 작업의 완료 기준이다.
